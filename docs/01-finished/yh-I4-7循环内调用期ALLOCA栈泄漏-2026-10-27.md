# I4-7 循环内调用期 ALLOCA 栈泄漏（2026-10-27）

## 结论

`yh` 的 ALLOCA 由 lowering 在**调用点所在基本块**发出，落在循环体里就每次
迭代再分配一份栈空间且不回收。56 字节结构体临时攒够 8 MB 栈后进程段错误，
与优化级无关。修复方式是把全函数 ALLOCA 统一提到**入口块**只发一次，槽位
跨迭代复用；ALLOCA 的语义因此收敛为「常量大小、按调用期存活的临时槽」。

这不是 fmt 的问题，但它是「输出全部走 fmt」的前置缺陷：fmt 打印族的惯用
写法 `fmt.print([fmt.of_int(i), …])` 每次调用都会产生聚合临时，正是本缺陷
的触发形态。

## 复现（修复前，纯 yh 单文件即可）

```yh
struct Big { a int  b int  c int  d int  e int  f int  g int }

fn make_big(i int) Big { return Big{ a: i, b: i, c: i, d: i, e: i, f: i, g: i } }
fn take(items []Big) int { return len(items) }

fn main() int {
    let i int = 0
    for i < 600000 {
        let n int = take([make_big(i), make_big(i)])   // 每次迭代泄漏 112 字节栈
        if (n != 2) { return 1 }
        i += 1
    }
    return 0
}
```

```
$ ./yh tmp/leak.yh -o tmp/leak && ./tmp/leak
Segmentation fault: 11          # 约 3.7 万次迭代后栈溢出
```

lldb 停在 `memcpy` 的第一条指令（`str x0, [sp]` 落在栈守卫页），说明是栈
耗尽而不是访存越界。对应 IR 证据（修复前的模块主函数）：

```
b3:                                  # 循环体
  %v7  = alloca i8, i64 16, align 8   # 切片头临时
  %v8  = alloca i8, i64 16, align 8
  %v10 = alloca i8, i64 56, align 8   # 结构体返回值槽
  %v15 = alloca i8, i64 56, align 8
```

## 根因

`compiler/lower/module_snapshot_lower_call.yh` 在传聚合实参（`:76`）、类型化
变参聚合元素（`:55`）、变参打包（`:137`）、结构体返回缓冲（`:155`/`:237`）
时就地调用 `ast_ir_b_add_alloca`。`ir/ssa.yh` 的入口块提升规则只覆盖变量
绑定（`IR_OP_ADDR`），没有覆盖这些调用期临时，于是 ALLOCA 留在了执行块里。

## 修复

- `compiler/backend/llvm_scalar.yh`：新增 `llvm_alloca_inst` 与
  `llvm_function_allocas`；`llvm_function` 在入口块一次性发射全函数 ALLOCA，
  插入点取入口块**前导 PHI 之后**（LLVM 要求 PHI 聚在块首；入口块只有 PHI
  或为空时插入点落到指令循环之后）；`llvm_instruction` 的 ALLOCA 分支改为
  按位置跳过。
- `compiler/ir/ssa.yh`：`IR_OP_ALLOCA` 注释补语义约束（常量大小、按调用期
  存活、后端提到入口块发射，不得表达按迭代/分支增长的存储）。

选择后端提升而不是 lowering 预分配的理由：ALLOCA 只有一处发射点，后端改造
无需重排指令编号，也不会遗漏后续新增的调用期临时（变参打包、返回缓冲等）。
语义安全性依据：yh 的 ALLOCA 大小是常量、生命周期是单次调用；同一指令在
一次迭代里只执行一次，跨迭代复用同一槽位不影响结果。切片字面量逃逸场景
本来就「不在本帧分配」（`l.slice_storage[scan] = -1`），不受影响。
