# yh_libs 重复装载导致 Linux/Windows「duplicate symbol」（2026-11-15）

## 1. 症状

`release.yml` 四端里 **linux-x64 / linux-arm64 / windows-x64 红、darwin-arm64 绿**，
失败点都在 `just ci-gate` 的第一步（用上一版种子 0.0.14 构建 `compiler/`）：

```
  [编译] sys            ← 同一次构建里出现两次
  …
  [编译] cli
ld.lld: error: duplicate symbol: is_error__yh_libs__sys_$yhllvmv1
>>> defined at api.yh
>>>            .build/…/obj/yh_libs-sys.o:(is_error__yh_libs__sys_$yhllvmv1)
>>> defined at api.yh
>>>            .build/…/obj/yh_libs-sys.o:(.text.is_error__yh_libs__sys__Syhllvmv1+0x0)
```

要点：

- 两处定义都在**同一个 .o 路径**上 → 同一个对象文件被加入链接两次；
- 对象本身是干净的（`llvm-readelf -s` 只有一个 `GLOBAL FUNC` 定义），不是 codegen 重复发射；
- 0.0.14 正式版那次（四端全绿）linux 只装载一次 `sys`，这是 0.0.14 之后引入的回归；
- Darwin 绿只是因为 ld64.lld 容忍同一对象重复出现。

## 2. 本地（Darwin 宿主）无法复现的部分

种子 `bin/yh-darwin-arm64` 的 sha256 与 CI 拉的 0.0.14 种子一致，源码同一提交，但本地：

| 变量 | 结果 |
| --- | --- |
| 原生 darwin target | 29 模块，`sys` 一次 |
| `--target x86_64-unknown-linux-gnu` | 29 模块，`sys` 一次 |
| `--target x86_64-pc-windows-msvc` | 27 模块（后续在别处失败），`sys` 一次 |
| 种子用相对 / 绝对 `argv[0]` | 都一次 |
| `git archive` 纯净副本 + 冷缓存 | 都一次 |

结论：与「目标文件集」无关（三个 target 都试过），复现需要 Linux 宿主。

## 3. 诊断作业（临时 workflow，用完已删）

分支 `diag/libs-dup` + `.github/workflows/diag-libs.yml`，三轮：

| 轮次 | 作业内容 | 结果 |
| --- | --- | --- |
| 1（run `43703197687`） | 种子构建 + `strace -f -e openat,getdents64` | Linux 上 `sys` 两次；trace 显示 `libs` 树被**两套路径拼写**各完整扫描一次 |
| 2（run `43703755818`） | 直接调种子，比较 `YH_STDLIB` 拼写 | 相对拼写 → 29 行 1 次；绝对拼写 → 30 行 2 次 |
| 3（run `43703985707`） | 与 CI 完全等价的 `seed-build.py` 调用 | 现状 30 行 2 次；`YH_STDLIB=../libs` 29 行 1 次 |

第 1 轮 trace 的关键事实（`libs` 每个子目录都出现两次，一绝对一相对）：

```
openat(AT_FDCWD, "/home/runner/work/x/x/libs/sys", O_RDONLY|O_DIRECTORY) = 3
openat(AT_FDCWD, "../libs/sys",                     O_RDONLY|O_DIRECTORY) = 3
…（cli / fmt / hash / io / json / libc / list / math / memory / net /
   num / os / string / testing / time / toml 同样各两次）
```

## 4. 根因

`compiler/build/api.yh` 的 `load_project()` 用 **root 路径的字节比较**判断项目是否
已装载（`proj.find_project_root`，见 `compiler/build/api.yh:1369` 与
`compiler/build/proj/api.yh:1494`）。同一个 `libs` 目录在 Linux 上被两条不同来源、
不同拼写的路径各装载一次：

- **标准库自动发现**：`mb_load_default_stdlib` 取种子的 `argv[0]` 目录拼
  `<bin>/../libs`，canon 后是**绝对路径** `/home/runner/work/x/x/libs`；
- **清单依赖**：`compiler/project.toml` 的 `[dependencies] libs = {path = "../libs"}`
  保留**相对拼写** `../libs`（canon 不做绝对化）。

两条路径字节不同 → 两个 PProj 记录，但都从各自清单读到 `project.name = "yh_libs"`
→ 产物标签都是 `yh_libs-sys`、符号名都是 `__yh_libs__sys` → 同一个
`.build/…/obj/yh_libs-sys.o` 出现在链接参数里两次。

`mod_dir_dup`（`compiler/build/proj/api.yh:190`）只按「同项目内同名模块数 > 1」判定，
两个项目各含一个 `sys`，所以目录指纹不生效——这也解释了为什么日志里的符号名
没有指纹。

未逐边核实的一点：两个项目都各被完整索引，但 `order` 里只有 `sys` 重复
（其余 libs 模块只出现一次）。第 4 节的结构性修复完成后该问题自然消失，故不再逐边追溯。

## 5. 修复（本次发布可生效）

改的是**构建脚本**，不是编译器自身逻辑——因为红的那一步由 0.0.14 种子执行，
种子编译进去的装载逻辑改不动，只有「喂给种子的输入」可以改。

`justfile` 的 `build` 与 `dev` 给种子构建设置 `YH_STDLIB=../libs`，让标准库根与
`[dependencies]` 用**同一种相对拼写**（基准是 `seed-build.py` 的工作目录
`<root>/compiler`），两个来源因此命中同一个项目。

验证（run `43703985707`，CI 等价调用）：

- 不加变量：`sys` 2 次、模块行 30（复现）；
- `YH_STDLIB=../libs`：`sys` 1 次、模块行 29。

本地（darwin）三门全绿：`just dev`、`just test`（389/391，2 跳过）、
`just selfhost-native`（固定点一致、project cases 125/125）。

## 6. 遗留（已进 `docs/todo.md`）

1. **项目身份规范化**：`load_project` / `find_project_root` 应先把 root 规范成绝对
   路径再比较，从根上消灭「同一目录两种拼写 = 两个项目」；它只对新种子生效。
2. **链接参数对象去重**：`mb_link_args` 按对象路径去重（并可在重复时给出诊断），
   作为任何来源重复的兜底。
3. **目录枚举一致化**：`project_dir.linux.*.yh` 的 `d_type == 4` 对 `DT_UNKNOWN`
   没有兜底（darwin 的 `getattrlistbulk` 总是给真实类型）；应补
   `openat(O_DIRECTORY|O_NOFOLLOW)` 探测，避免不同文件系统下目录被判成文件。
4. **构建脚本不该承担语义**：`YH_STDLIB` 的作用是绕过「两条装载路径拼写不一致」，
   编译器自身修好后应删除该变量，恢复 `just dev` 的原有形态。
