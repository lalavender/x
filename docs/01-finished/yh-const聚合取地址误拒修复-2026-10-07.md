# const 聚合常量取地址：修掉我自己引入的误拒

日期：2026-10-07。状态：已完成。修正第 34 轮「只读性」改动过严带来的误拒。

## 怎么发现的（探针驱动）

第 41 轮用三个探针摸编译期能力边界：

| 探针 | 写法 | 结果 |
| --- | --- | --- |
| A | `$first(&TABLE[0])`（全局 const 数组取地址作编译期实参） | 报「不能给 const 聚合常量赋值**或取地址**」 |
| B | `pub const ALIAS *char = TEXT;`（引用式指针常量，单文件） | `rc=0`（可用；跨模块才是第 40 轮修的那条） |
| C | 编译期正文里 `let p *char = TEXT; (*p)` | `rc=0`（可用） |

探针 A 的诊断暴露了问题：第 34 轮为了堵住「聚合常量可被写入」，在 `sem_ident_val` 的降级分支里
用 `c_lvalue != 0` 判断，但 **`c_lvalue` 同时表示「赋值目标」和「取地址」**：

- 赋值语句：`parse_stmt.yh:238` `gs.c_lvalue += 1`（0 → 1）
- 取地址：`parse_expr.yh:602` `gs.c_lvalue += 1`（0 → 1）

两者值域完全相同，所以 `&TABLE[0]`、`&ORIGIN.y` 这类**只读引用**被一起拒了 —— 而 C 里
`&const_obj` 是合法的。

## 改动（两处，各几行）

1. `compiler/parse/parse_expr.yh` 取地址处把 `gs.c_lvalue += 1` 改成 **`+= 2`**：其余所有
   `c_lvalue != 0` 的判断语义不变（仍是「处于左值上下文」），但从此能与赋值区分。
2. `compiler/gen/sem_value.yh` 的只读检查由 `c_lvalue != 0` 改为 **`c_lvalue == 1`**，
   诊断去掉「或取地址」：`不能给 const 聚合常量赋值`。

## 效果

| 写法 | 之前 | 现在 |
| --- | --- | --- |
| `const_agg.f = v;`（赋值） | 拒绝 | 拒绝（诊断更准） |
| `&const_agg.f`、`&const_arr[i]`（只读引用） | **误拒** | **可用** |
| `let p *int = &const_arr[0]; *p`（运行期读） | **误拒** | **可用** |

探针 A 的诊断随之变成「**变量不是编译期常量**」—— 这是**正确**的边界：`&TABLE[0]` 是运行期地址，
本来就不能当编译期实参（与只读性无关）。
