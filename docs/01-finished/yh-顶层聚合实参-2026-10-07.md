# 顶层编译期调用的聚合实参（CT3 主体）

日期：2026-10-07。状态：已完成（结构体字面量、字段全标量）。承接第 32/33 轮的顶层聚合常量。

## 问题

`const R int = $take(Point{ x: 3, y: 4 });` 此前被拒绝：顶层编译期调用的实参由前端求值成
`args [64]gen.Res`（`parse_expr.yh`），而 `Res` 只有 `ival`/`sym`/`is_const` 一类标量字段，
没有聚合值表示；编译期函数体内之所以可以，是因为那边实参走 typed IR（`ct_ir_args_fill`），
在执行器 arena 里构造聚合。

## 关键观察（决定了不需要动调用协议）

执行器本来就把**聚合实参的 `CtValue.value` 当作对象指针**使用。所以只要前端能拿到一个
「字段值区」对象指针，把它写进 `Res.ival`、`is_const = 1`，`ct_call` 与执行器就会自然按聚合
处理 —— **`ct_call` 一行都不用改**（实测确认：`ct_call` 无条件把 `args[i].ival` 写进
`values[i].value`，聚合与标量走的是同一条赋值）。

## 改动

### 1. `compiler/comptime/ct_ir.yh`：顶层聚合实参的临时构造区（新增约 25 行）

顶层调用没有 CT 帧，所以给前端开一个独立的全局帧：

```yh
let ct_arg_pool CtFrame;                       // 只服务顶层聚合实参
pub fn ct_arg_pool_reset() void;               // 会话开始清零
pub fn ct_arg_pool_struct(type_id int, vals *i64, tys *int, n int) i64;
```

- 参数用**扁平标量数组**（值 + 各自类型）而不是 `CtValue` 数组：调用方在 parse 侧，拿不到
  comptime 私有类型 `CtValue` 的构造能力（第一版就栽在这里，报「模块没有导出该类型」）。
- 复用 `ct_ir_aggregate_new`，它只用到帧的 `aggregates` 与 `aggregate_element_count` 两个字段，
  所以独立全局帧不需要别的初始化。
- **区只增不减**：借用出去的对象可能被结果池 `ct_ir_result_pool_keep`，主动释放有悬空风险；
  总量由 `ct_ir_aggregate_new` 的 100000 元素上限兜住。

### 2. `compiler/parse/parse_expr.yh`：折叠 + 跳过重解析（约 90 行）

- 新增 `p_ct_arg_struct_literal(res, tid)`：解析 `类型名 { 字段: 表达式, ... }`，字段按**声明
  顺序**填位（字面量里可以乱序）、按字段类型 `sem_can_assign` 检查、用 `c_fold += 1` 折叠成常量，
  再调 `ct_arg_pool_struct` 拿到对象指针。不支持的形态（非该类型名、聚合字段、非聚合常量字段）
  返回 1 交调用方诊断。
- 原拒绝点改为：结构体形参先尝试折叠；折成功则置 `folded = 1`，实参循环**跳过**
  `parse_expr_iso`（字面量已被消费完；不跳过会报「此处需要一个表达式」）。
- 剩余不支持的形态保留拒绝，诊断改为可操作表述：
  「编译期调用实参里的聚合值暂时只支持字段全是标量的结构体字面量：数组、切片、联合体与嵌套聚合字段仍需在 `@[comptime]` 函数体内构造」。
