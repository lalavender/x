# 枚举判别值里编译期调用的可读诊断

日期：2026-10-07。状态：已完成（诊断加固；支持路径已立项）。

## 缺陷（诊断质量）

枚举判别值里写编译期调用时，报的是与用户代码无关的内部措辞：

```yh
@[comptime] fn two() int { return 2; }
pub enum Palette {
    red = $two() + 1;
    green;
}
// 错误: 编译期函数正文不在受支持的 typed IR 子集内
```

`two` 的正文完全在受支持子集内，真正的原因是**求值时机**：判别值在 pass1 折叠成常量，
而编译期函数的 typed 正文要到 pass2 才捕获，pass1 里没有可执行的正文。用户看到这句话
会去检查函数体，方向完全错。

## 本轮改动

`compiler/parse/parse_decl.yh` 的枚举成员判别值解析：在求值**之前**扫描判别值 token
区间（以 `;` 或 `}` 结束），只要出现 `$`（编译期调用）就直接给出可读诊断：

```
枚举判别值里的编译期调用暂不支持（需要延迟到正文捕获之后求值），请改用纯常量表达式
```

扫描不区分 `$` 出现在表达式哪个位置，因为任何位置的编译期调用在 pass1 都不可求值。

## 顺带确认的边界

| 写法 | 结果 |
| --- | --- |
| `red = 5; green; blue;`（隐式递增，在编译期函数体内引用成员） | 正常（run/93 通过，`green:7`、`blue:8`） |
| `red = $two() + 1;` | 新诊断（fail/149） |
| 顶层 `const V int = Palette.green.to_type(int);` | 「引用了未声明的名字」—— 顶层引用枚举成员是另一个缺口，已立项 |

## 遗留

真正支持判别值里的编译期调用需要延迟求值：pass1 只登记成员符号（值待定），pass2
捕获正文后重解析枚举声明求值并回填 `cval`/`const_ready`。重解析会重走 `sym_push` 与
类型项创建，因此需要像 `iface_ct.yh` 那样保存并恢复 `c_sym_n`、`t_type_n` 等计数，
只取值不回填。已记入 `docs/todo.md`，与「顶层聚合实参」「顶层枚举成员引用」同属
CT1/CT2 统一入口方向。
