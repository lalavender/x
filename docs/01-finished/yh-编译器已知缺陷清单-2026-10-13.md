## 二、新发现并修复：SSA 字面量适配（两处）

原清单第 5 项的「SSA 混合宽度」在新语料上换了个形态复现：**SSA 降低路径把
整数字面量按它自己的类型（i32）装入**，需要 64 位时再经 CAST 扩展。

复现（模块模式，函数进入 SSA：`--stats ir_functions=1`）：

```yh
module m;
pub const BIG u64 = 0x80000000;
pub fn is_big(v u64) bool { return v == 0x80000000; }
```

`c.BIG != 0x80000000` 静默判不等、`c.is_big(0x80000000)` 收到
`0xFFFFFFFF80000000`；同一函数加上一次 `printf` 反而正常（该调用让函数退出
SSA 子集、回落旧发射器），因此只在「整个函数都能进 SSA」时暴露。IR 缓存
（`tmp/g1/dump-ir.py` 解析 `.build/ir/*.ir`）里能看到
`const r55:i32 imm=2147483648` 与 `call is_big(v55:i32)`。

修法（与旧语义层 `sem_binop` 的「字面量适配」同判据）：

- `ast/ast_ir_build.yh` 二元运算：整数字面量能落进另一侧整数类型时按另一侧
  类型取值（`gen.sem_lit_fits` 提为 pub 共用），并就地重定型常量指令；
- `ast/ast_ir_call.yh` 调用实参：按**形参类型**重定型字面量常量指令；支持性
  检查同步放宽（字面量适配放行），非字面量类型不一致仍整体回退旧发射器。

## 三、新发现并修复：寄存器同名符号（清单第 10 项）

`clang-21`（`/usr/bin/clang-21`）实测：`bl w12` 报
`error: expected label or encodable integer pc offset`，`adrp x0, w12` 接受；
GNU as 两者都接受。旧发射器把用户符号原样写出，于是同一份 `.s` 在 Linux/GNU
可汇编、在 clang 集成汇编器下不可汇编（macOS 因 `_` 前缀躲开，单文件 GNU
目标躲不开）。

修法（`gen/emit_arm64.yh`）：新增 `sym_is_reg_name`（x0-x30、w0-w30、
s/d/q/v/b/h0-31、sp/lr/fp/xzr/wzr）与 `sym_reg_guard_needed`——只在**最终
汇编名**恰好是寄存器名时（无 Darwin `_` 前缀、无模块后缀、非 extern/CABI）
追加 `__yhreg`；三个缓冲（`.text`/`.data`/`.bss`）共用同一判据，`em_sym_qualify`
等三处重复判据顺带收敛为 `sym_suffix_needed`。

测试：`tests/yh-run/check.py` 新增 `// asm-symbols-safe` 指令（`--emit-asm`
文本里不得出现寄存器同名符号），用例 `run/182-register-named-symbols.yh`
（函数 `w12`/`x0`/`d8` + 全局变量 `lr`）。

## 四、新发现并修复：const 长度数组在全局/字段/形参/返回位置

```yh
const N int = 3;
let g [N]int;                 // 全局
struct S { a [N]int; }        // 字段
fn f(a [N]int) int { }        // 形参
fn make() [N]int { }          // 返回
```

以上四种位置一律报「编译期常量尚未就绪」，只有函数内局部数组可用。根因是
**子遍顺序**：模块 worker 的顺序是 CT 捕获 → 布局登记 → 布局求值 → 全局
（普通 const 在这里才有值）→ 函数；而 `parse_type_ref` 的延迟布局分支被
`gs.c_pass == 1` 限制，pass2 以后重新解析这些类型时只能现场折叠长度常量，
此时普通 const 还没值。

修法：

1. `comptime/ct_layout.yh` 的 `ct_layout_array`：长度来自**声明在前**的
   未就绪 const 时，把它登记为布局期值请求（`ct_value_request_add`），让布局
   循环先求出该常量；前向引用（声明在后）仍不登记。
2. `parse/parse_ct_layout.yh`：布局值请求的候选从「初始化器含 `$` 调用」扩展到
   「已被登记为值请求」；依赖链上的常量同样登记（`const N int = M + 1;`），
   且只登记声明在 owner 之前的依赖。
3. `parse/parse_type.yh`：延迟判定改为 `p_ct_layout_expr_defer_now`——
   引用未就绪 const 时任何 pass 都延迟；含 `$`/`sizeof` 时仍只在 pass1 延迟
   （CT 正文 pass2 才捕获，而后续 pass 若再延迟会拿回长度仍为 -2 的 pending
   类型项，数组字面量个数检查会误报）。
4. `comptime/ct_layout.yh` 的卡死诊断：先按值请求报告，前向引用恢复
   「编译期常量尚未就绪」（`fail/118` 锁定）。

声明顺序规则保持不变（设计文档
[yh-编译期过程设计](../03-design/yh-编译期过程设计.md) §5/§6）：普通全局 const
仍按声明顺序求值，只有布局请求引用的、声明在前的常量允许在布局子遍提前求值。

## 五、新发现并修复：数组类型编号规范化（清单第 11 项）

延迟布局为长度表达式建立的数组类型项与 `gen.ty_array` 的规范项内容全同、
编号不同；此前只靠 `sem_can_assign` 对 `TY_ARRAY` 做结构化放行。本轮从两处
收敛：

1. **创建期按来源去重**（`ct_layout_array_find`）：同一元素类型 + 同一长度
   来源（同一 const 符号 / 同一长度 token 区间 / 同一已知长度）复用同一
   `type_id`——同一处声明在多个 pass 重复解析不再各建一项；
2. **布局完成后规范化**（`ct_layout_canonicalize`）：把同 (元素, 长度, 大小)
   的重复项归一到最小编号，改写面覆盖类型表（指针/切片/数组的元素）、结构体
   与联合体字段、签名返回与形参、符号类型；之后 `ty_array` 与后续比较都走
   规范编号。结构化兼容判定保留为第二道防线。
