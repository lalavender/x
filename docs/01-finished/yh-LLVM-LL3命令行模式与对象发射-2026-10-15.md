# LLVM LL3 首片：命令行 LLVM 模式与内嵌桥对象发射（2026-10-15）

本记录关闭 LL3 的主体：**yh 命令行可以直接用内嵌静态 LLVM 桥把 yh 源码编译成
x86_64 目标文件并原生运行**。已知遗留一项未定位的损坏输入崩溃，见文末。

## 背景

LL2 已经能：受检前端阶段不产生旧汇编、语义结束生成 `CheckedModule` 快照、
快照降低为 `ir.IRModule`、模块 IR 经 `llvm_module.yh`/`llvm_scalar.yh` 发成 LLVM 文本。
但这些能力只被专项门消费，命令行与项目构建仍全部走旧 ARM64 发射。LL3 把它们接进
`yh` 自身：`--backend llvm --target x86_64-unknown-linux-gnu [-O0|-O2]` 直接产出对象，
不调用任何外部 LLVM 工具，也不回退旧后端。

## 实现

### 1. 内嵌桥的 yh 侧绑定（`compiler/backend/llvm_bridge.yh`）

- 用 `@[extern]` 声明 `yh_llvm_version` 与 `yh_llvm_emit(text, length, triple, opt, kind,
  output_path, diagnostic, capacity)`，与 `compiler/llvm/bridge.h` 一一对应（改动必须同步两处）。
- `llvm_bridge_emit` 做参数校验（opt 只接受 0/2、kind 只接受 0 对象/1 汇编），
  产物由桥内部原子发布（临时文件 + rename），失败不留下部分产物。
- 桥归档在构建宿主时静态链进 `yh` 本身：`tools/llvm-host.py` 生成 `shim/gcc`
  包装器，链接阶段追加桥归档（`--whole-archive`）与固定 SDK 静态库；`make` 的
  `YH_LLVM_HOST=auto` 在宿主已准备时默认链入、未准备时打印诊断并按原路径构建。

### 2. 命令行与驱动（`compiler/cmd/driver.yh`、`compiler/cmd/llvm_emit.yh`）

- `drv_scan_target` 新增 `--backend legacy|llvm`、`-O0`、`-O2`、`--emit-llvm`；
  未知后端或未知 triple 明确拒绝，不静默回退。
- `run_emit_asm_to`（`-o`）在 LLVM 模式下走 `llvm_emit_single_file`：对象先写
  `<out>.yh-tmp.o`，再由宿主 cc 链接为可执行文件；`--emit-asm` 发当前目标的汇编文本到
  标准输出；`--emit-llvm` 只发 LLVM 文本（不调用桥）。
- 单文件受检前端（`mb_llvm_file_begin` + `mb_llvm_semantics`）采用与项目 worker 相同的
  「已索引文件」形态与语义两遍顺序，并在语义遍历前打开 `c_ast_capture`，
  让 arena 活到快照生成之后。

### 3. 项目 worker（`compiler/cmd/module_worker.yh`）

- `c_backend != 0` 时：进入受检前端（`front_checked_begin`，因此不产生任何
  `.text/.data/.bss`），语义结束后 `checked_module_capture`，再
  `ast.lower_module` → `backend.llvm_emit_module` → 桥发布
  `.build/asm/<tag>.o`（`--emit-llvm` 时另写 `.build/llvm/<tag>.ll`）。
- **不**进入旧的 `ast_ir_lower_module` SSA 替换与机器发射路径。
- `cmd/link_cache.yh` 在 LLVM 模式下跳过「汇编 → 目标」步，链接参数直接收
  `.build/asm/<tag>.o`；`cmd/module_build.yh` 新增 `.build/llvm/` 子目录。

### 4. 纯快照 lowering 的两处实质修复（`compiler/ast/checked_module_lower.yh`）

- **顺序语句必须显式收尾基本块**：赋值等简单语句不终结块，序列推进与复合语句
  退出时必须补无条件分支到新块（`checked_lower_continue_block` /
  `checked_lower_exit_block`），否则块保留默认 `unreachable` 终结符，后继语句
  变成死代码、退出块不可达。
- **赋值语句的返回协议**：`checked_lower_assign` 原先在成功时返回 0（"路径终结"），
  导致循环体只降低第一条语句、`has_latch` 恒为 0、循环没有回边。改为返回 1 后，
  `for i < 3 { i += 1; }` 与双语句循环体都能正确产生 header phi 与回边。

### 端到端观察值（单文件 → x86_64 → 原生运行）

- `tests/modules/projects/llvmlower/input/scalar.yh`（`arithmetic(5) + loop(4)`）：
  退出码 **13**，与源码语义一致（`arithmetic(5)=9`、`loop(4)=4`）。
- 探针 A（`for i < 3 { i += 1; }` 后 `return i`）：退出码 **3**。
- 探针 B（`for i < 3 { i += 1; sum += i; }` 后 `return sum*10+i`）：退出码 **63**。
- 生成的 LLVM 文本经 `opt-21 -passes=verify` 校验通过；`main` 的反汇编显示
  真实 `call arithmetic` / `call loop` 与 `add`。

## 顺带修复的编译器缺陷：`iface_ct_load` 悬垂路径（use-after-free）

LL3 期间 `build-check` 的 `ct5b-corrupt-body-signature-rejected` 出现 worker SIGSEGV，
定位结果是一个**在 HEAD 就已存在**的 use-after-free（LL3 改动只改变了堆布局把它暴露出来）：

- 调用方 `cmd/module_worker.yh` 用 `pj_pool_str(mb_dep_ctoff[cti])` 取路径，那是
  **可扩容名字池**里的裸指针；`iface_ct_load` 内部 `parse_source*` 会把隐藏正文名、
  形参名与类型名 intern 进同一个池，`tml_intern_str` 在扩容时 `free` 旧块并换新块，
  调用方指针当场悬垂。
- 解析之后的「正文签名不匹配」诊断读该指针 → 逐字节扫描已释放内存 → SIGSEGV。
  HEAD 之所以只表现为「诊断里路径打空」，是因为 freed 块首字节恰好为 0。
- 修复：`iface_ct_load` 入口把 `path` 快照进本函数栈缓冲，其后
  `read_source`/`header_valid`/诊断一律用快照。因果 A/B：只回退该修复重建，
  ct5b 再次 SIGSEGV；保留修复则正确拒绝并打出真实路径。

## 未关闭的边界

- LLVM 模式未常驻：默认仍是旧 ARM64 发射，`--backend llvm` 需显式给出。
- 首片覆盖边界：全局对象数据、聚合/指针/浮点、间接调用、变参、`switch`/`goto`/`for-in`
  明确拒绝并带来源，不回退。
- 未滚种子；`bin/yh` 与 `bin/yh-linux-arm64` 保持原哈希。
