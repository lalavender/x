# yh 内嵌 lld 链接器可行性实测（2026-10-15）

**状态：**实测完成，结论已写入
[LLVM 替换实施方案 §LL9L](../02-plan/yh-LLVM后端替换实施方案.md)；
未改生产路径、未改 SDK 清单、未滚种子。所有二进制与解包产物在 `tmp/`，未提交。

## 1. 目标

回答「能不能把 lld 库也静态链接进 yh 编译器」，并给出可直接用于方案的证据：
包与版本、库内 API、链接闭包、体积、进程内链接产物的可运行性。

## 2. 结论

**可以。**Ubuntu 与固定 LLVM SDK 同版本的 `liblld-21` 直接提供六个静态归档；
官方库内入口 `lld::lldMain` 支持可重入并带崩溃恢复。实测在同进程内把一个
x86_64 `_start` 对象链接成 `ELF64 ET_EXEC` 并运行，退出码与源码一致；
`readelf -d` 只有系统 `libz/libzstd/libm/libc`，没有 libLLVM/liblld。

环境：WSL Ubuntu（`resolute`，aliyun 镜像，amd64）。下载的两个包缓存于
`tmp/lld-check/`（gitignore），另有 Polly 包用于补全符号：

仓库现有 `tmp/llvm-migration/sdk/linux-x64-capi/` 的 62 个 LLVM 组件归档

## 4. 库内 API（lld 21）

`lld/Common/Driver.h` 提供的嵌入入口：

```cpp
enum Flavor { Invalid, Gnu, MinGW, WinLink, Darwin, Wasm };
using Driver = bool (*)(llvm::ArrayRef<const char *>, llvm::raw_ostream &,
                        llvm::raw_ostream &, bool, bool);
struct Result { int retCode; bool canRunAgain; };
Result lldMain(llvm::ArrayRef<const char *> args, llvm::raw_ostream &stdoutOS,
               llvm::raw_ostream &stderrOS, llvm::ArrayRef<DriverDef> drivers);
#define LLD_HAS_DRIVER(name) /* 声明 lld::<name>::link */
```

关键性质：注释明确 `lldMain` 可重入、支持崩溃恢复，`canRunAgain=false` 时
应结束进程而不是继续复用；单方言也可直接调 `lld::elf::link(...)`。

## 5. 实验

### 5.1 C++ shim

`/tmp/lldtest/lldmain.cpp`（仓库外临时目录，未进仓库；包缓存留在
`tmp/lld-check/`）形如：

```cpp
LLD_HAS_DRIVER(elf)
extern "C" int yh_lld_link(const char **argv, int argc,
                           char *diagnostic, unsigned long capacity) {
    std::string captured;
    llvm::raw_string_ostream errors(captured);
    lld::Result result = lld::lldMain({argv, argv + argc}, llvm::outs(), errors,
                                      {{lld::Gnu, &lld::elf::link}});
    /* 把 captured 有界拷贝进 diagnostic，返回 result.retCode */
}
```

### 5.2 链接

`g++` + `-Wl,--start-group`：
`liblldCommon.a`、`liblldELF.a` + `llvm-21-dev` 全部 226 个组件 +
`LLVMLTO/LLVMOption/LLVMObjCopy/LLVMCoverage` + `libPolly.a/libPollyISL.a`
+ `-lrt -ldl -lm -lz -l:libzstd.so.1 -lxml2 -pthread -static-libstdc++ -static-libgcc`。

### 5.3 产物与运行

- 可执行文件 **141 MB**（`strip --strip-all` 后 **123 MB**）；
- `readelf -d`：`NEEDED` 只有 `libz.so.1`、`libzstd.so.1`、`libm.so.6`、
  `libc.so.6`、`ld-linux-x86-64.so.2`，无 LLVM/lld；
- 用 `-o start start.o` 链接（`start.s` 只含 `_start`：`exit(7)` 系统调用），
  退出 0，产物为 `ELF64 ET_EXEC / Advanced Micro Devices X86-64`，
  执行退出码 **7**。

## 6. 依赖闭包（相对现有 62 个组件）

| 缺口 | 证据 |
| --- | --- |
| `LLVMLTO`、`LLVMOption`、`LLVMObjCopy`、`LLVMCoverage` | `nm -u liblldELF.a`：13 个 `llvm::lto`、11 个 `llvm::opt` 引用 |
| 全部目标后端 | lld 的 LTO/管线引用 `llvm::InitializeAllTargetInfos/Targets/...`，经 `libLLVMSupport.a` 拖出所有 `*Info/Target/CodeGen/AsmParser` |
| Polly | `libLLVMLTO.a(LTOBackend.cpp.o)` 未定义 `getPollyPluginInfo()` |

两个可选路线：

1. **全量发行归档**：实现快，yh 体积约 123–141 MB；
2. **源码构建裁剪**：`LLVM_TARGETS_TO_BUILD=X86;AArch64` + 关 Polly，
   体积与裁剪流程显著变小，但要自建固定 SDK（方案 L9L-1 决策项）。

## 7. 边界与风险

- **必须 C++ shim**：lld 是 C++ API（`ArrayRef`/`raw_ostream`/按值 `Result`），
  不能用 yh 的 `@[extern]`C ABI 直接调用；这一点与 LLVM C API 桥不同。
- **版本稳定性**：lld 的 C++ API 不保证跨版本 ABI；绑定固定 SDK 21.1.8，
  升级必须重编 shim 并重跑门。
- **驱动职责**：lld 只做「对象→可执行」，CRT/libc/动态加载器路径、`--sysroot`、
  `-lc/-lm` 需 yh 自己组装（现在由 gcc 的 collect2 包办）；自举阶段可走
  `-nostdlib` + 自有 `_start`。
- **仍需要 cc 构建编译器**：内嵌 lld 省掉的是「链接用户程序」的依赖，
  构建 yh 本身（种子 + 链接静态库）仍要有 C 工具链。
- **平台**：同一包内含 MachO/COFF 方言，可做 Linux 宿主交叉产 Mach-O/COFF；
  但 macOS arm64 ad-hoc 签名、Windows 导入库/启动不在 lld 内，属 F2/F3。
- 与 yh_link 的关系：内嵌 lld 基本覆盖其目标规划（除签名与「不含 LLVM」），
  进一步支持「asm/ 冻结、link/ 暂停」的既有判断；本记录不改变该结论。
