## 1. PL1e：capture 序列化 = 13.7 ms/函数（原 19.3）

改动两处，都只是去掉重复工作，编码字节不变：

| 改动 | 原来的浪费 |
| --- | --- |
| `ir_module_serialize_alloc`（一次 prepare = verify + plan 后直接分配并写出） | 原 `serialized_size` + `serialize` 会把 **verify 与 plan 各跑两次** |
| `ir_module_serialize_alloc_trusted`（capture 用：跳过 mini 模块的语义 verify，仍做规模检查） | mini 模块是本进程从已验证模块忠实重编号出来的；记录只在整模块 verify+emit 成功后由 `firc_commit` 落盘，坏记录不写盘；即使写盘，装载侧仍会校验 |

同一过程的单机测量（冷编 → 删对象 → 重编，1476 条记录、38.08 MB）：

| 版本 | capture 合计 | 每函数 | 说明 |
| --- | --- | --- | --- |
| PL1c 实验批（2 次 prepare + 2 次 verify） | 28.42 s | 19.3 ms | load 未记录，`real` 约 17.6 s 档 |
| 1 次 prepare + 1 次 verify | 20.21 s | 13.7 ms | `real` 17.67 s |
| + trusted（0 次 verify） | 18.9–21.3 s | 12.8–14.5 ms | load≈7 的两轮 |

成对 A/B（`--ab`，3 对交错，load 20–30）：**capture 累计 −13.2%**（34436 → 39682 ms 侧
比较），方向与单机一致。代码里去掉的是两次全量 verify + 一次全量 plan，所以
**收益上限就是这部分**；剩下的 12–14 ms/函数是迷你模块构造（名字复制 + 查重）+ 写缓冲。

## 2. PL1d：模块 verify 去掉两处 O(n²)，逐函数校验仍在

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| 符号名唯一性 | 两两 `str_eq`：O(n²) 次字符串比较 | 开放寻址哈希（FNV）+ 碰撞时再比字符串：期望 O(n)，语义不变 |
| 「每个定义恰一个实体」 | 每个符号各扫一遍 globals 与 functions：O(n×(G+F)) | 一次计数数组 O(S+G+F)，越界符号显式拒绝 |

实测（同一过程，1461–1476 函数量级）：模块 verify 累计 2.88 s → **2.68 s（−7%）**。
降幅小的原因很明确：**verify 的成本主要不在名字去重，而在逐函数指令校验**
（2.68 s / 1476 ≈ 1.8 ms/函数）。这两处改动对小模块是白赚，对**大模块**才是关键——
PL2 量到「单模块 8× 函数时 verify 每函数成本涨 3.9×」，正是那个 O(n²) 在放大。

## 3. PL1f：命中装载跳过整段语义 verify（merge 段 −8%）

- 记录头从 32 字节扩到 40 字节，新增 payload 的 **FNV-1a 校验和**；格式版本 1 → 2
  （旧记录自动失效重建，不读旧格式）。
- 装载时先校验和，通过后走 `ir_module_deserialize_trusted`：仍解析 + 规模校验 +
  规范编码校验（`ir_module_canonical`），只跳过语义 verify；合并后的整模块在
  lowering 结束时仍会完整 `ir_module_verify`，所以坏记录不会静默通过。
- 损坏记录测试仍然通过（校验和不符 → 当作 miss 重编），`llvm-function-cache.py` 的
  六场景矩阵 O0/O2 全绿。

成对 A/B（3 对，load≈28–38）在单函数改动场景上：`cache 合并` 段 **1195.7 vs 1300.1 ms
（−8.0%）**；墙钟差（−6.5%）小于该负载下单侧抖动（MAD 854–1246 ms），只作方向。

### 3.1 PL1f2：合并查找索引（已完成主体）

merge 原实现对**每条记录**的每个类型都线性扫目标类型表（结构等价比较），每个符号再
线性扫符号表 —— 单函数改动 204 条记录就是 O(记录数 × 模块规模 × 闭包规模)。

现在 `ir_function_cache_merge` 内为当前记录建一次目标模块索引
（`IRMergeIndex`：名字哈希 → 符号、结构键 → 类型；容量 ≥2n 的 2 的幂，开放寻址）：

- 类型键覆盖与 `ir_fc_type_equiv` **完全相同的字段**（名字 + kind/bits/size/align/
  count/abi/variadic + elem + 字段(类型,偏移)），迷你类型的依赖先经 `type_map` 映射再入键；
- 哈希只用来缩小候选，**命中仍用原比较函数确认**，语义不变；键不可算（依赖未映射）
  时自动退化为线性扫描；目标模块规模 ≤64 时索引关闭。

成对 A/B（3 对交错，load 6.8–12.6）：单函数改动场景 `cache 合并` 段 **940.1 vs 1029.3 ms
（−8.7%）**；该场景墙钟抖动 ±11%（MAD 126–200 ms），不作结论。

PL1f3（同日追加）：`ir_module_add_symbol` / `ir_module_add_type` 每次 add 都对整张表做
**线性查重**（`for i < unit.symbol_count`），合并 204 条记录时被放大一次。现在新增
`ir_module_append_symbol` / `ir_module_append_type`（**调用方保证不存在同名/等价项时**
直接追加），merge 在索引确认「未命中」后改走它们，把每次 add 从 O(S)/O(T) 降到 O(1)。

> **收益未能在本轮验证**：复测时 load1 ≈16（其它 worktree 在持续构建），A/B 单侧抖动
> 13–26%，`cache 合并` 段读数 1020.8 vs 888.6 ms 落在噪声里，**不作为改善证据**；
> 代码层面的依据是「去掉一次 O(S) 扫描」。若后续在安静机器上确认无收益，回退这两个
> `append_*` API 即可（调用点只有 merge 两处）。正确性由缓存矩阵与门禁覆盖。

## 3.2 PL1d2 首片：去掉每模块第二次全量 verify（已完成）

一次性实验（临时允许 `ir → gen` 计时，量完回退）测到：一次冷编里
`ir_module_verify_function` 累计 **5.33 s**，而 lowering 侧的 `time_lower_verify_ns`
只记 **2.72 s** —— 差额说明**每个模块被完整 verify 了两次**。查调用点定位到：

1. `lower/module_snapshot_lower.yh`（提交前，必须保留）；
2. `backend/llvm_module.yh::llvm_emit_module`（发射前的防御性重复）。

其中函数体 SSA 校验（`ir_verify`）占 `verify_function` 的 **83%**（2.97 ms/函数），
「其余」（type_map / loc / 参数签名）只占 17%。

改动：后端不再跑完整 `ir_module_verify`，改为新增的廉价谓词 `ir.ir_module_sealed`
（只查非空 + 版本），语义校验仍由生产者（lowering / `ir_module_deserialize`）负责，
发射前的 `llvm_target_same` / `llvm_preflight` 继续拒绝结构不完整的模块。

成对 A/B（3 对，load 3.5→11.5）：

| 场景 | 改动后 | 改动前 | 变化 |
| --- | --- | --- | --- |
| 冷编墙钟 | 12382.5 | 13854.3 | **−10.6%** |
| 单函数改动墙钟 | 3882.5 | 4477.8 | **−13.3%** |
| 冷编 worker 累计 | 26685.5 | 31976.7 | **−16.5%** |
| 冷编 lowering 侧 verify | 3418.8 | 3514.4 | −2.7%（这一侧未动，符合预期） |

**PL1d2b 结论：没有便宜的优化空间（两项改造实测无收益，已回退）**。
`ir_verify` 内部有两处「逐指令/逐 use 线性扫描」——`ir_find_value_type`（值→类型）与
`ir_find_value_position`（值→(块,指令)）——理论上把校验从 O(n²) 降到 O(n)。实现并接入
「值→类型表」与「位置表」后实测 verify 占 lowering 的 **17.2% → 17.0%**（绝对值下降
来自机器变安静），**无可测收益**：真实函数只有 100–500 条指令，扫描量 <2%，verify 的
时间花在真正的逐指令类型/操作数校验与支配性定点计算上。按「不做无收益的投机优化」
回退了两张表（`compiler/ir/ssa.yh`、`ssa_call.yh` 恢复原状）。

**因此 PL1d2b 只剩两条路**：① 换算法（支配性用 Cooper-Harvey-Kennedy 增量求解、
或用 bitset 减少定点轮数）；② 论证「发布构建关闭模块 verify」的替代门。两者都不是
本轮能安全落地的改动。

**原（PL1d2b）问题陈述**：`ir_verify` 本身（2.97 ms/函数）。优化它要么改 SSA 校验器内部
（需要再一次内部分解），要么论证「发布构建关闭」的替代门——目前模块 verify 是
lowering 之后唯一的语义兜底，不能只为性能关掉。

## 3.3 PC2c 重新定性：名字字节只占 0.7%，体积在「类型表」

对 PC2c（原假设：每条记录带一份字符串副本导致 `.fchk`/`.fir` 偏大）做了纯计数探针
（不涉及时钟，量完回退），一次全量重编（1493 条记录）：

| 指标 | 数值 |
| --- | --- |
| 每条记录 payload | **25.1 KB**（中位 18 KB、最大 287 KB） |
| 其中名字字节 | **0.2 KB（0.7%）** |
| 每条记录符号数 / 类型数 | **7.6 / 75.0** |
| capture 吞吐 | 1.91 MB/s |

结论：**PC2c 的前提不成立** —— 字符串副本不是体积来源；真正占体积的是**每条记录
平均携带 75 个类型条目**（函数闭包里的类型全部内嵌）。因此优化方向应改为
**按模块共享类型表**（记录只引用模块级类型池 + 池版本/校验），而不是共享字符串池。
按当前 25.1 KB/record 估算，若记录降到 ~5 KB，capture 有望从 13.4 ms/记录降到
5–6 ms/记录（全量重编 capture 累计 20 s → 8–9 s）。这是格式 v3 级改动，已作为
**PC2d** 立项。

## 4. PL3：内存口径从 `ps` RSS 换成 footprint / VmHWM

`tools/perf-baseline.py` 新增 `--mem {footprint,rss}`（`--rss` 保留为旧名）：

| 平台 | 取值 | 与 RSS 的差别 |
| --- | --- | --- |
| Darwin | `proc_pid_rusage(RUSAGE_INFO_V4).ri_phys_footprint` | 内核记账的物理足迹：含 dirty/压缩页，**不重复计入共享的干净文件页** |
| Linux | `/proc/<pid>/status` 的 `VmHWM` | 进程自身**高水位**，采样间隔不会低估（进程退出后不可见） |
| 兜底 | `ps -axo rss`（旧口径） | 保留作对照 |

实测（本机，`--mem footprint`，1 轮）：冷编进程树 **418.8 MB**、热编 **230.1 MB**；
同一进程上 footprint 12.5 MB vs RSS 24.4 MB，说明旧口径把共享页算进了约一半。
仍是采样：Darwin 的 footprint 是当前值（短峰可能漏），Linux 的 VmHWM 不会低估但
进程两拍之间退出的看不到；**cgroup v2 `memory.peak` 未接**（需要可写的 cgroup 层级）。
