# 模块模式枚举成员：根因定位到「成员符号在第二次解析不可见」

日期：2026-10-07。状态：已完成（诊断改进 + 根因定位；完整支持仍待办）。

## 本轮定位过程（三次插桩，逐步夹逼）

第 25 轮只知道「模块模式编译期正文里 `Level.mid` 报『.』的左侧不是结构体」，
两条分支条件放宽都无效。本轮改用插桩，一步步把根因逼出来。

### 一、报错分支分档

在 `sem_expr.yh` 的 `sem_member` 失败分支按「基类型 × 阶段」分档：

```
extra.yh:43:21: 错误: DBG member-fail: prepare + base TY_ENUM
```

→ 基底**求值成功**且类型是 `TY_ENUM`：说明枚举类型名走了**值路径**，然后 `.mid` 落到
字段访问。不是解析器没认出枚举，而是**基底被当值求值了**。

### 二、基名符号状态分档

在 `parse_expr.yh` 的 `parse_ident_primary`（唯一基名解析点）按符号状态分档，同一行
`43:12` 在一次编译里出现**两次**：

```
extra.yh:43:12: DBG ident-dot: base has no symbol     ← 第一次解析，符号不存在
extra.yh:43:12: DBG ident-dot: base symbol is CONST   ← 第二次解析，符号是常量
```

→ 第一次解析时枚举成员分支**命中**（此前看到的 `MATCH`），第二次解析时 `Level` 成了
`SYM_CONST` 符号，被 `sym_lookup(...) < 0` 挡住 → 走值路径 → 报字段错误。
**同一段正文被解析了两次**，这是模块 worker 的行为。

### 三、修法与它的失败

据此在 `parse_expr.yh` 加第二形态判据（基名是 `SYM_CONST` 且其 `type_id` 是 `TY_ENUM`）
—— 实测**仍失败**，说明该常量符号的 `type_id` 不是枚举类型。

改在 `sem_member` 里兜底（基底类型是 `TY_ENUM` 时按成员名查符号表）—— 报出
`DBG enum-base: member symbol not found`：**第二次解析时枚举成员符号 `mid` 在名字表里
查不到**（放宽 `type_id` 校验、保留 `F_ENUM_MEMBER` 都无济于事）。

→ 最终根因：模块 worker 第二次解析 CT 正文时，**枚举成员符号不可见**。
`parse_expr` 的标识符分支救不了它（那时基名已是有符号的常量），`sem_member` 兜底也救不了
（成员符号查不到）。要真正支持，得让第二次解析带上枚举成员符号，或让枚举类型项自带成员表
（当前 `ty_push(TY_ENUM, ...)` 不存成员）。

## 本轮交付

1. **准确可操作的诊断**（替代误导性的「『.』的左侧不是结构体或结构体指针」）；
   `sem_member` 新增枚举基底分支：

   - 模块模式（`c_module_mode != 0`）：
     「模块模式下编译期正文里直接引用枚举成员暂不支持；请在同模块顶层用
     `pub const X int = 枚举名.成员;` 中转后再引用」
   - 非模块模式：「枚举没有这个成员」

2. 新增 `tests/yh-run/fail/149-enum-value-member-access.yh`：枚举值上访问不存在的成员，
   锁定新增分支（此前报「左侧不是结构体」，语义变化后由该用例覆盖）。

3. `parse_expr.yh` 保持第 22 轮的单形态实现（第二形态判据无收益，不留）。

## 现在能用的写法

模块模式下用顶层常量中转（`comptimecross` 已锁定）：

```yh
pub const MID int = Level.mid;      // 顶层：可用（延迟判别值也已回填）
@[comptime] pub fn mid_ct() int {   // 正文读常量，别直接写 Level.mid
    return MID;
}
```
