# yh 全量门测试并行化（2026-10-15）

只改测试 harness（Python），不动编译器源码，因此**不需要重编与滚种子**。

## 为什么慢（改造前的实测）

宿主：WSL2 Ubuntu / x86_64 / 12 核 / 3.5GB 内存；仓库在 `/mnt/c`（9p）；
`yh` 是 aarch64 ELF，经 qemu-user 执行。

全量门 = `make test` + `make selfhost-native`，实测约 26 分钟。逐阶段计时：

| 阶段 | 耗时 | 规模 |
|---|---|---|
| L1 `tests/yh/check.py`（ANTLR，单进程内） | 5.5s | 120 文件 |
| L2 `tests/yh/check.py --compiler` | 69.0s | 120 文件（**每文件一次 yh 进程**） |
| L3 `tests/yh-run/check.py` | 338.1s | 308 用例（每用例编译+运行） |
| `tests/modules/check.py` | 11.9s | 18 文件 |
| `tests/modules/build-check.py` | 449.5s | 100 项断言 / 74 次 yh 调用 |
| `tests/selfhost/native-selfhost.py` | 600s | 3 代冷编 + 自解析 86 文件 + **又跑一遍 L2/L3** |
| 其余 6 个 selfhost 探针 | 97.9s | — |

根因是**进程启动成本 × 调用次数 × 全串行**，不是编译算力不足：

- 单次 `yh --syntax-check`（120 行以内文件）实测 0.52–0.67s；`yh version`
  0.35s（ext4）/0.66s（9p）；而小型 aarch64 静态程序在 qemu 下只要 22ms。
  即每次调用约 0.4s 是 yh 自身启动/初始化被 qemu 放大的 CPU。
- 同一批 120 个文件：L1 在**一个进程内**跑完 5.5s，L2 每文件起进程 69.0s →
  **12.5×**，差异全部来自进程启动。
- 单用例 1.10s ≈ yh 启动 0.5s + gcc 汇编/链接 0.25s + 运行 0.03s。
- 12 个核基本闲置：改造前整套门只有 `scratch-isolation.py` 用 8 个并发。

## 改动

四个 harness 都新增 `--jobs N`，缺省即并发，`--jobs 1` 恢复串行：

- `tests/yh/check.py`（`--compiler` 模式）：正例/反例合并成一个任务列表，
  线程池跑 `--syntax-check`，**结果按原顺序**（正例后反例）打印；缺省
  `min(8, CPU 核数)`。ANTLR 模式本来就在单进程内解析，不受影响。
- `tests/yh-run/check.py`：用例产物路径由 `<workdir>/<用例>` 改为
  `<workdir>/<run|fail|pass>/<用例>`（每用例独占路径，并发不互相覆盖）；
  `check_run_case`/`check_fail_case`/`check_pass_case` 改为接收调用方给的
  产物路径，删除了因此失效的 `stem_linux()`；缺省 `min(8, CPU 核数)`。
- `tests/modules/check.py`：accept/reject 两个目录内部并发，结果按原顺序打印；
  缺省 `min(8, CPU 核数)`。
- `tests/modules/build-check.py`：用例循环体抽成 `run_case(c)`，每用例的断言
  先收集、再由 `main` 按 `CASES` 顺序逐行打印（输出与串行逐行一致）；
  每个用例独占 `tmp/modcheck/<fixture>--<用例>` 目录——原先是**同一 fixture 的
  用例共用** `tmp/modcheck/<fixture>`，无法并发；缺省 `min(4, CPU 核数)`，
  因为每个用例本身就是若干次完整项目构建（每次还会 fork 4 个模块 worker）。

未改 `selfhost/*.py` 探针与 `Makefile`：`native-selfhost.py` 调用的两个语料
harness 走缺省并行，已经跟着变快。

## 验收（同一编译器二进制内串行/并行对照）

| 门 | 串行 | 并行 | 倍率 | 结果一致性 |
|---|---|---|---|---|
| `tests/yh/check.py --compiler`（120 文件） | 84.4s | **15.1s**（-j8） | 5.6× | 输出一致（正例 78/78、反例 42/42） |
| `tests/yh-run/check.py`（309 用例） | 302.5s | **60.9s**（-j8） | 5.0× | 输出一致（309/309） |
| `tests/modules/check.py`（18 文件） | — | — | — | 输出一致（18/18） |
| `tests/modules/build-check.py`（100 项） | 560.5s | **274.7s**（-j4）/ 258.8s（-j8） | 2.0× / 2.2× | 输出**逐行相同**（100/100） |

- 一致性判据：`diff <(串行输出) <(并行输出)` 为空（仅归一化附加的
  「并发 N」字样）。
- 复现命令（WSL，仓库根）：`export PATH="$PWD/tmp/boot/crossbin:$PATH"`、
  `SEED=bin/yh-linux-arm64`、`YH_LINK=/nonexistent`，然后
  `python3 tests/yh/check.py --compiler --compiler-path "$PWD/yh" --jobs 1|8`。
- 表中「串行 84.4s / 302.5s」与上文「69.0s / 338.1s」不是同一次测量：期间
  另一会话重建过 `./yh`（LLVM 切片），跨行数字不可比，**同一行的串并行配对
  才是倍率依据**。

## 边界与未做

- 并发后失败诊断仍按原顺序打印，但 `build-check.py` 的 `OK` 行改为全部用例
  跑完后一次性输出（串行时是边跑边输出），这是为可比对性做的取舍。
- 本机 3.5GB 内存 + 9p 下，8 路并发自举探针（`scratch-isolation.py`）出现过
  「读取编译器自身失败」；因此 `build-check.py` 缺省上限取 4。实测该门
  -j4 274.7s、-j8 258.8s（只快 6%，CPU 占用却高得多），故缺省保持 4；
  内存更小的机器应显式下调 `--jobs`。
- 仍未做（已记 `docs/todo.md`）：工作目录/编译器二进制移到 ext4/tmpfs
  （实测单次调用 665ms→464ms，整用例 −25%）；`selfhost-native` 内部与
  `make test` 重复的那遍语料；编译器模块 worker 上限（硬编码 4）；批量
  `--syntax-check`；门禁分层。
