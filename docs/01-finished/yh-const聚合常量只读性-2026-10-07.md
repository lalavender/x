# const 聚合常量只读性

日期：2026-10-07。状态：已完成。补第 32/33 轮放宽 `const` 聚合时留下的缺口。

## 问题（先实测确认，不靠推理）

第 32 轮把聚合类型的 `SYM_CONST` 在取值路径降级为变量语义（否则会把 `cval = 0` 当地址用、
运行期段错误）之后，**写入路径也就不再有拦截** —— 聚合数据发在可写数据段，于是下面这段
不但编译通过，还真的改了值：

```yh
pub struct P { x int; }
const P0 P = P{ x: 5 };
fn main() int {
    P0.x = 6;        // 之前：编译通过且写入生效
    return P0.x - 6; // → 0
}
```

对照：**标量** `const` 本来就被拦（`C = 6;` 报「赋值目标必须是可寻址的表达式」——const 不是地址，
所以走不到赋值）。也就是说聚合与标量两种 const 的只读语义此前不一致。

## 改动（一处，5 行）

`compiler/gen/sem_value.yh` 的 `sem_ident_val`，在聚合 `SYM_CONST` 的降级分支里加左值上下文检查：

```yh
if (ck == TY_STRUCT || ck == TY_ARRAY || ck == TY_SLICE || ck == TY_UNION) {
    // 聚合常量只读：左值上下文（赋值目标、取地址）直接拒绝 —— 降级为变量语义
    // 只是为了按符号地址读取，不能连可写性一起放开。
    if (g_state.c_lvalue != 0) {
        return sem_err("不能给 const 聚合常量赋值或取地址");
    }
    kind = SYM_VAR;
}
```

放在降级**之前**是有意的：`c_lvalue` 只表示「当前处于左值上下文」，取值路径的两个消费者
（`sem_stash_lvalue`、写回）都在其之后，不必改别处。取地址（`&P0`）同样被拒，符合 const 语义。

## 仍缺（承接 `fail/148`）

顶层聚合**实参**（`$take(Point{ x: 1 })`）仍需「在调度阶段为顶层调用建帧再解析聚合实参」，
本轮读代码确认：顶层调用走 `comptime.ct_call(sym, &args[0], arg_n, res)`，实参在此之前已被
前端求值成 `Res`；而聚合实参的求值需要 CT 帧（`comptime` 侧无法反向调用 parse 侧的
`parse_expr`），所以这不是一处小改。相关分析已写在[收尾方案](02-plan/yh-编译期收尾方案.md)。
