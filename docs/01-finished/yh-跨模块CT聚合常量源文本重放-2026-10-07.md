# `.s.ct` 携带聚合常量源文本（并暴露真正的阻塞点）

日期：2026-10-07。状态：**部分交付** —— sidecar 传输打通，CT 执行仍缺「全局聚合常量的值」。

## 探针先行

先扫「编译期错误写法的诊断质量」，四个探针的诊断**都清晰**，没有可修的：

| 探针 | 诊断 |
| --- | --- |
| 编译期除零 | `编译期除数不能为零` |
| 编译期下标越界 | `编译期数组/切片下标越界` |
| 传运行期变量给 CT 函数 | `变量不是编译期常量` |
| 编译期递归过深 | `编译期函数调用深度超过 64 层` |

于是转向第 47 轮实测定位的那条：`.s.ct` 闭包携带**聚合常量**。

## 已交付：`const_expr_kind = 4`（聚合常量初始化式源文本）

`compiler/parse/parse_global_init.yh`：结构体与数组两个分支在标记 `const_ready = 1` 时，用
`record_aggregate_const_src(idx, first, after)` 记下**初始化式的源文本**（首尾 token 的
`start/len` 求范围后 intern 进名字池）。`compiler/parse/iface_ct.yh` 的 `iface_ct_emit_const`
新增 `agg_src` 分支：类型是 `TY_ARRAY`/`TY_STRUCT` 且 kind 为 4 时，把源文本原样重放进 `.s.ct`，
由导入侧按模块模式重新解析（私有聚合常量第 47 轮已放行，所以导入侧能接受）。

**这一步是通的** —— 跨模块后不再报「跨模块 CT 正文引用了不支持的模块常量类型」。

## 但真正的阻塞点暴露出来了

打通传输后，导入侧 CT **执行**时报：

```
错误: 内部错误：编译期定长数组源值无效
```

根因与第 46 轮**同一处**：全局聚合常量的 `cval` 是**数据段标签**，不是 `CtAggregate` 对象指针
—— 数据在**发射阶段**才写出，而 CT 执行在**语义分析阶段**，那时编译期根本没有这些元素值。
所以 `.s.ct` 能不能重放源文本**不是**关键，关键是要让全局聚合常量在编译期有值。

本轮把这条也改成明确诊断（`ct_ir_place.yh` 的 `ct_ir_array_clone_mode`）：

```yh
if (source == 0 || source.count < 0 || source.count > 100000) {
    gen.sem_err("编译期不支持使用全局聚合常量（其存储尚未在编译期建模）");
    return 0;
}
```

## 结论与下一步

第 46、48 两轮从两个不同入口（单文件下标、跨模块闭包）撞到**同一个根因**：
**全局聚合常量在编译期没有值**。要真正解决，必须在**语义阶段**把它的元素值建模成
`CtAggregate`（局部聚合常量已经这么做）。这已作为独立条目记入 todo，是本方向唯一剩下的实质工作。
