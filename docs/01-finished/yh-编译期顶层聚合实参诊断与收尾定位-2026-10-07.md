# 编译期顶层聚合实参诊断改进与 CT1/CT2 收尾定位

日期：2026-10-07。状态：已完成（诊断改进 + 方案落盘；本轮无行为扩展）。

## 一、顶层聚合实参：把走不通的出路换成真话

旧诊断（`compiler/parse/parse_expr.yh`）说：

> 编译期调用实参里的聚合值需要在编译期函数体内构造（顶层实参必须是编译期常量）

问题在于「顶层实参必须是编译期常量」这句给了**走不通**的出路 —— 实测顶层聚合常量本身也
不支持：

```
$ cat tmp/t30.yh     # const P Point = Point{ x: 1 }; const R int = $take(P);
tmp/t30.yh:13:17: 错误: const 不支持聚合类型
```

即用户按诊断提示改也改不通，且没有任何中转写法。本轮把诊断改成：

> 编译期调用实参里的聚合值只能在 @[comptime] 函数体内构造：顶层实参缺少捕获通道，
> 聚合字面量无法在 pass1 折叠成常量，`const` 也尚不支持聚合类型（没有中转写法）

同步更新 `tests/yh-run/fail/148-comptime-top-aggregate-arg.yh` 的 `fail:` / `fail-contains:`
注释与用例说明。单文件复跑确认输出与新诊断一致。

## 二、CT1/CT2 收尾：定位到具体代码，写成可执行方案

实测记录了两条入口的同构结构：单文件 `compiler/cmd/compile.yh`（27–42 捕获编译期函数正文、
45 登记延迟区间、**47–71 固定点循环**、72 `ct_layout_resolve`、76 `ct_enum_pending_run`）与
模块 `compiler/cmd/module_worker.yh`（15/55/157/159 同一套）。**「逐轮重解析」就是 47–71 的
固定点循环** —— 每轮把 `ct_layout_*` 登记的全部表达式重解析一遍，第 26 轮夹逼出的「同一段
正文被解析两次」正是它的副作用。

据此写了 `docs/02-plan/yh-编译期收尾方案.md`，把剩余工作拆成互相独立的两件（去重解析、
统一入口），并定下第一步是**先插桩量化每轮白跑占比**再改，而不是直接动循环控制流 —— 验收标准是
语料输出与两代自编产物逐字节不变。同时在方案里记录了 `gen/state.yh:150` 的 `c_arg_agg` 是
预留字段（全仓只有分配与空指针检查），不能当作现成的聚合实参通道。

`docs/todo.md` 的两条相关条目已按上述结论改写。
