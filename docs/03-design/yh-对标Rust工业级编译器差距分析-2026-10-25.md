# yh 对标 Rust 级工业编译器：差距分析

日期：2026-10-25
性质：**以代码为准的差距分析**，不改代码、不改种子、不滚种子。
方法：实测 `compiler/`（13 模块 / 118 个 `.yh` / 约 5.2 万行）、`libs/`、`tests/`，
对照 Rust 编译器的能力面，逐项判断"是工程缺口、设计取舍，还是生态缺口"。
既有事实基线见[当前架构重新分析](yh-当前架构重新分析-2026-10-25.md)与
[代码复核](yh-代码复核-2026-10-24.md)；本文不重复其数字，只做对标判断。

---

## 0. 判定口径

"工业级编译器"不是"能编出正确代码"，而是六根支柱同时成立：

| 支柱 | 含义 | Rust 的对应物 |
|---|---|---|
| 前端工程 | 错误恢复、多条诊断、源码渲染、suggestion、错误码、结构化输出 | `rustc_errors`、`--error-format=json`、`error[E0382]`、`--fix` |
| 语义深度 | 独立检查阶段、类型推断、流敏感分析、穷尽性、安全边界 | HIR→THIR、borrowck、MIR、`match` 穷尽性、`unsafe` |
| 中端与分析 | 通用数据流框架、use-def、支配、别名分析，支撑诊断与优化 | MIR、`rustc_mir_dataflow`、`Polonius` |
| 增量与构建 | 查询系统、依赖图失效、对象级增量、LTO/PGO、并行前端 | salsa、`-Z incremental`、ThinLTO、PGO |
| 工具链与生态 | 包管理、LSP、格式化、lint、文档、调试信息、覆盖率、UB 检测 | cargo、rust-analyzer、rustfmt、clippy、rustdoc、DWARF、Miri |
| 治理与可信 | 稳定性承诺、edition、RFC、回归矩阵、可复现构建、供应链 | edition、stability attrs、crater、mrustc、reproducible builds |

yh 目前在第 4 支柱（增量）和第 6 支柱（自举/门禁）上**明显超出玩具编译器**，
在第 1、2、5 支柱上**差距最大**，第 3 支柱是"够用但不可扩展"。

## 1. 现状基线（编译器阶段视角）

| 阶段 | 现状 | 评价 |
|---|---|---|
| 词法 | 手写 lexer + layout（隐式语句终结）+ 插值词法 | 完整 |
| 语法 | 手写递归下降 + 两遍声明扫描 | 完整，**无错误恢复**（首错即停）、无嵌套深度上限 |
| 语义 | 散在 `parse/` 两遍扫描与 `gen/sem_*` 单遍检查 | **没有独立检查阶段**，边解析边检查 |
| IR | 自有 typed SSA（CFG/phi/支配校验/序列化/函数级缓存） | 作为"传递"完整，作为"分析平台"缺失 |
| 优化 | 直通 LLVM，O0 默认、`-O2` 显式；自有 `ssa_inline`/`ir_simplify` 已删除（无调用点） | 取舍合理（Rust 同样外包给 LLVM） |
| 后端 | LLVM 文本 → 固定闭包（内嵌 lld）；4 个 triple × 2 平台 | 强；缺 DWARF、缺 x64 原生门 |
| 增量 | 函数级 check/IR 缓存 + 链接缓存 + 进程池（fork，并发 4） | 强；缺对象级与查询图 |
| 工具链 | `yh test`、`--emit-llvm`、`--stats`、`--syntax-check`、yh-explorer | 有骨架；缺 LSP/fmt/lint/doc |
| 运行时 | 无 GC、无异常、无 panic、无线程；除零定义为 0，越界无检查 | 语义明确但默认不安全；缺并发与 UB 检测 |
| 治理 | 固定点自举、803+ 语料、arch-check、ADR 19 篇、Gitea CI | 强；缺稳定性承诺与可信重建 |

## 2. 差距逐项

### 2.1 前端诊断：最大的单点差距（P0）

现状证据：

- 诊断格式只有 `路径:行:列: 错误: 消息`，单条 2KB 栈缓冲拼装
  （[gen/buffer.yh:209](../../compiler/gen/buffer.yh#L209)）。**无源码行、无 caret、
  无次级 span、无 label、无 note/help、无错误码、无 JSON 输出。**
- **一次只报一条**：`parse_source_fns` 首错 `return -1`
  （[parse/parse_decl.yh:449](../../compiler/parse/parse_decl.yh#L449)），
  `mb_llvm_semantics` 每个阶段遇 `c_errors > 0` 立即返回
  （[build/llvm_emit.yh:95](../../compiler/build/llvm_emit.yh#L95)）。
- **警告体系几乎不存在**：全仓 `warn_lc` 仅 1 个调用点
  （[comptime/ct_diag.yh:98](../../compiler/comptime/ct_diag.yh#L98)）；无 lint 框架、
  无 `-W` 分级、无 `@[allow]`。
- **无 ICE 协议**：内部错误走 `gen.fail` 直接写 stderr，不带版本/目标/源码位置/
  复现提示（[gen/buffer.yh:315](../../compiler/gen/buffer.yh#L315)）。

这带来的连锁后果：编译器"能用"，但用户拿到的第一条错误可能不是根因；LSP 拿不到
结构化数据；CI 无法按错误码统计；教学与排障成本高。

工业级最小集（每项都有可验收的判据）：

1. `Diagnostic` 数据模型（level/code/spans/labels/children/suggestion）。
2. 源码渲染器（行号、caret、多行 span、tab 与 UTF-8 列映射）。
3. 错误恢复：parser 的同步集 + 检查器的错误类型占位，**一次编译报出全部独立错误**。
4. `--message-format=json`（LSP/CI 消费）。
5. 错误码 + 索引文档；ICE 自动附带环境信息。
6. warning/lint 框架（默认集、`-W/-A`、作用域属性）。

> 这是"不改语言设计、收益最大"的一块。按投入产出比应排在第一位。

### 2.2 语义分析：没有独立阶段，也没有流分析（P0）

- `check/` 模块（958 行）是**内部一致性校验**（AST arena 边界、CheckedModule 完整性），
  **不是用户级类型检查**（[check/verify.yh:1](../../compiler/check/verify.yh)）。
- 用户类型检查耦合在解析器里：两遍声明处理 → 单遍函数体检查 → 就地报错 → 中止。
  这是 TCC 血统的遗留，也是"一次一条错误"的根因。
- 无类型推断：`let` **必须显式标注类型**
  （[docs/yh.g4:172](../yh.g4#L172)，"不允许省略类型"）。
- 无流敏感分析：无未初始化使用检查（局部零初始化兜底）、无死代码/可达性诊断、
  **无 enum `switch` 穷尽性检查**、无空指针/边界/别名分析。
- 无 `unsafe` 概念：`@[extern]` 是 FFI，但语言无法在类型层面区分安全与不安全代码。
- 无可扩展的类型系统：无泛型、无 trait、无方法（仅内建 `.to_type`）、无闭包捕获、
  无 `match` 解构、无运算符重载、无 const generics。
- 可见性只有 `pub`/私有，且 **struct 字段一律公开**（
  [00-语义边界 §3](00-语义边界-0.0.1.md)），无 `pub(crate)` 粒度。

对标的两个不同性质：

| 差距 | 性质 | 判断 |
|---|---|---|
| 独立类型检查阶段 | **工程缺口** | 必须补。它同时是错误恢复、增量粒度、LSP 的上限 |
| 穷尽性/未初始化/溢出/边界检查 | **工程缺口** | 极简语言也应给"安全默认"，否则 UB 是默认语义 |
| 泛型/trait/所有权/生命周期 | **设计取舍** | 不要为"对标 Rust"而加；但要认清代价（见 2.3） |

### 2.3 语言设计的代价已经体现在标准库（设计取舍，但需记账）

无泛型的直接后果，在 `libs/` 里已可实测：

- **标准库没有任何通用容器**：无 `Map`/`Vec`/`List`（全仓 grep 仅见业务结构体）。
  TOML 自带池分配、`cli` 自带池、JSON 预留哈希索引 —— 每个消费者重复造数据结构。
- 无 trait ⇒ 无统一 `Allocator`（M5 列为可选）、无统一 `Error`/`Result`（
  [libs/cli/cli.yh:294](../../libs/cli/cli.yh#L294) 自定义 `Result`）、无迭代器抽象。
- 无所有权 ⇒ 切片悬垂、重复释放、漏释放都是**文档化 UB**
  （[00-语义边界 §6](00-语义边界-0.0.1.md)），只能靠人。
- 无 RAII/`defer` ⇒ 错误路径的释放靠手写 goto/返回前清理，样板随规模线性增长。

这是 yh 的定位选择（极简、无 GC、Zig 式），不是缺陷。但"工业级"意味着这些代价
最终会以**库的重复实现、用户 bug 密度、生态无法复用**的形式付账。建议把这条明确
记账（ADR 或设计文档），而不是在宣传"对标 Rust"时隐含承诺泛型。

若将来要补，最小可行路线是 **类型参数 + 单态化**（不带 trait bound），因为
`.s.i` 接口契约与函数级缓存已有版本键，单态化实例的命名与缓存可以复用现有机制。

### 2.4 中端：有验证器，没有分析框架（P1）

`ir/` 4,230 行里只有：模型、`ir_verify`（唯一定义、支配、phi 前驱、类型合法）、
序列化、函数级缓存/重绑定。**没有** liveness、use-def 链、别名分析、通用数据流框架；
可达性只在 verifier 内部用一次性数组临时实现
（[ir/ssa_module_20_verify.yh:256](../../compiler/ir/ssa_module_20_verify.yh#L256)）。

Rust 的差距不在"优化 pass 数量"（它同样把优化交给 LLVM），而在 **MIR 这一层承担了
诊断与安全语义**：借用检查、drop 插入、const prop、穷尽性、unreachable 检测。
yh 若只把 IR 当"传递格式"，就永远无法在 IR 上做安全检查、精确增量失效、
或 LSP 的语义查询。

判断：短期不需要 Rust 级 MIR；但**"统一的分析接口"应当作为增量与诊断的前置**
（例如：可靠的 use-def、支配树复用、函数摘要），否则后续每项都要重写遍历。

### 2.5 后端：缺调试信息与运行时语义（P0）

- **无 DWARF**：全仓无 `DICompileUnit`/`dwarf` 字样 ⇒ 无法在 gdb/lldb 单步、
  无源码级栈、无变量查看。这是 IDE 调试（VS-U3/DAP）的硬前提，也是崩溃定位的基础。
- 无 panic/unwind：运行时错误没有统一语义 —— 除零定义为 0
  （[backend/llvm_scalar.yh:199](../../compiler/backend/llvm_scalar.yh#L199)），
  越界是文档化 UB，只有 `exit` 兜底。
- 无线程/async：`libs` 无 thread/async（J4 线程、并发 HTTP 均后置）。
- 无 sanitizer / Miri 类 UB 检测：自己 malloc/free，无 ASan/valgrind 集成；
  `comptime` 是受限子集解释器，无 UB 检测。
- 无 LTO/PGO：多模块 `.o` 链接，无跨模块内联；发布配置无 ThinLTO。

除零、越界这类语义分歧都已"明确"，但**默认不安全**：语言没有提供任何开启检查的
开关，也没有 `unchecked` 之类的显式标注，安全与否只能靠读文档。

### 2.6 增量与构建：已到函数级，缺依赖图与对象级（P1）

现状：函数级 check/IR 缓存（键含源码/受检事实/编译器/目标/优化级）、链接缓存、
模块快照、fork 进程池并发 4。这在新语言里属于上游水平。

缺：

- **对象级增量未落地**（todo R4 明确）；改一个头/接口仍可能整模块重编。
- **无 query 依赖图**（salsa 式）：失效靠手写键，粒度与正确性都靠人维护。
- 无编译时间预算门禁（PF0/PF1 待实施），性能无回归保护。
- 无 LTO、无 PGO、无远程/共享缓存。
- 测试构建"每次整模块重编"（todo YT2d-2）说明缓存键还有覆盖盲区。

### 2.7 构建系统与包管理：生态的封口（P1）

`project.toml` 支持模块、`[link]`、`[c]`、`yh_libs`，但**无**：

- 版本约束、锁文件、registry、feature、workspace、profile、patch/vendor
- 依赖解析与 semver 检查、`publish`、文档托管
- 标准库随 Release 分发（T5.2 仍待定，当前靠 `make install`）

对"单仓库自举"够用；对"第三方生态"直接封死。Rust 的工业级有一半是 cargo 给的。

### 2.8 工具链与开发者体验（P1）

有 `yh test`（语言内 `test` 块 + 外部 runner）、`--emit-llvm`、`--stats`、
`yh-explorer`。缺：

- **LSP**（I2 VS Code 扩展待做）、保存后诊断、跳转、重命名
- 格式化器（`.yh` 无 fmt，风格靠人）
- lint（clippy 类；当前 warning 只有 1 个调用点）
- 文档生成（`doc.yh` 手写）、doctest
- 覆盖率、基准门禁（PF 系列）、fuzz（解析器无嵌套深度上限）
- 调试信息 + DAP

依赖关系：LSP 需要 2.1 的结构化诊断 + 2.2 的独立检查阶段 + 稳定的 AST 查询。
**顺序不能倒**，这也是为什么 2.1/2.2 必须先行。

### 2.9 平台与 ABI（P1/P2）

- 认识 4 个 triple（Linux/Darwin × arm64/x64，
  [gen/target_info.yh:10](../../compiler/gen/target_info.yh#L10)），但**种子与门禁只覆盖
  arm64**；x64 靠 qemu/Apple container 模拟，且已记录运行期崩溃（D3）。
- **Windows 全缺**：MSVC ABI/LLP64、COFF/PE、Unicode、进程模型。
- C ABI 受限：聚合值须指针、回调受限、用户裸变参不支持；无 C++ interop
  （`lld_bridge.cpp` 是内部桥）。
- 无 wasm/其他目标。
- 内嵌 LLVM/lld 闭包 569MB，首次 `make bootstrap` 需源码构建；SDK 27 与内嵌
  lld 21 不兼容（C3）。

### 2.10 治理与可信度（P2，但"可信编译"值得单列）

- 无 edition、无 stability attribute、无 MSRV、无废弃策略；0.0.x 期间破坏性变更
  可随时发生（模块私有类型 2026-10-12 才引入）。
- 无 API 稳定性检查（semver-checks）、无迁移工具。
- 测试厚度好：803+ 语料、固定点门、arch-check、TOML 681/681 与 string
  参考差分。
- **可信重建缺失**：源码无法在仓库内独立重建编译器（依赖种子二进制 + 固定点，
  AGENTS.md 明示），种子是单一信任根；无签名（gpg/cosign）、无 provenance。
  Rust 至少有多条独立路径（stage0 源码、mrustc、reproducible builds）。
  这不是功能差距，是**信任模型**差距 —— 若 yh 要用于生产分发，这一条会被审计问到。

## 3. 差距分类（决定"该不该补"）

| 类别 | 内容 | 判断 |
|---|---|---|
| **工程缺口**（必须补） | 诊断基础设施、错误恢复、独立检查阶段、DWARF、对象级增量、边界/溢出/穷尽性等安全默认、LSP/fmt/lint、编译时间门禁 | 与语言大小无关，工业级硬门槛 |
| **设计取舍**（据定位决定） | 泛型、trait、所有权/借用、闭包、方法、`match`、宏、运算符重载、GC | 不补也可以是工业级语言（Zig 路线）；但要为"无通用容器/无统一抽象/UB 默认"记账 |
| **生态缺口**（需外部条件） | registry、包管理、文档托管、社区库 | 先做本地锁文件与版本约束，托管后置 |
| **平台缺口**（工程量） | Windows、x64 原生、交叉编译、C++ interop | 按目标用户排期，不阻塞语言核心 |

一个容易误判的点：**"对标 Rust"不等于"实现 Rust 的特性清单"**。Rust 的工业级
来自"错误的可诊断性 + 破坏性变更的可控性 + 生态的可复用性"，而不是 trait 本身。
yh 若把预算投在 trait/泛型上而不投诊断与 LSP，得到的是"更难用的玩具"。

## 4. 优先级路线与验收标准

### P0（不改语言设计，决定"能不能被第三方用"）

| # | 事项 | 验收（可观测） |
|---|---|---|
| P0-1 | Diagnostic 模型 + 源码渲染 + 多条错误恢复 | 一个含 5 个独立错误的文件一次编译输出 5 条，每条含 caret 与颜色/无颜色两态 |
| P0-2 | `--message-format=json` + 错误码 | 任意一条诊断可被脚本解析出 code/spans/severity；错误码有索引文档 |
| P0-3 | 独立类型检查阶段（从 `parse/` 抽出，`yh check` 可用） | 只做语义检查不产码；后续函数在首错后仍被检查 |
| P0-4 | DWARF 调试信息（`-g`） | gdb/lldb 在 yh 源码行下断点，`bt` 显示函数名与行号 |
| P0-5 | 安全默认：边界检查、整数溢出语义、enum switch 穷尽性 | 越界触发确定性 trap；溢出在 O0 报错/在 O2 有明确文档语义；缺分支报错 |
| P0-6 | 对象级增量 + 编译时间门禁（PF0/PF1） | 改一个函数体，重编时间 < 全量 10% 且产物逐字节相同；CI 有回归阈值 |

### P1（生态与体验）

LSP（诊断→跳转→重命名）、fmt、lint 框架、包管理最小版（锁文件 + 版本约束 +
本地 registry）、ThinLTO、fuzz + 覆盖率、Windows/x64 原生门。

### P2（按需）

edition/稳定性属性、签名与可复现构建、C++ interop、远程缓存、PGO。

### 明确不建议现在做

泛型/trait（除非先解决单态化与 `.s.i` 接口稳定性）、宏系统、GC、
自定义优化 pass 族（LLVM 已够，缺的是分析与诊断而非优化）。

## 5. 结论

yh 已经跨过"玩具"与"能用"之间的门槛：自举、固定点、LLVM、函数级增量、
803+ 语料、无环模块图 —— 这些在新语言里属于少数派。

与 Rust 的差距可以压缩成一句话：**yh 的编译流水线是"正确的"，Rust 的是"可诊断的、
可增量的、可演进的"。** 三条具体表现：

1. **错误是副产品**（fail-fast、单条、纯文本），而非产品（恢复、多条、结构化、
   可修复）。
2. **语义分析是解析的附庸**（无独立阶段、无流分析），所以安全默认与 IDE 能力
   都被卡在上限。
3. **变更管理是版本号**（0.0.x 随时破坏），而非制度（edition/稳定性/semver 门）。
