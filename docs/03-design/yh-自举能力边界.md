# yh 自举能力边界与验收契约

## 1. 自举的定义

本文把三个目标分开，避免把“语法能解析”误认为“编译器已经自举”。

1. **语法自举**：一个用 `.yh` 编写、由现有 C 版 yh 编译出的词法/语法检查器，能够读取自己的完整 `.yh` 源码，按 `docs/yh.g4` 消费到 EOF，并对 `tests/yh/` 的正反例作出正确判断。
2. **编译器自举**：同一份 `.yh` 编译器源码由现有 C 版编译出 stage1；stage1 编译该源码得到 stage2；stage2 再编译该源码得到 stage3。stage1 与 stage2 都能编译当前语言的语义/运行用例，stage2 与 stage3 对固定输入生成一致的规范化汇编，并运行结果一致。
3. **工具链完全自给**：构建过程不再需要宿主 C 编译器、外部汇编器、链接器或 C 编写的运行时。这不是前两项的前提；现有 `libtcc1.a` 与 Darwin 终链仍依赖外部工具。

第一条是用户所说“语法自举”的最低证明；方案最终按第二条验收，防止只写出一个能解析自己但不能生成可执行程序的演示品。首个验收平台固定为 AArch64 Linux ELF。Darwin arm64、其他架构与多平台方案独立推进。

## 2. 当前语法与必需的能力

现有 `fn`、显式类型、指针、结构体/联合体、数组/切片、函数类型、递归、控制流、位运算、`sizeof(T)`、`malloc/free/memcpy` 足以表示词法器、符号表、类型检查和 AArch64 指令编码。新的编译器可以采用不同于现有 TCC 的内部结构，不要求把 C 文件逐行翻译为 yh。

**最低闭环不新增语法产生式。** 程序入口仍可用 `fn main() int`；源码从标准输入读取，汇编文本写到标准输出，构建脚本负责重定向、汇编与链接。为此必须把下面的 libc 函数加入编译器内置 prelude：

```yh
// 此处展示签名；用户源码仍不能直接写无函数体原型。
fn read(fd int, buf *void, count u64) i64
```

语义与现有 `write` 对称：返回正数为实际读取字节数，0 为 EOF，负数为错误；允许短读。循环读取时，`read` 的 `count` 不得超过缓冲区剩余容量；错误要打印到文件描述符 2 并以非零码退出。输出循环处理 `write` 的短写。标准输入/输出的文件描述符分别为 0/1，仅在首个 Linux 自举目标承诺 POSIX 行为。

推荐同阶段增加 `close(fd int) int` 以支持显式打开的输入文件，但语法自举的流水线不依赖它。实际文件路径、`-o` 等 CLI 功能需要额外允许 `fn main(argc int, argv **char) int`；这是 `main` 的**语义检查及 ABI 改动**，现有 `fnDecl` 语法已经能解析此写法。保留 `fn main() int`，两种签名都返回进程退出码。`argv[argc]` 为空指针，`argv[i]` 为 NUL 结尾字符串。新增参数入口须分别在 Linux 和 Darwin AArch64 验证；第一轮自举只依赖 Linux。

不在第一轮增加 `import`、`extern fn`、宏、泛型、动态数组字面量、`sizeof(expr)` 或内联汇编。运行时函数继续由 prelude 明确登记；编译器源码按依赖顺序放在多个 `.yh` 文件，构建时拼接到 `tmp/bootstrap/compiler.yh`。各源文件保持职责单一和约 500–1000 行。拼接只处理完整的顶层声明，不做文本替换或条件编译；所有 stage 使用同一个拼接产物。若未来要求直接编译多文件且保留独立命名空间，再单独设计模块系统。

## 3. 自举编译器的边界

- 输入：当前 `.yh` 词法、语法及已定案语义；完整源文件必须消费至 EOF。语法检查模式不解析符号；编译模式必须报未定义名、类型错误等语义错误。
- 前端：先登记顶层类型/函数签名，再编译函数体，支持互递归与现有 `pub`、const 和作用域规则。类型必须先声明后使用的限制与现行语义一致。
- 输出：先生成确定性的 AArch64 Linux 汇编文本；由系统汇编器/链接器生成 ELF。汇编器仅做指令编码与重定位，不能调用现有 `yh` 或 `libtcc` 来解析或生成 yh 代码。
- 语言覆盖：stage1/stage2 必须通过当前 `tests/yh/`、`tests/yh-run/` 的正例、反例与运行用例，并补齐指针写入、结构体/联合体、数组按值、切片、函数指针、类型化变参、浮点、全局初始化等运行用例。任何未覆盖语法不得靠“编译器自身没用到”跳过。
- 诊断：非法源文件返回非零码，不能崩溃、无限递归或产生成功伪装的输出；可读错误至少含文件位置及错误类别。
- 可重复性：固定源码、目标与工具链版本时，stage2/stage3 的规范化汇编一致。规范化只去除不承诺稳定的路径/时间戳，不删指令、符号或数据。

## 4. 与现有设计的关系

现有 C 版继续作为 stage0 种子；不把 `.c` 改名为 `.yh`，不把 `libtcc` 当作 stage1 的代码生成后端。`docs/03-design/00-语义边界-0.0.1.md` 中无参 `main` 的约束，在 CLI 阶段扩展为上面两种签名；`docs/yh.g4` 的注释与 prelude 清单应在实现时同步更新。旧版 C 编译器可以保留供差分测试，替换默认 `yh` 前须完成 stage1/stage2 全量验证。
