# yh 对标 Zig 级工业编译器：差距分析

日期：2026-10-25
性质：**以代码与实测为准的差距分析**，不改代码、不改种子、不滚种子。
方法：实测 `compiler/`（13 模块 / 118 个 `.yh` / 52,398 行）、`libs/`（24,069 行 /
366 个 `pub fn`）、`tests/`（`.yh` 语料 792 个文件：`tests/yh` 130、`yh-run` 360、
`modules` 278、`selfhost` 24）；并用本机 **zig 0.16.0** 做同题对照实验（探针在
`tmp/zigprobe/`、`tmp/yhprobe/`，不入库）。
配套：已有[对标 Rust 分析](yh-对标Rust工业级编译器差距分析-2026-10-25.md)，
本文不重复其结论，只做 Zig 口径的差异与收敛（见 §3）。

---

## 0. 判定口径：Zig 的"工业级"不是 Rust 那张清单

| 支柱 | Zig 的对应物（0.16 实测/文档） | 与 Rust 口径的差异 |
|---|---|---|
| 一体化工具链 | 单个 `zig` 二进制内含 `build-exe/build-lib/obj/run/test/fmt/ast-check/cc/c++/ar/objcopy/translate-c/fetch/env/reduce`，`-femit-bin/asm/llvm-ir/h/docs` | Rust 靠 cargo 生态；Zig 是"编译器即工具链"，**缺一环就是体验断点** |
| 交叉与自包含 | `zig targets` 实测 58 arch / 42 os / 27 abi；自带 libc（darwin/glibc/mingw/musl/wasi）+ compiler_rt + 头文件；四目标无 SDK 交叉实测成功 | Rust 目标多但依赖系统 SDK/链接器 |
| 显式控制 + 安全档 | 无 hidden control flow、无 hidden allocation；Debug/ReleaseSafe/ReleaseFast/ReleaseSmall 四档，ReleaseSafe 保留越界/溢出/窄化检查 | Rust 是**编译期**安全（借用检查）；Zig 是**运行期可选**检查 |
| comptime 参数化 | `type` 是一等编译期值，标准库全部泛型容器靠它（`ArrayList(T)`/`HashMap(K,V)`） | Rust 用 trait + 单态化；Zig 用 comptime |
| 双后端 | LLVM + 自研 x86_64 后端（`-fllvm/-fno-llvm` 实测存在） | Rust 只有 LLVM |
| 构建图 + 内容缓存 | `build.zig`（Step 图、`-D` 选项、install/uninstall）+ `build.zig.zon`（`url`+`hash` 或 `path`、`fingerprint`、`minimum_zig_version`）+ 全局缓存 | cargo 的 TOML/lock + 中央 registry |

**先说结论**：按 Zig 口径，yh 最缺的不是"诊断"（那是 Rust 口径的第一名），而是三件：

1. **comptime 不够深**：没有"类型作为编译期值"，于是没有参数化多态，于是标准库没有容器；
2. **交叉不闭环**：4 个 triple、链接模板绑定构建宿主、无自带 libc/C 前端；
3. **安全默认反了**：唯一档等于 Zig 的 ReleaseFast，越界/除零/空指针全部静默，且**无开关**。

## 2. 逐项差距

### 2.1 comptime：不是"有没有"，而是"能不能当类型用"（P0）

现状：`@[comptime]` + `$f(...)` + 函数体 `$if/$for` + `$is_type`；typed IR 解释器
（100000 步 / 64 帧预算）；语言**显式拒绝**"泛型、first-class 类型值、按实参类型
特化"（[CT6 §1](yh-编译期CT6语法设计.md#L16)、[§3.2 候选 C](yh-编译期CT6语法设计.md#L77)）。

后果已可实测：

- `libs/` 无任何通用容器（无 `Vec`/`Map`/`HashSet`）；三份私有池各造一遍：
  `toml/document.yh`（444 行）、`json/document.yh`（340 行）、`cli/cli.yh`（893 行）；
- 无统一 `Allocator`、无 `Result<T,E>`、无 `sort(lessThan)`（`libs/libc/sort.yh`
  是 O(n²) 插入排序的 qsort 兼容层）；
- 标准库的"泛型"只能靠复制粘贴或 `*void`。

Zig 对照：`type` 是 comptime 值，`fn Box(comptime T: type) type` 一个函数产出全部
实例；`@typeInfo` 反哺序列化/格式化；标准库容器全部由此而来——**Zig 没有泛型语法，
但有完整的参数化多态**。

判定：**工程缺口（语言表达力），不是设计取舍**。这是本文与 Rust 版分析最大的
分歧点：Rust 版把"泛型"归为设计取舍，理由是"Zig 路线不补也能工业级"；但在 Zig
路线里，不补的只是**语法**，参数化多态本身是标配。

最小可行切片（复用现有基础设施，不引入 trait/借用）：

1. `paramName: type` 形参（类型作为 comptime 实参）+ `T` 可用于 `*T`、`[]T`、
   `[N]T`、`sizeof(T)`；
2. 实例化命名 = `fn` 名 + 实参类型身份摘要（`.s.i` 已有类型编号，IR 缓存键已含
   签名/受检事实，单态化实例可直接进现有函数缓存）；
3. 不做隐式推导（`Vec{1,2,3}` 需显式 `Vec(i32)`）。

验收：`libs/vec`/`libs/map` 落地且被 ≥2 个既有库替换；实例符号可预测；
`make test` + `make selfhost-native` 固定点仍绿。

### 2.2 安全默认：唯一档等于 ReleaseFast，且不可选（P0）

实测与证据：

| 项 | 现状 |
|---|---|
| 除零 | 商 0、余数=被除数，不 trap（[llvm_scalar.yh:199](../../compiler/backend/llvm_scalar.yh#L199)） |
| 运行期溢出 | 回绕，无 `nsw/nuw`（[llvm_scalar.yh:230](../../compiler/backend/llvm_scalar.yh#L230)）；**编译期**才报"编译期整数运算溢出" |
| 越界 / 悬垂切片 | 文档化 UB，不检查（[语义边界 §6](00-语义边界-0.0.1.md#L91)、ADR-0001；todo 明列"决定不做"） |
| 窄化 `to_type` | 截断不检查（`300.to_type(i8)` = 44） |
| 空指针 | SIGSEGV 静默（实测 139） |
| 安全开关 | **不存在**：CLI 只有 `-O0/-O2`，属性只有 `extern/inline/comptime/noreturn` |

Zig 对照：Debug/ReleaseSafe 默认检查溢出/越界/窄化/非法枚举值/未初始化，
`@setRuntimeSafety(false)` 逐点关，`unreachable` 显式标注不可达。**Zig 的"无隐藏
控制流"并不等于"无声失败"**，yh 现在把两者混在一起了。

判定：**工程缺口**（不动语义，只加档位）。验收：新增检查档后，溢出/越界/除零三条
探针 trap、`-O2` 保持现状；语义契约新增"检查级别"一节；`make test` 语料按档筛选。

### 2.3 错误处理与资源清理（P1）

现状：无 error union / `try` / `catch` / `defer` / `errdefer` / `?T` / `unreachable`。
实际范式是"结果结构 + early return"（全 `libs` 34 处），**没有自动清理**；
分配失败规范反而做得不错（先 `memory.release` 再返回，不留半成品，
[string/owned.yh:29](../../libs/string/owned.yh#L29)）。

判定：**设计取舍**（显式控制流），但代价必须记账：错误路径清理靠人，随规模线性
增长；366 个 `pub fn` 每一个都要手写。

若要补最小切片：只加 `defer`（不加 `errdefer`）——它仍是显式控制流，与 Zig 的
立场一致，且能消掉绝大多数清理样板。

验收：`defer f()` 在早退/break/continue 路径执行、嵌套逆序；固定点与语料不变。

### 2.4 内存与容器（P0/P1）

- `libs/memory` 18 行，只有 `alloc/release/copy`；底层是 **mmap**（Linux
  `linux_syscall6` 222/9，Darwin `MAP_ANON`），用户产物已不链 libc 的
  `malloc/free/printf/memcpy`（`nm -u` 仅 `_mmap/_munmap/_write`）；
- 无 `reallocate`/Arena/FixedBuffer/Pool/统一 `Allocator`（M0–M6 全未做）；
- 无泄漏/重复释放检测，且设计文档明说因 `free` 立即 `munmap` **做不了** Zig 式
  DebugAllocator（[memory 设计 §60](yh-memory标准库设计-2026-10-23.md)）。

Zig 对照：`std.mem.Allocator` vtable 贯穿一切容器，`std.heap.*` 多种实现，
`std.heap.DebugAllocator` + `testing.allocator` 检测泄漏/双 free。

判定：**工程缺口**（已有 M0–M6 设计，缺实施）。验收：M1 `reallocate` + M3 Arena
过 `MEMORY_TEST_FAIL_AFTER` 注入门；一个容器被 ≥2 库替换。

### 2.5 并发与原子（P1/按需）

现状：线程/锁/TLS/async/原子内建**全无**（`libs/cli` 里的 `mutex` 是参数互斥组）；
编译器自身并发是 `fork`+COW 进程池、`active < 4`，J4/LA5 未做；HTTP 并发后置。

Zig 对照：`std.Thread/Mutex/RwLock/Condition/ThreadPool`、`@atomicLoad/@cmpxchgWeak`、
`std.atomic`。

判定：**设计取舍（无线程）+ 工程缺口（无原子）**。注意"无原子内建"比"无线程"更
硬：连单线程无锁数据结构都写不了。若定位是"系统工具语言"可延后；若要对标 Zig 的
服务端/并发叙事（HTTP 服务端已在设计里），则是前置。

### 2.6 后端与产物质量（P1）

现状：**文本 LLVM IR + C API 桥**——`LLVMParseIRInContext` → `LLVMVerifyModule` →
`LLVMRunPasses("default<O0>"|"default<O2>")` → `LLVMTargetMachineEmitToMemoryBuffer`
（[bridge.c:151](../../compiler/llvm/bridge.c#L151)）。发射器不写 metadata、不挂
per-function 属性组、CPU 固定 `"generic"`；运行时函数全带 `optnone noinline`
（实测 `--emit-llvm` 产物）；只有 `-O0/-O2` 两档；无 LTO/PGO/sanitizer。

Zig 对照：C++ API 直接建 IR（单编译单元、可跨文件内联、可挂 DWARF/属性/TBAA），
`-flto`、`-fno-llvm`（自研 x86_64 后端）实测存在。

判定：**设计取舍（文本 IR、单后端）**，但两个后果要单独记账：

1. **无 DWARF**：全仓 `DICompileUnit|DILocation|DIBuilder|!dbg` 0 命中，`-g` 不存在，
   产物 debug 节计数 0 —— 只能反汇编级调试。这是 IDE 调试、崩溃定位、性能剖析的
   共同前置，属**工程缺口**而非取舍。
2. **无跨模块内联**：每模块独立 parse+O2，模块间零内联；`-O2` 与 `-O0` 的 `.ll`
   文本逐字相同（实测），差别只在 LLVM pass 层——所以"前端 O2"没有内容。

验收：`-g` 后 `otool -l`/`readelf -S` 出现 `__debug_info/__debug_line`，`lldb`
能在 `.yh` 行下断点；`-flto` 后跨模块私有函数符号消失。

### 2.7 目标矩阵与交叉编译（P0，Zig 的招牌）

- 4 个 triple（[target_info.yh:10](../../compiler/gen/target_info.yh#L10)）；桥内白名单
  虽含 `x86_64-pc-windows-msvc`，但 `target_resolve` 不认 → **不可达**；无 wasm、
  无 freestanding/bare-metal；
- 交叉受**链接模板绑定构建宿主**：Linux 模板烘焙宿主 GCC 的绝对路径
  （`crt1.o`、`-L/usr/lib/gcc/aarch64-linux-gnu/13`、`-lc`、`-lgcc`）；Darwin 侧只有
  340K 的 `libSystem.tbd` stub；
- **实测失败**：macOS/arm64 上 `--target x86_64-unknown-linux-gnu` 因 ld64.lld 模板
  报 `must specify -arch`；Linux 产 Mach-O 需显式 `SDKROOT` 才能链接纯 `.yh` 程序。
  两个方向的交叉编译任务已于 2026-11-06 从 todo 撤下（见 todo P0 段说明），
  待重新立项。

Zig 对照：58/42/27 目标组合；自带 libc 源码、compiler_rt、头文件；**四目标无 SDK
交叉实测全部成功**（ELF/PE32+/wasm/Mach-O）。

判定：**工程缺口（目标包与链接模板解耦）+ 平台缺口（Windows/wasm）**。

验收：目标链接配置从"构建宿主 `gcc -###` 派生"改为"随编译器分发的目标包"；
macOS 产 x64 ELF 与 Linux 产 Mach-O 各一条 `file` 门。

### 2.8 C 互操作（P1）

现状：`@[extern]` 手抄签名 + 自动 C ABI（arm64 完整 AAPCS64/Apple HFA；x64 是简版
SysV：>16 字节直接 MEMORY，无 SSEUP/complex/unaligned 细分）；`extern struct/union`
共享布局（比 Rust 版分析里记得要好）；拒切片、按值数组、普通聚合、裸变参；**无头
文件解析、无 translate-c、无 C 预处理器**，`[c].sources` 交宿主 CC。

Zig 对照：`@cImport`/`zig translate-c`/`zig cc`——从真实头文件推导布局与宏。

判定：**工程缺口（C 前端/translate-c）+ 设计取舍（不开放裸变参）**。

验收：给定 `.h` 能生成等价 `@[extern]` 绑定（或明确诊断"需 translate-c"）；
`[c].include` 路径参与编译期布局校验。

### 2.9 构建系统与包管理（P1）

现状：静态清单——`[project]`（name/version/author/source/os/arch）、
`[dependencies]` **只接受 `{ path = "..." }`**、`[c]`（sources/objects/libs）、
`[link]`/`[link-<os>-<arch>]`/`[link-options]`；无 step、无 `-D`、无 install 步骤、
无自定义命令、无脚本入口；无 URL/版本/锁文件/哈希/workspace/feature；标准库靠
`YH_STDLIB` 隐式装载，Release 资产只含 `yh`（T5.2 未决）；缓存只在项目内
（`.build/targets/<triple>/llvm/O<n>`），无跨项目共享、无 `--cache-dir`。

Zig 对照：`build.zig` 可编程 Step 图 + `build.zig.zon`（`url`+`hash` 或 `path`、
`fingerprint`、`minimum_zig_version`，实测）+ `install/uninstall` steps +
`-Dtarget/-Dcpu/-Doptimize`（实测 `zig build -h`）+ 本地/全局两层缓存。

判定：**工程缺口**。清单驱动对"单仓库自举"够用，对第三方生态封死；Zig 也没有
中央 registry（`zig fetch` 直接按 URL 取），所以**缺的不是 registry，是可编程图与
内容哈希锁定**。

验收：`yh build -Dk=v` 被项目真实消费；依赖内容摘要落锁文件（改依赖必重编）；
`--cache-dir` 两项目复用且 `--stats` 见 `ir_cache_hits>0`。

### 2.10 工具链一体化（P1，Zig 最显著的特征）

| 能力 | yh | Zig |
|---|---|---|
| 源码格式化 | **无** | `zig fmt`（就地 + `--check`） |
| 文档生成 | 手写 `doc.yh`，无 HTML | `-femit-docs`（HTML + 源码归档） |
| 语法检查 | `--syntax-check`（只静默/非零） | `zig ast-check`（定位到具体节点） |
| C 工具链 | 无 | `zig cc/c++/ar/objcopy/dlltool` |
| C 头文件 | 无 | `-femit-h` |
| 构建产物形态 | `--emit-asm`/`--emit-llvm`/`-o` | `-femit-bin/asm/llvm-ir/h/docs` |
| 并行 | `active < 4` 硬编码，无 `-j` | `-j` 可配 |
| 缓存控制 | 无 `--cache-dir`、无 clean 子命令 | `--cache-dir`/`--global-cache-dir` |
| 测试 | `test "名" {}` + doctest 绑定、`--filter/--timeout/--no-run`；**每例 fork，无并行**；无 `expectEqual` 族、无 `testing.allocator` | `zig test` + `std.testing.*` + 泄漏检测 |
| LSP | 无（I2 未做，且被进程级全局 `GenState` 挡住） | 无官方 LSP（ZLS 社区），但有 fmt/ast-check/增量 |

判定：**生态缺口**（可增量补，`fmt` 与 `doc` 投入产出最高）。`fmt` 只需复用现有
parser + layout 信息做"最小重排"，`doc` 只需遍历 `.s.i` 与声明注释。

验收：`yh fmt` 幂等（连跑两次字节相同）且语料输出不变；`yh doc` 覆盖每个 `pub`
声明与其注释块。

### 2.11 标准库门类（P1）

24 个门类：**有 2**（toml 681/681 + 注入门、cli）、**部分 12**、**无 10**
（containers、unicode、tls、http、crypto、compress、debug/log、locale、
mime/url、regex、uuid）。质量分布极不均：toml 有 124 点注入与一致性门，json 缺
J4/J5，string 有参考差分，memory/math 基本空壳。

判定：**生态缺口**（按消费者补，不做全量对标）。验收：每库一个
`make test-<lib>` 进 `make test`；json 补一致性+注入。

### 2.12 编译器工程与治理（P2，影响"工业级"的信任面）

- **诊断**：单条、无源码行/caret/span/JSON/错误码、无 ICE 协议（与 Rust 版一致；
  Zig 也不是结构化诊断，但至少有 caret + note）；
- **无独立检查阶段**：用户级类型检查耦合在 `parse/` 两遍扫描 + `gen/sem_*` 单遍，
  `check/` 只是 arena 内部一致性校验（Zig 有 AstGen→Sema 分层）；
- **增量**：函数级 check/IR 缓存 + 链接缓存 + 进程池（Zig 的增量编译仍在
  选项面推进，这一点 yh 不落后）；缺对象级与查询图、缺性能门（PF0–PF4 待做）；
- **自举与信任**：两代固定点（强项）；但种子是唯一信任根，无签名/可复现构建；
- **版本治理**：0.0.9，无 edition/稳定性属性；Zig 同样"1.0 前不承诺稳定"，但每次
  release 有迁移说明 + `zig fmt` 统一风格 + 全量 langref。

判定：诊断与检查阶段 = **工程缺口**；版本治理 = **设计取舍**，但要比 Zig 多付一笔
"风格不统一"的账（Zig 用 `fmt` 抵掉了它）。

## 3. 与既有 Rust 版分析的关系（两套口径不打架）

| 事项 | Rust 版判定 | Zig 版判定 | 依据 |
|---|---|---|---|
| 与泛型/参数化 | 设计取舍（不补也能工业级） | **工程缺口**（Zig 用 comptime 给足参数化） | §2.1 |
| trait/所有权/借用检查 | 设计取舍 | **确认不需要**（Zig 也没有） | Zig 路线 |
| 诊断/错误恢复/JSON/错误码 | P0 | P1（Zig 自身也不结构化） | §2.12 |
| 交叉自包含、C 前端、`cc` | 平台/生态缺口 | **P0**（Zig 的招牌） | §2.7/§2.8 |
| 安全默认 | P0（边界/溢出/穷尽性） | **P0，且更严重**（唯一档 = ReleaseFast） | §2.2 |
| DWARF | P0 | P0 | §2.6 |
| 对象级增量/查询图 | P0/P1 | P1（Zig 增量仍在选项面推进） | §2.12 |
| 构建图/包管理 | P1 | P1（Zig 有 zon，无中央 registry） | §2.9 |

一句话：**Rust 版问"能否被第三方依赖"，Zig 版问"能否一个人带着一个二进制做全平台
交付"**。两者重叠的部分是 DWARF、安全默认、构建/缓存；分歧在诊断权重与 comptime。

## 4. 分类总表

| 类别 | 内容 |
|---|---|
| **工程缺口（必须补）** | comptime 类型参数（→ 容器/Allocator）、安全档位、DWARF、`defer`、目标包与链接模板解耦、C 前端/translate-c、`fmt`/`doc`、构建图与依赖哈希、M0–M6 内存、测试并行与断言族 |
| **设计取舍（据定位）** | 无 trait/借用检查、无 error union、无线程、文本 IR、单后端、无裸 C 变参、静态清单 |
| **生态缺口（需外部条件）** | 容器/crypto/compress/regex/uuid/mime/unicode 门类、第三方库、文档托管 |
| **平台缺口（工程量）** | Windows/COFF/MSVC、wasm/freestanding、x64 原生种子与门禁 |

### 不建议现在做（与 Zig 对照后仍然不做）

自研机器 IR/寄存器分配/JIT/32 位/LTO 落地（ADR-0014 既定；Zig 双后端的收益是
"免 LLVM 也能出码"，yh 没有这个诉求）、trait/所有权/借用检查、中央 package
registry（Zig 自己也没有）、宏系统、GC。

## 5. 优先级（Zig 路线）

**P0 —— 决定"能不能当 Zig 的替代品被单兵使用"**

| # | 事项 | 验收（可观测） |
|---|---|---|
| P0-1 | 安全档位（checked 档：溢出/越界/除零/窄化 trap） | 三条探针在 checked 下 trap、`-O2` 下保持现状；契约新增检查级别 |
| P0-2 | comptime 类型参数 + 单态化命名 | `Vec(i32)`/`Map(str,i32)` 落地，≥2 库替换；固定点绿 |
| P0-3 | 目标包解耦（链接模板/自带 crt 与目标 libc 描述） | macOS 产 x64 ELF、Linux 产 Mach-O 各一条 `file` 门 |
| P0-4 | DWARF（`-g`） | lldb 停在 `.yh` 行；无 `-g` 时产物无 debug 节 |
| P0-5 | `yh fmt` + `yh doc` | fmt 幂等且语料不变；doc 覆盖全部 `pub` 声明 |

**P1**：构建图/`-D`/依赖哈希与 `--cache-dir`；translate-c 或 `[c].include` 布局
校验；`defer`；M1/M3 内存与两个容器；标准库门类补齐（json J4/J5、crypto 首片）；
测试并行 + `expectEqual` 族；诊断错误恢复与 JSON 输出。

**P2**：原子/线程与 `serve_fork`；`-flto`/`-O1/-O3/-Os`/`--gc-sections`；Windows
与 wasm；LSP（前置是把进程级 `GenState` 收敛成显式上下文）；种子签名与可复现构建。

## 6. 结论

yh 已经具备"自举 + LLVM + 函数级增量 + 无环模块图 + 792 个语料"的地基，这在
新语言里是少数派。与 Zig 的差距压缩成三句话：

1. **语言层最锋利的缺口是 comptime 深度，不是缺泛型语法。** Zig 用"类型是编译期
   值"这一条，换来了全部容器与反射；yh 的 comptime 明确拒绝类型值，于是标准库只能
   每个类型硬编码一份。这不违背极简路线——补的是参数化，不是所有权。
2. **工具链层缺的是"自包含"三件套：目标包、C 前端、fmt/doc。** Zig 用一个二进制定
   义了"工业级交付"，yh 现在是"能自举，但离开宿主 C 工具链与手写文档就交付不出去"。
3. **运行期语义层默认反了：唯一档等于 ReleaseFast。** Zig 用 ReleaseSafe 证明"无隐藏
   控制流"与"默认检查"并不冲突；yh 现在越界读 0、除零得 0、空指针静默 139，而文档
   把这些写成契约。这不是缺功能，是缺一个开关与一套检查语义。

补齐 P0 五项不需要动语言设计（安全档是纯新增、类型参数复用现有接口/缓存机制、
目标包是工程解耦、DWARF 与 fmt/doc 是加工具），却能把"能自举的编译器"变成"能被
单兵交付的编译器"。
