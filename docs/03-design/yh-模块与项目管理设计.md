# yh 模块与 project.toml 项目管理设计

日期：2026-09-29。状态：**已实施**（MOD-U0–U5 于 2026-09-29/30 交付，
`make selfhost-native` 全绿；清单文件 2026-09-30 由 `mod.toml` 改名为
`project.toml` 并删除 `entry` 字段，入口改为模块名 `main`）。
本文是现行设计的权威描述；交付记录见 [finish.md](../finish.md)。

本文件替代上一版 Go 风格模块与包方案。用户已确定四项规则：项目管理
文件使用 `project.toml`；源码归属声明使用 `module`；没有 `internal` 特殊
机制；`import os;` 按当前项目、标准库、第三方库的顺序搜索。

下文将这些要求补充为可实现、可验证的语义。同模块多文件、清单字段和
同名诊断是配套规则，均已实现并由 `tests/modules/` 语料钉住。
实施步骤见 [实施方案](../02-plan/yh-模块与项目管理实施方案.md)，
取舍见 [ADR-0005](../adr/0005-yh-mod-toml与按名称导入.md)。

## 1. 只区分项目、模块和文件

| 概念 | 职责 | 身份 |
| --- | --- | --- |
| 项目 Project | 源码根、依赖、版本和入口，由 project.toml 管理 | project.name |
| 模块 Module | 命名空间、可见性与源码组织 | 解析后的项目身份 + module 名 |
| 文件 SourceFile | 实现模块，保留源码位置与自己的导入表 | FileID |

一个项目可以有多个模块，一个模块可以由多个 `.yh` 文件实现。不再设置
另一层名为 package 的源码单元，也不把项目称为源码 module。

模块名来自文件头的声明，不从目录名或文件名推导。目录只用于组织源码。
同一项目中都声明 `module math;` 的文件共同实现一个 math 模块，即使
分布在不同子目录，也不会因为移动文件改变模块身份。

首版模块名采用单个合法标识符；不引入嵌套模块树。`_` 不能作模块名。
模块名、声明名区分大小写，与 yh 标识符规则一致。

## 2. 用户如何使用

```text
demo/
  project.toml
  src/
    main.yh
    math/
      add.yh
      helpers.yh
    os/
      local.yh
```

项目清单：

```toml
[project]
name = "demo"
version = "0.1.0"
author = "lavender"
source = "src"

[dependencies]
json = { path = "../json" }
```

`src/math/add.yh`：

```yh
module math;

// 对外提供加法接口，结果交给同模块辅助函数处理。
pub fn add(a int, b int) int {
    return normalize(a + b);
}
```

`src/math/helpers.yh`：

```yh
module math;

// 保留当前整数值，仅供 math 模块的全部实现文件使用。
fn normalize(value int) int {
    return value;
}
```

`src/os/local.yh`：

```yh
module os;

// 返回项目自己定义的状态码，用于展示本地模块优先。
pub fn status() int {
    return 0;
}
```

`src/main.yh`：

```yh
module main;

import math;
import os;

// 入口使用本项目的 math 和 os，正常执行后返回零。
fn main() int {
    return math.add(0, os.status());
}
```

此处的 os 绑定到本项目模块。标准库 os 不与它合并。
所有源码示例均为拟议语法；本次没有创建实际项目清单或迁移编译器源码。

## 3. module 和 import 语法

模块模式文件顺序固定：注释与空白 → module 声明 → import 声明 →
顶层业务声明。**每个文件的第一行（注释除外）必须是 module 声明**；
**每个目录有且只有一个模块**（违反报错）；源码模块导入图禁止循环
（报完整环链）。

```yh
module app;

import os;
import libs.os as l;
```

简单语句沿用 yh 的分号规则。import 形式（2026-09-30 已实施）：

| 形式 | 查找 | 绑定名 |
| --- | --- | --- |
| `import os;` | 三层搜索（本项目→标准库→直接依赖） | os |
| `import os as os1;` | 三层搜索 | os1 |
| `import libs.os;` | 直接解析到依赖键 libs 的项目的 os 模块 | os |
| `import libs.os as l;` | 同上 | l |

第一段为 [dependencies] 依赖键时走跨项目直解析（不走三层，键缺失或
依赖无可导入模块显式报错）；绑定名重复报错（这正是 as 的用途）。
导入只允许出现在文件头，不允许出现在函数体或业务声明之后。

拟议 grammar 增量如下，不直接改写当前 `docs/yh.g4`：

```antlr
// 保留旧单文件入口，项目模式要求模块文件。
sourceFile
    : moduleSource EOF
    | topLevelDecl* EOF
    ;

// 模块文件先声明归属，再声明本文件依赖。
moduleSource
    : moduleClause importDecl* topLevelDecl*
    ;

moduleClause
    : 'module' IDENT ';'
    ;

importDecl
    : 'import' IDENT ';'
    ;
```

module/import 加入关键字时须同步检查已有的保留字成员名规则。
import 的绑定属于文件，不能被同模块其他文件借用。重复导入和未使用
导入报错；导入名与本模块顶层声明重名也报错。局部声明的遮蔽沿用既有
词法作用域规则。

纯语法检查只判断文件形态，不读取 project.toml、不搜索依赖。未知 os
不构成语法错误，项目构建阶段才决定它是否存在。

## 4. project.toml 最小清单

清单采用 [TOML 1.0](https://toml.io/en/v1.0.0) 格式。使用标准 TOML
语法和错误诊断，不把它当作 yh 源码，也不以字符串按行切割代替 TOML
解析。首版 schema 只需要以下字段。

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| project.name | 字符串 | 必填，标识符（字母或下划线开头，其余字母数字下划线）；项目的稳定身份，`yh build` 无 `-o` 时产物名取它 |
| project.version | 字符串 | 可选，`yh version` 读取显示；具体版本规则另行确定 |
| project.author | 字符串 | 可选，仅接受不解释 |
| project.source | 字符串 | 可选，默认 src；相对 project.toml 所在目录的源码根 |
| dependencies | 表 | 可选，记录当前项目直接依赖的项目 |
| dependencies.<依赖键>.path | 字符串 | 本地阶段必填，相对声明它的 project.toml 定位依赖项目 |

源码根必须位于本项目内；依赖 path 可以指向外部本地项目。依赖键用于
清单管理和错误定位，不充当源码导入别名。源码仍以依赖提供的 module
名导入，例如 json 项目中的 `module json;` 对应 `import json;`。

允许一个依赖项目提供多个非入口模块。构建器从直接依赖项目的模块索引
查找名字，而不是只导入依赖键或依赖项目根文件。

从当前工作目录向上查找最近的 project.toml，确定命令所属项目。项目的
source、依赖 path 均相对各自清单解析，不受运行命令的工作目录影响。
源码根内遇到嵌套 project.toml 时停止进入，该目录属于另一个项目。

无效 TOML、字段类型错误、未知字段和不可用源根要有清晰诊断。
不接受旧清单作为隐式替代，也不扫描未列入 dependencies 的任意库目录。
远程来源、版本求解和锁文件在后续阶段独立设计，当前示例只承诺本地依赖。

## 5. 模块发现与搜索顺序

构建器遍历项目 source 中的普通 `.yh` 文件，读取模块头，按 module
名建立索引。扫描顺序稳定，索引文件路径保留原始位置。同模块的多个
文件属于一个候选，不是多个同名模块。

索引只负责发现文件头；可达模块再执行完整词法、语法和语义检查。
入口项目构建从 `module main;` 的模块出发（模块名与目录名无关），
库项目（无 main 模块）构建以其库模块为根。临时产物放在
tmp/，不放进 source；目前不增加测试后缀和平台文件名的特殊筛选规则。

对 `import os;`，按以下顺序查找：

```text
导入名称 os
  ↓
导入文件所属项目的模块索引
  ├─ 找到：使用该项目的 os，停止搜索
  └─ 未找到
       ↓
当前工具链的标准库模块索引
  ├─ 找到：使用标准库 os，停止搜索
  └─ 未找到
       ↓
该项目直接依赖提供的第三方模块索引
  ├─ 唯一候选：使用该第三方模块
  ├─ 多个候选：同名冲突错误
  └─ 没有候选：模块不存在错误
```

搜索的单位是完整模块，不是某个成员。找到本地 os 后，`os.open`
不存在或本地 os 有编译错误，都直接报错，不能转而使用标准库 os，
也不能从标准库补齐本地缺少的成员。

第三方多个项目都提供 json 时，只有搜索进入第三层才报告歧义。
本地 json 或标准库 json 已匹配时，较低层的同名候选不会改变绑定。
首版不按依赖表顺序任选候选；需要调整提供方的模块命名或项目依赖。

缺失、损坏的依赖来源不能被当作“模块不存在”而静默跳过。当前层无法
可靠判断候选时，要报告来源错误。模块解析不自动访问网络下载。

## 6. 当前项目指谁

“当前项目”指包含这条 import 源文件的项目，不固定为最终可执行程序
所在的主项目。每个项目拥有自己的 source 与直接依赖表。

例如 app 定义本地 os，依赖 json 项目，而 json 文件写了 `import os;`：

1. app 的 import os 先查 app 的模块。
2. json 的 import os 先查 json 自己的模块，再查标准库及 json 的依赖。
3. app 的本地 os 不会替换 json 内部已声明的依赖。

标准库源码的 import 使用工具链标准库自身的索引上下文，不会被调用
项目的同名模块替换。这保证用户能局部遮蔽标准库，又不会改变标准库
内部实现的绑定。

标准库索引来自当前工具链，不从工作目录或任意全局库目录拼凑。现有
prelude 与新标准库模块是两种能力：保留既有内置调用行为，实施阶段再
提供最小可导入标准库及其接口，不能把当前 prelude 宣称为已实现的 os 模块。

一个项目不能借用其他项目的传递依赖。例如 app 只依赖 A，而 A 依赖
B；app 要直接 import B 提供的模块，必须在自己的 dependencies 中
声明 B。清单记录项目真实依赖，不能依靠缓存中碰巧存在的模块构建。

解析缓存键至少包含导入者项目身份和导入名，不能只按 os 缓存结果。

## 7. 身份与同名模块

`import os;` 是查找请求，os 本身不是全局唯一身份。解析结果必须记录
提供方项目身份、模块名、来源类别、实际文件集合与清单。

| 来源 | 同名示例 | 实际身份 |
| --- | --- | --- |
| 本地 | module os | 当前项目身份 + os |
| 标准库 | module os | 工具链标准库身份 + os |
| 第三方 | module os | 依赖项目身份 + os |

具名类型身份包含模块归属，机器符号编码包含提供方项目与模块；不能
只把函数链接成 os_open。导入名和文件路径变化不应创造另一个类型。
类型别名沿用原类型身份。

首版本地构建中，一个 project.name 只允许一个来源。相同项目身份
从不同真实目录装载时报告冲突；重复依赖同一规范化来源则复用实例。
多版本共存和远程项目身份验证另行设计，不在首版暗中作任意选择。

## 8. 私有与 pub，没有 internal 特例

继续使用 yh 的显式 pub。首版采用两档权限：默认模块私有、pub 可由
其他模块访问；大小写不决定导出，不增加 pub(package) 等新权限语法。

| 声明 | 同模块其他文件 | 其他模块 |
| --- | --- | --- |
| 普通函数、变量、常量、类型 | 可访问 | 不可访问 |
| pub 函数、变量、常量、类型 | 可访问 | 显式导入后可访问 |
| 无 pub 的结构体字段 | 可访问 | 不可访问 |
| pub 结构体字段 | 可访问 | 获得所属类型或值后可访问 |

不同模块即使属于同一项目，也执行 pub 检查。同一模块的辅助函数可以
分散到多个文件，不需要为了拆文件加 pub。模块本身没有额外导出开关；
能被当前搜索上下文找到的非入口模块，可提供自己的 pub 声明。

internal 目录与名为 internal 的模块均按普通名字处理，不限制导入者
的祖先目录，不保留 internal 关键字，也不引入额外目录访问规则。
两档权限意味着项目内部跨模块协作需要 pub；这是首版简洁性的明确取舍。

2026-10-02 起 struct/union/enum 一等化为 `pub struct`/`pub union`/
`pub enum`：裸写非法。struct/union **字段一律公开**（不存在私有字段），
字段不再接受 pub 前缀；enum 成员常量随枚举导出，跨模块以
`模块名.成员` 引用。**let 不支持导出**（`pub let` 非法）：可变全局
私有，跨模块共享经 pub fn 封装；编译器内部状态即以 `GenState` +
`gen.G()` 指针访问实现。公开接口必须携带所需的完整类型布局与依赖
元数据——依赖接口按拓扑序先行加载，接口正文里的跨模块类型按 mangle
名引用；跨模块字段访问与位置式构造不设字段级限制，类型自身的 pub
决定其可否被限定引用。方法归属和访问也以声明模块为边界检查。

pub let 仍表示可变公开存储，不自动变成只读属性。pub const 导出其值。
enum 沿用当前枚举项登记规则，不借模块化引入另一套枚举命名空间。

## 9. 多文件、图与入口

同模块先登记所有文件的顶层名字、类型占位和函数签名，再完成类型与
函数体分析。跨文件前向调用及函数互递归允许；同模块重复顶层声明要
报告两个原始位置。不得靠裸拼接让导入表共享或让文件排序决定可见性。

源码模块导入图禁止自循环、直接环和间接环，错误显示完整模块链。
同模块文件之间没有 import 边，拆文件不会凭空创造模块循环。
源码图与后续版本需求图分别管理。

模块名为 `main` 的模块即本项目入口（清单不另设入口字段）。仅该模块的 main 按已确定的 yh
入口签名生成最终程序入口；main 不需要 pub。库模块不要求 main。
其他模块里名为 main 的函数仍按普通模块符号处理。

入口模块不能被其他模块作为库导入。项目可以同时含入口和库模块；
作为第三方依赖时，仅其非入口模块进入可导入候选集合。

## 10. 构建流程与编译器接入

```mermaid
flowchart LR
    A[读取 project.toml] --> B[索引 module 文件头]
    B --> C[按三层优先级解析 import]
    C --> D[检查身份与模块导入环]
    D --> E[登记同模块声明并检查权限]
    E --> F[生成模块接口与代码]
    F --> G[链接入口与依赖]
```

最小必需模型如下。不是要求先重构编译器全部内部层次。

| 信息 | 必需内容 |
| --- | --- |
| Project | 身份、清单、源根、入口、直接依赖、模块索引 |
| Module | 提供方项目、名称、文件集合、已绑定依赖、声明表 |
| SourceFile | 路径、源码、token、模块归属、本文件导入表 |
| ImportBinding | 导入名称、源位置、解析后的 ModuleID 和来源 |
| ExportInterface | 可访问名字、类型闭包、常量、签名、ABI 与机器符号 |

0.0.3 起仓库已无 C 版 stage0（`src/core/` 已删除），只有自举侧实现：
词法 `compiler/lex/lexer.yh`、语法 `compiler/parse/parse_*.yh`、
语义与符号 `compiler/gen/symbols.yh` 与 `compiler/gen/sem_*.yh`、
入口 `compiler/cmd/driver.yh`。换 C 后端的接入点已随删除终结。

现有 pub 的机器链接绑定不能代替语言权限检查。限定名 m.T、m.f 和
m.value 都要查询已绑定的模块接口；模块名字不是运行时对象。
函数体源码位置和导入表要与声明所属文件一起保存。

首个完整本地里程碑应产生模块对象和稳定接口，接口不保存编译器地址
或临时类型编号。对象家族、目标、ABI 和接口格式版本必须一致；不能
假设 stage0 与自举对象未经验证就可混合链接。

## 11. 命令与兼容

以下命令属于拟议项目工具，不代表当前 CLI 已实现。

| 命令 | 行为 |
| --- | --- |
| yh build | 查找 project.toml；有 `module main;` 则构建程序（产物默认 `.build/<name>`），否则构建项目库模块 |
| yh build math | 只选择当前项目 math 为构建根，再构建其依赖 |
| yh check | 检查当前项目全部模块的语义，不生成汇编、对象或可执行文件 |
| yh check math | 检查 math 及其依赖，不生成后端产物 |
| yh run | 构建并运行 `module main;`；库项目报告无入口模块 |
| yh version | 打印当前项目的 name 与 version；裸 `yh` 用法后附同一行 |
| yh list | 列出当前项目的模块名和实现文件 |
| yh list --resolve os | 解释该项目 import os 的匹配来源与优先级 |

诊断工具列出项目身份、来源和路径，让同名遮蔽可检查；正常成功构建
不为用户要求的本地优先另加警告或审批步骤。

保留旧无 module 的单文件编译／语法入口。新项目模式的普通源码必须
声明 module，不能与旧文件静默混编。包含 module 的单文件可以纯语法
检查；真正构建时收集整个模块，不静默遗漏其他实现文件。

## 12. 缓存与后续边界

缓存要记录模块实际提供方，而非仅记录短名称。项目新增本地 os 后，
原先绑定到标准库 os 的导入必须重新解析，即使导入源码没有变化。
project.toml、模块索引、直接依赖来源和标准库身份均参与绑定有效性判断。

对象缓存还包含实现内容、接口、依赖接口、编译器／ABI／target／选项。
冷构建与热构建结果应一致；失败产物不得发布为可复用接口与对象配对。

第一阶段只做当前项目、标准库和本地第三方依赖。远程来源、版本选择、
锁文件、工作区、选择性导入、导入别名、初始化和测试发现后续按实际
需求另立设计，不照搬旧方案的 yh.mod/yh.sum/yh.work 或 MVS 承诺。

## 13. 验收矩阵

| 场景 | 应有结果 |
| --- | --- |
| 本地、标准库、第三方同时提供 os | 本地 os |
| 本地无 os，标准库和第三方都有 | 标准库 os |
| 前两层无 os，唯一直接依赖提供 | 第三方 os |
| 三层均无 os | 位置诊断与已搜索来源 |
| 本地 os 有语义错误或缺少调用成员 | 报本地错误，不回退或合并 |
| 两个直接依赖都提供 json，前两层没有 | 同名歧义，报告两个提供方 |
| 两个文件都声明 module math | 合并实现，私有声明共享 |
| 同模块另一个文件未 import os | 不能借用其他文件的导入 |
| 依赖内部 import os，主项目也有 os | 依赖按自己的上下文解析 |
| 仅传递依赖提供所导入模块 | 拒绝，要求声明直接依赖 |
| internal 目录内提供普通模块 | 与普通目录相同的规则 |
| 不同项目／模块定义同名类型和函数 | 身份与链接符号互不混淆 |
| 新增或删除本地同名模块，执行热构建 | 绑定重算，与冷构建一致 |
| module/import 纯语法合法但模块未知 | syntax-check 接受，项目构建拒绝 |

每项真实实现时在 tests/ 下新增 `.yh` 项目用例，正反例与运行分别
计数。当前只是方案修订，不用已有单文件回归宣称模块功能通过。
