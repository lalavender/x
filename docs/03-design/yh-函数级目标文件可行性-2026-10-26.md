# 函数级目标文件（单函数改动 ≤3 s 的唯一路径）可行性

日期：2026-10-26。状态：**评估，未实施**。前置数据见
[性能分析](../02-plan/yh-编译器性能分析-2026-10-25.md) §14/§14.1。

## 1. 问题

低负载实测（load≈4.5）单函数改动 3.9 s，拆开是：

| 阶段 | 秒 | 说明 |
| --- | --- | --- |
| 链接 | 1.17 | object 变了必须重跑 lld（静态 LLVM，产物 70 MB） |
| 对象/摘要 | 0.87 | 其中约 0.9 s 是**每轮重哈希 271 MB**（含 70 MB 的编译器自身与链接产物） |
| 模块重编 | 2.03 | check 205 个函数（命中 38）+ lower 1 个 + **LLVM 重发整模块 205 个函数** |

即使把摘要全部改成 (size, mtime) 复用（省 ~0.4 s），单函数改动仍是 ~3.5 s。
**≤3 s 必须让「只改了 1 个函数」不再重发整模块**，即把对象粒度从「模块 `.o`」降到「函数 `.o`」。

## 2. 现状约束

- worker 每个模块调用一次桥（`llvm_emit_module_to_cached`），输入是整份模块 LLVM 文本，
  一次产出 `<build>/obj/<tag>.o`；链接参数收集 13 个对象（`llvm_objects` 分支）。
- 模块对象键（manifest）覆盖模块源码 + 依赖接口 + 目标/选项；函数级 IR 缓存已经能把
  「未改动的函数」以缓存记录形式复用（v3），但**发射粒度仍是模块**。

## 3. 可选方案

| 方案 | 做法 | 预期单函数改动 | 风险/代价 |
| --- | --- | --- | --- |
| A 函数级 `.o` | 每个函数一个 `.o`：lower 后按函数切 LLVM 文本逐函数调桥，产物落到 `obj/<tag>/<fn>.o`；链接收 N 个对象 | ~1.4–1.8 s（模块重编 2.03 → ~0.1，链接 1.17 → 1.3） | 1460 个对象的链接与目录/清单开销；模块键需改成函数级（或按函数对象集合）；桥调用次数 13 → 1460（每次都有 LLVM 解析/初始化成本，可能抵消收益） |
| B 函数级 `.o` + 桥批处理 | 一次桥调用接收「多段函数文本 + 各自输出路径」，内部共享 LLVM 上下文 | 同上，且避免 N 次初始化 | 需要扩 C 桥 ABI（`compiler/llvm/bridge.h`）与 `lld_link_config.h` 身份；桥是种子的一部分，改 ABI 需滚种子 |
| C 增量 `.o` 重写 | 仍按模块发 `.o`，但用 `ld -r`/对象合并避免全模块重发 | 需要 LLVM 侧支持按函数替换，不可行 | — |
| D 只做摘要缓存 | (size, mtime) 复用摘要 | 3.9 → ~3.5 s（**不达标**） | 需接受 mtime 信任（make/ninja 级语义） |

## 4. 结论与建议

- 方案 A/B 都能把单函数改动压进 3 s 档，但**都动到发射与链接两层**，B 还要改桥 ABI
  （进而要滚种子）。工作量按天计，建议单独立项（PC7）。
- 与此独立、可立即做且语义不变的是**摘要缓存**（方案 D）：热编 1.14 → ~0.9 s、
  单函数改动 3.9 → ~3.5 s，并为将来任何粒度改进保留收益。
- 在函数级对象落地前，`≤3 s` 目标不可达；把目标改成 ≤4 s（现状满足）是诚实的收口。
