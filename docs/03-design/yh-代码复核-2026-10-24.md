# yh 编译器代码复核（2026-10-24）

性质：**代码级静态复核**，只读，不构建、不改代码、不动种子。
基线：分支 `llvm`，HEAD `19dd392`（`merge: 0.0.9 发布线合入 llvm`）；
工作区仅 `.gitignore` 有 2 行改动与未跟踪的 `deliverables/`，与本次复核无关。
方法：按 `.yh` 文件做行数/函数/导入/导出/全局/调用点/固定缓冲/分配的静态统计，
逐条验证上一版架构结论；**未运行** `make`、`make test`、`make selfhost-native`，
因此本文不构成任何"当前工作区已通过门禁"的声明。

## 1. 结论摘要

1. **分层是真的，不是纸面**：10 个模块、114 个 `.yh`、51,578 行，24 条显式依赖边、
   **0 个环**；`ir` 与 `backend` 中 `gen.G()` 调用点为 **0**，说明"IR/后端不碰前端
   全局状态"这条边界在代码里成立，不只是文档约定。
2. **复杂度是集中而非弥散**：1,411 个函数，行长中位数 **20 行**、均值 34 行；
   超过 200 行的只有 **24 个**（1.7%），超过 500 行的只有 1 个。这说明不需要
   "全面重构"，需要的是**定点拆解 24 个热点**。
3. **`cmd` 是唯一的过载模块**：24 文件 / 12,502 行（占 24.2%）/ 66 个模块级全局 /
   174 个 `G()` 调用点，并且**内含一个测试框架**（`test_cmd.yh` 1,655 行）与
   **一个 TOML 子集解析器**（`toml.yh` 604 行）。
4. **状态问题比上一版统计的更严重**：模块级可变 `let` 189 个（与上版一致），但
   `gen.G()` 是 **463 个调用点**，不是"51 个文件"这种模糊量级。
5. **增量能力比 10-22 复核时更完整**：函数级 **check 缓存与 IR 缓存已接入项目
   主路径**（`module_worker.yh:318-415`）。仍未落地的是**文件级对象**与**线程池**，
   以及 J5 的性能目标。
6. **新增一类此前未记录的风险：边界纪律**。`gen.append_str` **没有容量参数**，
   全仓库 236 个固定栈缓冲依赖调用方自觉；解析器**没有嵌套深度上限**；293 个
   `malloc` 调用点中约 **57 个**在随后 4 行内没有判空。
7. **约 500 行"已维护但从不执行"的优化代码**：`ir/ssa_inline.yh` 283 行与
   `ir_simplify` 217 行的调用点均为 **0**，无测试引用。它看起来像能力，实际是负债。

## 3. 依赖与边界（实测）

24 条显式边，按消费者列出：

```
ast      → comptime, gen, ir
backend  → gen, ir
builtin  → gen
check    → ast, gen
comptime → gen
lex      → gen
parse    → ast, comptime, gen, ir, lex
cmd      → ast, backend, builtin, check, comptime, gen, ir, lex, parse
```

判断：

- **无环**，方向是"数据向下、协调在上"，与设计意图一致。
- `ir` 零依赖、`backend` 不依赖 `ast`/`parse`/`comptime` —— 这是最值钱的一条边界，
  且被 `G()` 调用点为 0 佐证。
- `cmd` 依赖全部 9 个模块：它是唯一知道"整个系统怎么拼起来"的地方，这也是它
  无法被单独测试、无法被别的程序链接复用的根因。
- `parse → ir`、`ast → ir`：前端把 IR 类型当数据结构用。可接受（IR 零依赖），
  但意味着 **IR 模型不能反向依赖前端**，否则立刻成环。

## 5. 状态审计

`gen.G()` 调用点分布：`cmd` 174、`parse` 152、`comptime` 83、`ast` 31、`lex` 14、
`check` 5、`gen` 2、`builtin` 2、`ir` 0、`backend` 0。

模块级可变 `let` 分布：`cmd` 66（`module_build` 18、`link_inputs` 14、`toml` 11、

判断修正：上一版把"189 个全局"当作主要证据，其实**更强的证据是 463 个读取点**——
全局变量的数量可以靠合并减少，但 463 个"从任意深处直接取进程单例"的调用点，

意味着**语义分析目前无法在函数粒度上脱离进程状态运行**。

## 6. 缓存与增量：真实接线

实测调用链（不是文档承诺）：

```
build_scheduler.mb_schedule_modules
  → fork → mb_emit_indexed_module
      → firc_check_load(check_dir, &check_in)          // 函数级 check 缓存装载
      → checked_check_cache_begin(&check_in, check_env)
      → 逐文件 pass2（函数体检查，命中则复用受检切片）
      → checked_check_cache_capture / firc_check_commit
      → firc_load(firc_dir, &ir_in)                     // 函数级 IR 缓存装载
      → mb_llvm_emit_module(..., &ir_in, &ir_out, env_key, ...)
          → llvm_emit_module_to_cached(...)             // 共用发射管线
              → lower_module_cached(unit, ..., ir_in, ir_out, env_key)
              → backend.llvm_emit_module → 桥 → 原子发布
      → firc_commit(firc_dir, &ir_out)
```

结论：

- **函数级 check 缓存与 IR 缓存都已接线**，并在 `check_only` 与 `test_mode` 下
  主动关闭（避免检查变缓存报告、测试体与生产记录串用）——这个设计是对的。
- **未落地的是文件级对象**：LLVM 仍按模块整体发射一个 `.o`，所以单函数修改
  仍要重跑该模块的 LLVM 代码生成。这与 J2/LA4 的规划一致。
- **未落地的是线程池**：调度仍是 `fork` + `waitpid`（`build_scheduler.yh:59/246`），
  父进程持只读快照、子进程写时复制。这不是缺陷，是当前唯一正确的选择。
- 缓存键里混入了**编译器二进制自身的哈希**（`mb_mix_compiler_fingerprint` 对整个
  可执行文件做 FNV）。正确但昂贵：每次编译器重建都会全量失效，且首次构建要多读
  一遍二进制。属于可接受的设计，但应写进性能口径，别在 PF 报告里误判为"缓存没生效"。

## 7. 边界与健壮性审计（新增发现）

| 项 | 实测 | 风险 |
| --- | --- | --- |
| 字符串拼接 | `gen.append_str(buf, n, s)` **没有容量参数**，只在遇到 NUL 时停止；带容量的 `append_str_limit` 只用于诊断拼装 | 236 个固定栈缓冲（`[700]u8`×34、`[900]u8`×18、`[1200]u8`×12…）全靠调用方自觉；超长项目路径会**静默写坏栈** |
| 路径上限 | 未发现 `PATH_MAX` 常量、未发现"路径过长"诊断 | 深目录 + 长模块名组合可触发；错误表现为随机崩溃而非可读报错 |
| 嵌套深度 | `ast_expr_parse_depth` 是 CT 捕获语义计数器，**不是**递归上限；无 `max_depth` | 深层嵌套表达式/类型 → 栈溢出（信号 11），不是诊断 |
| 分配失败 | 293 个 `malloc` 调用点，随后 4 行内判空 236 个（80%），**57 个未判空** | 集中在 `test_cmd` 并行数组、`ssa_inline`（未接线）、`link_cache` 参数表 |
| 诊断 | 361 处 `gen.fail(...)`，统一出口（好），但**全部是自由文本，无错误码** | 无法稳定断言、无法被编辑器/CI 分类、文案改动即破坏快照 |
| 退出路径 | 代码中无 `exit()`/`abort()` 调用 | 好：错误统一经返回值 + 诊断，不搞进程级退出 |

这一组问题的共同点：**当前输入规模下不会暴露**。一旦面对"大型项目 / 生成代码 /
编辑器里未保存的半成品"，它们会以崩溃而不是诊断的形式出现。对 LSP 而言这是硬门槛。

## 8. 未接线与重复能力

| 项 | 规模 | 证据 | 判断 |
| --- | ---: | --- | --- |
| `ir/ssa_inline.yh` | 283 行 | `ir_inline_one`、`ir_inline_candidate_ok` 调用点 **0**，测试无引用 | 与 I4-5（`@[inline]` 无后端效果）同源；应删除或接线，不要继续维护 |
| `ir/ssa.yh::ir_simplify` | 217 行 | 调用点 **0** | 同上；NP1 已按 ADR-0014 退出生产路径 |
| `cmd/toml.yh` vs `libs/toml` | 604 行 vs 3,747 行 | 前者是 `project.toml` 的**刻意子集**（文件头写明"其余形态一律报错"），后者是完整 TOML 1.1 | **有意的临时重复**，迁移路径见 T6；不算缺陷，但同一格式存在两套语义，长期必须收敛 |

`ssa_inline` 与 `ir_simplify` 合计约 500 行：它们能被编译、能被静态检查、
却从不执行。这比"删掉的代码"更危险——它让人以为编译器有内联和化简能力。

## 10. 修订后的建议顺序

原顺序（契约 → 会话 → 拆分 → 增量 → 平台 → 生态）整体仍成立，但**插入一项、
调整一项**：

1. **A0 边界纪律（新增，最优先）**：给 `append_str` 系列加容量上界（或引入
   `buf` 结构携带 cap），把路径构造改为"失败即诊断"；给解析器加嵌套深度上限
   （复用现有 `ast_expr_depth_*` 计数器，超限报错而非崩溃）。理由：这是
   LSP/大型项目的前置，且改动局部、可用负例锁住。
2. **A1 契约版本化**（原 K1，不变）。
3. **A2 会话上下文**（原 K2）：先把 463 个 `G()` 读点**冻结**（只减不增），
   再按模块迁 `TaskCtx`。`parse` 的 152 个读点优先。
4. **A3 `cmd` → `cmd` + `build`**（原 K4）：先搬 `mb_link`（674 行，7 职责）
   与 `mb_compile_start`（292 行）到 `build/link`、`build/module`；再把
   `test_cmd` 从编译器二进制里拆出去（它是产品表面，不是编译器职责）。
5. **A4 删除未接线代码**（新增）：`ssa_inline.yh` 与 `ir_simplify` 二选一——
   接线（按 I4-5 让 `@[inline]` 真正生效）或删除。**不要保留第三种状态**。
6. **A5 前端装配收敛**：三处装配序列收敛为一个 `front_prepare(require_main,
   indexed)`，`driver`/`llvm_emit`/`module_worker` 只传参数。
7. 之后按原 M2（文件级对象 → 线程池）、M3、M4、M5。

顺序理由：A0 与 A4 是**减法**，风险最低、收益立刻可见（崩溃变诊断、代码变少）；
A1/A2 是加法但不可回避；A3/A5 是搬迁，必须排在 A1 之后，否则搬完又要再改一次。

## 附录：复现命令

```bash
# 规模
for d in compiler/*/; do m=$(basename "$d"); [ "$m" = tmp ] && continue
  echo "$m $(find "$d" -name '*.yh' | wc -l) $(find "$d" -name '*.yh' -print0 | xargs -0 cat | wc -l)"; done

# 固定缓冲
```
