# ADR-0001：yh 数组按值调用的互操作边界

- 状态：已接受（语义与互操作范围）；具体传递机制待 M0 实测后另立 ADR
- 日期：2026-09-27
- 对应计划：`docs/02-plan/yh-0.0.1-改造方案.md` 的 M0-03、M4-01

## 背景

yh 允许 `[N]T` 作为函数参数和返回类型。现有 TCC 的数组形参沿用 C 的指针
退化规则；`src/targets/arm64-gen.c` 的 `arm64_pcs_aux()` 也把 `VT_ARRAY`
按指针大小分类，不能由此推断 yh 数组已有按值调用语义。

0.0.1 需要先确定语言可观察的行为，再选择内部 ABI。用户已确定：数组按值
传递只要求发生在 yh 函数之间，不要求与 C 函数的数组调用 ABI 互操作。

## 决定

1. yh 函数接收 `[N]T` 参数时，函数体观察到独立的数组值；修改形参元素
   不改变调用方的数组元素。返回 `[N]T` 时，调用方得到独立的数组值。
2. 数组元素类型和长度共同决定参数、返回类型是否相容；透明 type 别名按
   其目标类型判断。内部表示可以降糖，但不得改变上述可观察行为。
3. 0.0.1 的数组按值调用仅适用于 yh 函数。内置 C 函数和外部 C 函数不接收
   yh 数组值；需要互操作时使用已有的指针等明确边界。未来若要求 C 接收
   数组值，应另作接口与 ABI 决策。
4. 切片 `[]T` 是含长度和数据地址的视图，不能因数组按值规则而被误认为
   元素副本；数组转切片的生命周期和转换规则由类型设计单独约束。

## 不在本 ADR 中决定的事项

- 内部调用采用「包装结构体」还是「调用点复制后传隐式指针」；M0 必须实测
  参数、返回和寄存器耗尽情形，再以新的 ADR 记录最终机制。
- 零长度数组是否合法、数组赋值的一般语义、切片是否做边界检查。
  这些问题不得由 ABI 探针的偶然行为代替语言决定。

## M0 探针与 M4 语言验收矩阵

M0 在 AArch64 Linux 上用 `tmp/abi/` 中的 C/结构体代理探针比较两个
候选机制，记录后端所需改动，并另立实现 ADR。代理探针只验证后端与调用
约定，不能证明 yh 语言行为；M4 必须用真实 `.yh` 调用用例逐项复验
下表，才能认定按值语义已实现。

| 场景 | 必须观察到的结果 |
| --- | --- |
| `[1]int`、`[4]int` 参数；形参修改元素 | 调用方原数组不变 |
| 数组返回值；返回局部数组 | 调用方得到正确元素，且不依赖已结束的被调用方栈帧 |
| 两个数组参数、嵌套调用、递归调用 | 每次调用的副本互不串写 |
| `[2]f64`、`[4]f32` 参数与返回 | 浮点元素正确；覆盖 HFA 分类和寄存器耗尽 |
| 多参数导致寄存器/栈切换 | 参数顺序、对齐、返回值正确 |
| 大数组及多大数组参数 | 不触发后端 `gfunc_call()` 的 `stack < 0x1000` 断言；若要设尺寸上限，须先写入语言规则并使编译器给出诊断 |
| 同型透明别名与不同长度数组 | 前者可调用，后者在编译期拒绝 |

比较两种候选机制时，记录：调用方和被调用方各自负责的拷贝、返回值存放
位置、别名关系、对齐、代码改动范围，以及与 AArch64 后端现有 HFA/栈路径
的冲突。未通过验证门前，不得在计划中宣称「数组直接复用现有 ABI」或
「arm64 后端无需修改」。

## 后果

- 可以选择最简单、可验证的 yh 内部表示，不必模拟 C 数组形参退化。
- 每个调用边界可能产生数组复制；性能评估晚于正确性验收。
- 跨语言 ABI 不在 0.0.1 的承诺内，后续互操作需要显式适配设计。
