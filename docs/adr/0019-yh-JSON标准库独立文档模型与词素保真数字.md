# ADR-0019：yh JSON 标准库采用独立文档模型与词素保真数字

日期：2026-10-24。状态：**接受并实施首期**（J1–J3、J6；一致性语料与
注入门待做，见 todo）。
设计见[完整设计](../03-design/yh-JSON标准库设计-2026-10-24.md)，
分期见[实施方案](../02-plan/yh-JSON标准库实施方案-2026-10-24.md)。

## 背景

标准库已有 `toml`（完整 TOML 1.1 reader，681/681 语料、124 个注入点）
与 `string`（拥有者 + UTF-8）。JSON 的需求来自另一侧：工具链输出（代码统计、
性能报告、IaC `--json`、发布清单）目前全是 Python，`toml-test` 桥还在手写
JSON 文本。要迁回 yh，先要有 JSON 读写库。

三个问题必须一次定清，否则后面返工：

1. 值树要不要和 `toml` 共用一个公共 DOM 模块？
2. JSON 的 number 是存词素还是分类成 i64/f64？
3. 先做 reader 还是先做 writer？

## 备选

**问题 1（DOM）**

1. 抽 `libs/value` 公共 DOM，`toml` 与 `json` 都建在上面。
2. 各自独立文档模型，只共用十进制 ↔ binary64 转换（`libs/num`）。
3. `json` 直接复用 `toml` 的 Document（跨格式依赖）。

**问题 2（数字）**

1. 照 `toml` 二分 `kind_integer`/`kind_float`，解析期就定型。
2. 一律 f64。
3. 单一 `kind_number` + 原样保存词素，取值时用 `as_i64`/`as_f64`/`is_integer` 询问。

**问题 3（顺序）**

1. reader 先行（对齐 `toml` 的「读优先、写后置」）。
2. writer 先行。
3. 一次交付读写。

## 提议

- **问题 1 选 2**：`json` 自带私有池与只读句柄，API 形状对齐 `toml`；
  把 `toml/numbers.yh` 的精确十进制转换抽成 `libs/num`，两个格式共用。
- **问题 2 选 3**：只校验 grammar、原样保存词素；`as_i64` 要求整数形式且
  在范围内，`as_f64` 走精确转换、上溢报范围错误而不返回 ±inf；写出时词素
  原样输出，浮点值输出最短往返十进制。
- **问题 3 选 2**：J1 先交 writer（约 500 行，直接替掉 `toml-test` 桥的手写
  输出），J3 再做 reader。
- 严格性 profile 固定：拒绝 BOM、重复键、孤立代理、尾逗号、尾随内容；
  不做 JSON5/JSONC，不提供宽松 `Options`（无消费者）。
- 不改 `docs/yh.g4`，不改编译器；首期不引入自举风险。

## 理由

**DOM 不共用**：抽取公共 DOM 要重写已验收的 `toml` 存储层（444 行池 + 表定义
状态），收益是省一份同类代码；风险是把 681/681 语料与 124 个注入点的既有
证据作废。第二个格式刚出现，正属于「无消费者不建框架」的边界。等第三个格式
（YAML/MessagePack）出现再抽，届时两份实现就是现成的规格。

**数字共用 `num`**：与 DOM 相反，这条有**两处真实消费者**且算法复杂
（正确舍入、次正规、长尾数）。复制必然发散，而 `toml` 已有 1437 组随机/边界
值 + 400 组中点的位模式差分，是现成的回归网。抽取不改算法，只搬位置。

**词素保真**：JSON 规范只有一个 number 类型，`1`、`1.0`、`1e2` 语义相同。
解析期二分类型等于凭空造一个规范没有的区分，并会让 `1.0` 往返成 `1`；
一律 f64 则把 `9007199254740993` 这类超过 2^53 的 ID 静默改值。存词素同时
解决往返保真与超范围值（`1e400` 可解析、`as_f64` 报范围错）。

**writer 先行**：现有消费者全是**生产者**（工具输出 JSON），读入口还没有
真实调用方；writer 也更小、更容易先落地验证 `string` 依赖与 builder 状态机。

## 后果与权衡

- 两份值树存储有重复：`json` 约 400 行池/节点，`toml` 已有同类代码。
  代价是重复，收益是互不影响；`json` 无表定义状态，实际比 `toml` 简单。
- 词素保真意味着同一数值有多种文本表示，`json` 的相等比较必须按语义或按
  位模式，不能按文本；README 必须写明，测试要覆盖 `1`/`1.0`/`1e0` 三种输入。
- `1e400` 能解析但 `as_f64` 失败，与 `toml`「越界即解析失败」不一致。这是
  按各自规范语义实现的结果，不是疏漏；文档需并列说明。
- 拒绝重复键与 ECMAScript `JSON.parse` 的 last-wins 不同，读第三方脏数据会
  失败。这是有意选择（避免静默丢字段），宽松模式留给未来的独立切片。
- `libs/num` 抽取会改到已验收代码，属本方案最大单点风险；以 toml 一致性门
  与注入门作阻断，一天内定位不到根因就回退为「`json` 内复制一份」。

## 验证与关联

- 一致性：固定 JSONTestSuite 提交，`y_` 全接受、`n_` 全拒绝、`i_` 逐条登记。
- 差分：Python `json` 比值树；浮点比位模式（不比字符串，避免指数格式差异）。
- 回归：`make test-toml-conformance` 681/681 与 `make test-toml-injection`
  在 J2 后必须保持；`make test` / `make selfhost-native` 保持绿。
