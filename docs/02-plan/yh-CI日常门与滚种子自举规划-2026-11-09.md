# yh CI 日常门、滚种子与自举规划（2026-11-09）

一句话：**日常循环靠 `just` 分层命令，CI 是四端托管 runner 的唯一权威；可分发种子只由
tag Release 产生，本地 `just seed` 只是本机预检；自举链（seed → cc2 → cc3 → cc4，双代固定点）
已经成立，缺的是「新机一条命令」与「合入门槛」两个决定。**

本文只做规划与取舍，未改任何代码或 workflow。落地项见文末清单，已同步到
[`../todo.md`](../todo.md)。

## 1 现状（2026-11-09 实测口径）

### 1.1 CI（`.github/workflows/ci.yml`）

| 项 | 现状 |
| --- | --- |
| 触发 | push/PR 到 `llvm`（`main`/`arm64` 为遗留分支），另可手动 dispatch |
| 并发 | 同分支 push/PR 共组，`cancel-in-progress` |
| 矩阵 | `linux-x64`（ubuntu-24.04）、`linux-arm64`（ubuntu-24.04-arm）、`darwin-arm64`（macos-15）、`windows-x64`（windows-2022） |

| 闭包 | Linux 用 `vendor/llvm` 预编译 deb；Darwin/Windows 源码构建 + `actions/cache`（与 release.yml 同 key，可互命中） |
| 实测耗时 | run `42507415505`（HEAD `6614864`，四端全绿）：总 17m42s；linux-x64 11m56s、linux-arm64 10m52s、darwin-arm64 9m39s、windows-x64 17m37s |

### 1.2 种子与自举

| 项 | 现状 |
| --- | --- |
| 种子存放 | `bin/yh-<平台>-<架构>`，**被 `.gitignore` 忽略**，不入库（2026-10-21 起，无 LFS） |
| 分发通道 | **只有 tag Release**：`release.yml` 四端「取上一版种子 → 冷编 → 平台门 → 自举门 → 取 cc4 打包」 |
| 取种规则 | 最新带该平台资产的 Release；排除当前 tag；忽略 draft 与 `seed-*` |
| 版本链 | rc.N 用 rc.N−1；正式版用该版最后一个 rc；正式 tag 必须落在 `llvm` |
| 当前代际 | 最新 Release `0.0.12`（2026-11-05），HEAD 距该 tag **83 个提交** |
| 本地 `just seed` | 只覆盖本机 `bin/` + 写 `.sha256`；拒绝带构建机 `$HOME` 路径的种子（`seed_path_warnings`） |
| 自举链 | seed → cc2 → cc3 → cc4（三冷编）；cc3/cc4 的 `asm/iface` 逐字节一致；cc2→cc3 允许迁移差异（只打印）；cc4 自解析 178 文件 + 语料；发布取 cc4 |
| 首次/换机 | 文档要求 `just fetch-seed` → `just bootstrap`（两步）；`just bootstrap` 本身**不取种子** |

## 2 日常循环：分层命令与判据

目标：**编辑循环秒级，提交前分钟级，自举敏感改动十几分钟，CI 十几分钟**；每一层都有
明确判据，不靠感觉。

| 层 | 命令 | 何时跑 | 判据 |
| --- | --- | --- | --- |
| 编辑循环 | `just dev`（增量） | 每次改代码 | 编译通过；缓存命中，不删 `.build` |
| 语法/前端快检 | `just quick` | 改 `parse`/`lex`/`check` 语法面时，随时 | ANTLR + `--syntax-check` 全过（约 20s） |
| 提交前 | `just build` + `just test` | 每次提交前（AGENTS 硬要求） | 冷编通过；三层回归全绿（本地含 ANTLR） |
| 自举敏感 | `just selfhost-native` | 改 `parse`/`check`/`build`/`link`/`comptime`/缓存键/种子相关 | 双代固定点一致 + cc4 自解析 + 语料 + 项目验收 |
| 发布前 | `just full` → `just seed` | 改版本号、打 tag 前 | `test` + `selfhost-native` 全绿后才滚本机种子 |
| 远端 | 等 CI 四端 | 每次 push | 四端绿；红则就地修，不叠加提交 |

两条纪律（有实测代价）：

1. **同一 worktree 不并发跑构建**。2026-11-08 出现 `yh-link.s.ct.session-<pid>` 打不开，
   两个会话同时在一个工作区构建会互相踩 `.build`。
2. **CI 红时不发 tag、不滚种子**。CI 的 `cancel-in-progress` 会让新 push 吞掉上一轮证据，
   红的时候先停下来修，不要用下一次 push「顺手看看」。

## 3 CI 规划

### 3.1 不新增 nightly 全量门

push/PR 已经覆盖每个提交，四端 10–18 分钟出结果；再加一轮每日四端全量门，成本
（4×~18min + macOS 排队）换不到新信息。**「每日」只保留 `perf.yml`**，并把它修成可信信号
（P0）。若担心新机 onboarding 腐化，用一条**每周一次、只有 linux-x64** 的
「空 `bin/` → `just bootstrap` → `just quick`」冒烟，不动四端矩阵（P2，可选）。

### 3.2 门禁口径统一（P1，建议做）

现状：Linux/Darwin 手工列语料步骤，Windows 跑 `just test`。这带来一个真实的漂移风险：
**以后往 `just test` 里加的门，只会在 Windows 上进入 CI**，本地绿/CI 绿的口径越走越远。

建议四端统一为：

```
YH_ANTLR=0 just test                    # 与本地同一真源；ANTLR 层留给本地（无 Java 依赖）
<平台专项门>                            # test-llvm-linux-arm64 / test-llvm-darwin / windows
just SEED=... SKIP_CORPUS=1 selfhost-native
```

- `YH_ANTLR=0` 是必须的：ANTLR 参考层要 Java + 本机 antlr4 运行时
  （`tests/yh/check.py` 里写死托管 venv），CI 从未装过；显式关掉才与现状等价。
- 代价：估计 Linux/Darwin 各多 2–4 分钟（build-cache、opt-level、fmt、global-cache、
  code-stats、arch-check），换「新增测试自动进 CI」。
- 验收：四端仍绿；在分支上故意改坏 `tests/yh-run` 一例，四端都必须红（验完立刻回滚）。

**2026-11-09 已落地**（本机 darwin-arm64 已验证，四端待下一次 CI 实跑）：

- justfile 新增 `ci-gate`（`test` → `platform_gate` → 自举 `SKIP_CORPUS=1`）与
  `release-asset`（cc4 冒烟 + tar + sha256）；`platform_gate` 按宿主分派：
  Linux/x64 → `test-llvm`、Linux/AArch64 → Windows 目标编译侧、Darwin →
  `test-llvm-darwin`、Windows → 语料交叉编译 + 本机执行。
- `ci.yml` 与 `release.yml` 的 8 个平台 job 都只调这两条配方：分支门 `just ci-gate`，
  发布 `KEEP=1 just ci-gate` + `just release-asset "$TAG" <资产平台名>`。四份 cc4
  打包脚本（各约 29 行）与两套门禁清单合成一份。
- 顺带修掉两处漂移：release 的 Windows runner pin 由 `windows-latest` 改为
  `windows-2022`（与 ci 一致，VS 18 下闭包 CMake 生成器找不到实例）；release 的
  artifact 路径改用 prepare 输出的 tag（原先用 `github.ref_name`，`workflow_dispatch`
  演练时上传会找不到文件）。
- 本机实测：`KEEP=1 just ci-gate` 全绿（test 三层 + `test-llvm-darwin` + 自举：
  固定点一致、cc4 自解析 180 文件、project cases 129/129）；
  `just release-asset 0.0.14-test darwin-arm64` 产出单成员 `yh` 的包，
  `shasum -a 256 -c` 通过，解包后 `./yh --version` = `yh 0.0.13`。

### 3.3 合入门槛：两个选项，默认 A

| 选项 | 做法 | 代价 | 结论 |
| --- | --- | --- | --- |
| A（默认） | 保持直推 `llvm`；CI 红就修；纪律见 §2 | CI 不是硬门，依赖人 | **推荐**：单人主线 + 四端 18 分钟内出结果，PR 流程收益低 |
| B | 分支保护 + required status checks | Windows 闭包冷启动 1–3h 会卡主线；若只 required `linux-x64`，其余仍靠人 | 需要时再开；先只 required `linux-x64`，Darwin/Windows 作 advisory |

不变的一点：**tag 不因为 CI 而放行或拦截**——`release.yml` 会在 tag 提交上重新四端冷编并跑
全门，坏提交不会成为种子，最多浪费一次构建。所以 A 的风险可控。

### 3.4 维护项

- `actions/checkout@v4`、`extractions/setup-just@v2` 已被强制跑在 Node 24 上，每次运行都出
  弃用注解；升级动作版本（P2，低风险）。
- `windows-2022` 是 pin：`windows-latest`（VS 18）没有「Visual Studio 17 2022」实例，闭包
  CMake 生成器写死会找不到；长期方案是生成器动态检测（已登记 todo）。
- `ubuntu-24.04` 也是 pin：`ubuntu-latest` 已滚到 26.04，libxml2 SONAME 与 gcc15/gnu23 会让
  种子与 C ABI 用例红。不要改回 `-latest`。

## 4 滚种子规划

### 4.1 链路定位（别混）

```
本机 bin/ 种子（ignored）  ← just seed（只影响本机，不共享）
        ↓ 只用于本机构建/预检
tag Release（唯一分发）    ← release.yml：四端冷编 + 全门 + selfhost → cc4 → tar.gz
        ↓ fetch-release-seed.py（CI、release、开发者机器同一规则）
下一轮构建的种子
```

推论：**「滚种子」在仓库层面 = 发 Release**；`just seed` 只改本机文件，不能当团队种子。
`seed-*` 里程碑 Release 已被 `fetch-release-seed.py` 排除，不要复活。

### 4.2 节奏（当前最该决定的事）

种子代际决定 CI 每天在验证什么：种子越旧，「上一版编译器能编当前源码」这个不变量的
覆盖面越窄（旧种子不认识后来新增的语法面，等于每天只验证一个陈旧的向后兼容点）。
当前 `0.0.12` 距 HEAD **83 个提交、4 天**，已经偏大。

建议：**每完成一个可交付切片就发 rc，不攒大版本**（S3a/S3b/S3c、标准库一期、LLVM 目标面
变化各算一个）；硬上限约 **30 个提交或 2 周**，超了就发 rc 重置代际。

第一件事：发 `0.0.13-rc.1`（版本号两处 + `docs/01-finished/release-0.0.13-rc.1.md`），
其后 rc.2 用 rc.1 编译，形成链。

### 4.3 种子规则（已实现，不要改）

- rc.N 用 rc.N−1；正式版用该版最后一个 rc；正式 tag 必须在 `llvm` 上。
- 版本号两处（`compiler/project.toml`、`cmdline.yh` 的 `YH_VERSION_TEXT`）必须与 tag 一致。
- 四端资产成员必须是单个 `yh`；发布前 `sha256sum -c` 校验；发布说明缺失即失败。
- 发布后用发布物验收：`rm -rf bin && just fetch-seed` → `just` → `just test` →
  `just selfhost-native`。

## 5 自举规划

### 5.1 首次/换机：把「一条命令」补成真的（P0）

现状 `just bootstrap: llvm-host _ensure_built`：先准备闭包，再冷编。但冷编会先
`verify-seed` 检查 `bin/` 种子——新机没有种子，于是会**先花 1–3 小时源码构建闭包，再失败**。
AGENTS 写的「首次/换机一条命令」与事实不符。

两种修法：

| 方案 | 改动 | 验收 |
| --- | --- | --- |
| (a) 推荐 | `bootstrap` 前置取种：种子缺失（或哈希不符）时才 `fetch-seed`，已有则跳过 | 空 `bin/` 下 `just bootstrap` 一次成功；第二次构建不发网络请求（看 `fetch-release-seed.py` 输出） |
| (b) | 不改配方，改 AGENTS/README 口径为「两步」 | 文档与 `just --dry-run bootstrap` 的顺序一致 |

(a) 的边界：`fetch-release-seed.py` 已有离线 fallback（找不到 Release 且种子已存在时退回），
但**默认每次都会请求 API**；需要加「已存在且哈希匹配则跳过」的短路，否则 `bootstrap`
每次联网。这是唯一需要动代码的地方（几十行内）。

### 5.2 自举链判据（已成立，别加门）

- 三代冷编：seed → cc2 → cc3 → cc4，前端每代都冷编，不复用缓存。
- 固定点：cc3/cc4 的 `asm/`、`iface/` 逐字节一致；cc2→cc3 允许差异（种子迁移代，只打印）。
- cc4 自解析（178 文件，每文件一次进程）+ 语法/运行语料 + 固定点探针 + CLI 冒烟。
- 发布取 cc4 打包，并在包里做 `--syntax-check` 冒烟（防 rc.4 那种「打包出旧二进制」）。

### 5.3 闭包与环境风险

| 风险 | 现状 | 处置 |
| --- | --- | --- |
| 闭包冷启动 | Darwin 首次 1–2h、Windows 2–3h；靠 `actions/cache` | 缓存 key 与 release.yml 一致（同存储互命中）；cache key 不承担正确性，`just llvm-host` 的身份 check 判失效 |
| Windows 缓存易失效 | key 含 `compiler/project.toml` | 改项目清单会触发重建；大改前留意 |
| 宿主系统漂移 | ubuntu/macOS/windows 都 pin 了具体镜像 | 升级镜像要单独验证（26.04 已踩过） |
| 种子代际漂移 | 83 commits | 用 §4.2 的 rc 节奏控制 |

## 7 明确不做

- 不新增 nightly 四端全量门；`perf.yml` 保持「只测量、不设硬门」。
- 不复活 `seed-*` 里程碑 Release；不把种子入库、不引入 LFS。
- 不改自举链（三代冷编 + 双代固定点已经够，加门只增成本）。
- 不为了「CI 看着更全」在四端重复跑同一门；统一到 `just test` 之后再谈专项。
