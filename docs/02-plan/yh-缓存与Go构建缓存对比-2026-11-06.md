# yh 缓存与 Go 构建缓存对比

日期：2026-11-06
状态：**分析/建议，未实施**。当前 yh 缓存实现见
[缓存设计](../03-design/yh-缓存设计.md)；目标架构见
[架构设计](../03-design/yh-架构设计.md) 与 `docs/todo.md` 的 S0–S6。

---

## 0. 对比对象

这里对比的是 **Go 的构建缓存**（`cmd/go` 的 `GOCACHE` / action cache），
不是 Go runtime 的 GC 缓存。

Go 的模型：

```text
ActionID = SHA-256(一次构建动作的全部输入)
OutputID = SHA-256(输出内容)

GOCACHE/
  actions/<ActionID>   -> OutputID
  outputs/<OutputID>   -> 文件内容
```

特点：

- 全局 `GOCACHE`，跨项目/跨 worktree 共享；
- action 命中直接跳过整个 compile/link/test 动作；
- 工具链身份、目标、编译参数、环境、输入内容都进键；
- 输出内容寻址，可去重；
- 测试结果单独缓存；
- `go clean -cache`、trim、`GOCACHEPROG`、`GODEBUG=gocachehash/gocacheverify`。

yh 当前模型：

```text
模块接口/对象缓存  → 命中跳过整个 module worker
函数 check 切片    → 命中跳过函数体解析/检查
函数 IR            → 命中跳过 lowering
链接缓存           → 命中跳过 lld
InterfaceReady     → 调度就绪标记
```

四层缓存的键、manifest、提交各实现一份，缓存目录按项目/目标隔离。

## 1. 总对照

| 维度 | Go build cache | yh 当前 | 评价 |
|---|---|---|---|
| 缓存模型 | ActionID → OutputID + 内容存储 | 模块 manifest / 函数键 / 链接 manifest 各自实现 | yh 更分散 |
| 哈希宽度 | SHA-256（32 字节） | FNV-1a 64-bit（16 hex） | **yh 碰撞风险高** |
| 工具身份 | 工具内容/build ID | 编译器二进制 `(size, mtime)` | **yh 可被 mtime 欺骗** |
| 缓存范围 | 全局 `GOCACHE` | 项目 `.build/targets/...` | yh 跨项目/worktree 复用差 |
| 输出存储 | 内容寻址，按 OutputID 去重 | 按模块 tag 命名，manifest 存摘要 | yh 无法自然去重 |
| 缓存粒度 | 包/action（compile/link/test） | 模块 + 函数 check/IR + 链接 | yh 函数级更细，但后端未受益 |
| 命中效果 | 跳过整个 action | 模块命中跳过 worker；函数命中只跳 lowering | yh 函数缓存收益被整模块 LLVM 吃掉 |
| 路径处理 | 支持 `-trimpath`，跨目录复用 | 函数键混入源路径 | yh 换目录/克隆后失效 |
| 环境输入 | 记录影响构建的环境 | 部分 target/opt/legacy，环境审计不完整 | yh 有错误命中风险 |
| 键计算 | 一处 action ID 生成 | check 键与 IR 键两套重复逻辑 | yh 容易分叉 |
| 验证 | 默认信任，`gocacheverify` 可校验 | 命中校验对象/接口摘要与架构 | yh 更保守，但哈希成本高 |
| 并发 | 文件锁 + 原子 action entry | session 接口隔离；manifest 最后写者赢 | yh 同项目并发不安全 |
| 清理 | `go clean -cache`、trim | `firc_recycle_old` 只回收旧键 | yh 会累积旧 target/孤儿文件 |
| 测试缓存 | 成功测试结果缓存 | 只缓存测试构建，不缓存结果 | yh 测试重复执行 |
| 远程缓存 | `GOCACHEPROG` | 无 | yh CI 共享能力弱 |
| 调试 | `gocachehash`/`gocacheverify`/`-x` | `--stats` 只有计数/耗时 | yh 难定位 miss 原因 |

## 2. yh 做得比 Go 好的地方

不要为了“像 Go”把这些丢掉：

1. **函数级 check/IR 缓存**
   Go 是包/action 级，没有函数级；yh 能在单函数改动时复用其他函数的 check
   切片和 IR。方向正确，只是后端对象粒度还没跟上。

2. **InterfaceReady 提前发布**
   yh 在函数体 pass2b 之前发布 `.s.i/.s.ct/.ready`，消费者可提前开始。Go 的包
   action 通常要等整个包编译完成。这是 yh 的调度优势。

3. **manifest + 内容摘要 + 架构校验**
   yh 模块命中校验对象/接口摘要和机器架构；链接产物校验 ELF/Mach-O/PE。
   Go 默认信任本地 cache，需要 `gocacheverify` 才逐字节校验。yh 更保守。

4. **check/test 隔离**
   `yh check` 不读写正式缓存；`yh test` 用 `tmp/yh-test`，不装载/提交函数
   缓存。隔离比 Go 的 build/test cache 更显式。

5. **目标/自举身份显式**
   yh 的键包含 target/ABI/bridge/selfhost 闭包；Go 的 GOOS/GOARCH/CGO 也明确，
   两者方向一致。

## 3. 可优化项（按优先级）

### P0：键的正确性

#### 3.1 64-bit FNV → 128/256-bit 内容哈希

当前：

- 函数键：16 hex = 64-bit FNV；
- 模块 manifest 的对象/接口摘要：64-bit；
- 链接键/产物摘要：64-bit。

Go：ActionID/OutputID 都是 SHA-256。

64-bit 在缓存规模变大、CI 共享、对抗性输入下碰撞风险不可忽视。缓存错误命中
会静默产出错误对象。

建议：

- 至少 128-bit；共享/远程缓存用 SHA-256；
- 如果自举源码暂不便实现 SHA-256，可先用 128-bit 非加密哈希，长期换 SHA-256；
- 键宽变化要 bump `CHECKED_SLICE_VERSION`、`IR_FUNCTION_CACHE_VERSION`、
  模块缓存 tag、link manifest 版本，做一次性失效。

#### 3.2 编译器/工具身份不要用 size/mtime

`mb_mix_compiler_fingerprint` 当前按 `(size, mtime_ns)` 取编译器身份。Go 用工具
内容/build ID。mtime 可被 `touch`、复制、容器层缓存欺骗。

建议：

- 用编译器二进制内容哈希或 release build ID；
- 只算一次，缓存到 sidecar/构建会话，不要每模块重哈希 70 MB；
- 同样审计 lld、bridge、SDK 的身份。

#### 3.3 路径与环境输入显式化

yh 函数键混入源路径；Go 支持 `-trimpath`，让同一源码在不同目录/克隆复用缓存。

建议：

- 把“语义键”和“位置映射”分开：函数体/类型/签名/常量进键，绝对路径不进；
- 诊断位置单独存 locs，命中后按当前路径重建；
- 提供 `--trimpath`/相对路径模式；
- 把影响构建的环境收敛为显式 `CacheInputs` 白名单（`YH_*`、SDK、selfhost
  flags），不要读隐式环境。

#### 3.4 统一键计算

当前 `ast/module_snapshot_check_key.yh` 与
`lower/module_snapshot_lower_cache.yh` 有两套相似键逻辑。Go 的 action ID 在一处
生成。

建议：

- 抽 `cache/key` 公共模块，定义 canonical action description；
- check/IR 键共享同一序列，避免一侧改了另一侧没改；
- 给每个键加 schema 版本。

### P1：缓存模型与粒度

#### 3.5 全局 action cache + content store

Go：

```text
GOCACHE/actions/<ActionID>  -> OutputID
GOCACHE/outputs/<OutputID>  -> bytes
```

yh：

```text
项目/.build/targets/.../manifest/<tag>.manifest
项目/.build/targets/.../obj/<tag>.o
```

yh 缓存按项目/目标隔离，同类对象在不同 worktree/项目不能复用，磁盘重复。

建议：

```text
YH_CACHE/
  actions/<actionID>       # 输出 ID 列表 + 元数据
  outputs/<outputID>       # 对象/接口/二进制内容
```

项目 `.build` 只保留“项目 → actionID/outputID”的索引，或者用硬链接/复制把产物
放回项目路径。这样跨 worktree、CI、多个项目都能共享内容。

注意：模块对象含模块 tag/符号后缀，去重不会 100%；相同 action 的重复构建仍受益。

#### 3.6 文件级对象优先于函数级对象

当前函数 IR 缓存命中只跳过 lowering；`backend.llvm_emit_module` 仍对整模块生成
LLVM 文本。Go 的 action cache 是包级，命中直接跳过整个 compile action。

建议：

- 先做**文件级对象**（每个 `.yh` 一个 `.o`），而不是函数级 `.o`；
- 文件级对象让单文件改动只重发该文件 LLVM，链接复用其余对象；
- 函数级 `.o` 会产生大量桥调用（编译器自身约 1460 个函数），固定开销可能抵消
  收益；
- 函数 check/IR 缓存保留，但目标是减少前端/lowering；后端靠文件对象。

这与架构设计 §4.6 的方案 A/B 一致：文件级对象是更稳的中间粒度。

#### 3.7 缓存清理、锁、可观测性

Go 有 `go clean -cache`、trim、文件锁、`gocachehash`/`gocacheverify`。

yh 目前：

- 没有全局 GC；`.build/targets/<旧 triple/O>` 会累积；
- `firc_recycle_old` 只回收旧索引里的记录，孤儿文件不枚举；
- 同项目并发构建靠 session 后缀隔离接口，但 module/link manifest 最后写者赢；
- `--stats` 只有命中计数，没有 miss 原因/action ID。

建议：

- `yh clean --cache`/`yh cache trim`，按大小/年龄清理；
- 每个 action 的提交加文件锁或原子 action entry；
- `YH_CACHE_DEBUG=1` 输出 action ID、键组成、miss 原因；
- `YH_CACHE_VERIFY=1` 做逐字节校验。

### P2：测试与共享缓存

#### 3.8 测试结果缓存

Go 的 `go test` 缓存成功测试结果（`(cached)`），跟踪测试二进制、参数、环境、
文件访问。yh 目前只缓存测试构建，不缓存测试结果。

建议：

- 不盲抄。测试可能有副作用；
- 如果做，只缓存成功用例，跟踪 env/文件访问，提供 `--count=1`/
  `--no-test-cache`；
- 先做“纯测试”/显式 opt-in，避免语义语料被缓存掩盖。

#### 3.9 远程/共享缓存

Go 提供 `GOCACHEPROG` 外部缓存程序。yh 可以做 `YH_CACHEPROG` 或 HTTP 后端，
用于 CI 共享。前提：

- 键/内容哈希足够强；
- 有校验/签名；
- 不把自举闭包/种子路径烘焙进缓存；
- 有清理和权限策略。

建议后置，不要先做。

## 4. 建议的目标缓存模型

```text
ActionID = H(
  schema_version,
  tool_id,                 # 编译器/lld/bridge 内容身份
  target triple/data_layout/ABI,
  opt/flags,
  env_whitelist,
  input OutputIDs          # 源码/接口/依赖/对象
)

OutputID = H(output bytes)
```

三层映射：

```text
ModuleAction   -> { object, s.i, s.ct } OutputIDs
FunctionAction -> { fchk, fir } OutputIDs
LinkAction     -> executable OutputID
```

存储：

```text
YH_CACHE/
  actions/<actionID>       # output ID 列表、版本、依赖 action
  outputs/<outputID>       # 内容
  trim/                    # 清理策略
```

项目 `.build` 只保留：

```text
targets/<triple>/llvm/O<opt>/
  index/<module>           # module -> actionID
  ...
```

这与 Go 的 action cache + content store 对齐，同时保留 yh 的函数级 check/IR
缓存。

## 5. 不建议照搬 Go 的点

1. **不要退化成纯包级缓存**
   yh 的函数级 check/IR 缓存是优势，只是要被后端对象粒度配合。不要因为 Go 是
   包级就删掉。

2. **不要盲目缓存测试结果**
   Go 的 test cache 有成熟的环境/文件跟踪，yh 目前没有；测试副作用风险更高。

3. **不要直接照抄 `GOCACHE` 布局**
   yh 的模块接口/CT/自举闭包/target 身份不同；借 action/content 模型，不要照抄
   目录。

4. **不要为了全局缓存牺牲自举可重现性**
   全局缓存必须可校验、可清理、可拒绝版本；不能把构建机路径/闭包隐式带进内容。

---

## 6. 建议的第一步

按投入产出排序：

1. **缓存键审计**：列出每个键的输入，补 env/工具身份，去掉绝对路径依赖。
2. **哈希升级**：FNV64 → 128/256-bit；一次性 bump 缓存版本。
3. **抽 `cache_context`**：统一键、manifest、原子提交、统计；check/IR 键共享序列。
4. **全局 content store**：先做项目内 `actions/` + `outputs/`，再扩到 `YH_CACHE`。
5. **文件级对象**：比函数级 `.o` 更稳，直接减少 LLVM 整模块重发。
6. **清理/锁/调试**：`yh clean --cache`、`YH_CACHE_DEBUG`、并发锁。
7. **测试结果/远程缓存**：最后做，且 opt-in。

---

## 7. 结论

Go 的缓存强在“action ID + 内容寻址 + 全局共享 + 清理/锁/调试”这套基础设施；
yh 强在函数级粒度和 InterfaceReady。

yh 最该补的不是“更多函数缓存”，而是：

- 键的正确性（哈希宽度、工具身份、环境/路径）；
- 全局内容存储与去重；
- 后端对象粒度（文件级优先）；
- 缓存的可运维性（清理、锁、调试、校验）。

一句话：**借 Go 的 action/content 模型补基础设施，保留 yh 的函数级缓存和提前
发布优势；不要照抄 Go 的包级粒度。**
