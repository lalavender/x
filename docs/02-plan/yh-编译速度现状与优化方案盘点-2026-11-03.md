### 2.3 O2（次要但方向相反）

O2 冷编 30.69 s（O0 的 2.95×），**内嵌桥占 73.5%**；单函数 O2 **7.55 s**，

但发布/CI 用 O2，**桥侧优化（SP3/SP4/SP5）在 O2 上收益最大**。

## 4. 几个需要说清的判断（避免用乐观数字排期）

1. **SP3/SP4 在默认（O0）构建上收益有限**：路线给的是 −5~15%，但那是按「桥占大头」估的；
   实测 O0 冷编桥只占 **8.4%**（PF2:28）。真正吃这两项的是 **O2**（桥 73.5%）和 Windows（桥 73–90%）。
   两项仍值得做——成本是两行 C，收益在 O2/Windows 上是被放大的。
2. **并发不是当前瓶颈**：13–16 个模块、缺省 4 worker 已到 2.79× 有效并发；
   PF3 的 8 worker 只 2.43× 且 worker 累计工作量 +58%（争用）。要真吃到 16 核，
   必须先有**比模块更细的调度单位**；该方向已暂缓（ADR-0020），`-j` 只作为受限优化。
3. **单函数 3.9 s 不是调参能解决的**：构成是链接 1.17 + 对象 0.52 + 模块重编 2.03，
   其中 2.03 s 是「LLVM 为 205 个函数重发整模块 `.o`」。**≤3 s 不再承诺**；C1 已暂缓。
4. **全量重编 17.5 s 的对手是 capture**：记录 25.1 KB/条、75 类型/条，13.7 ms/条。
   C3（共享类型池）是唯一把这个量级打下去的结构性改动；C2 削的是 I/O 次数。
5. **热编已接近地板**：1.00 s 里 object 0.4–0.5 + link 0.27 + project 0.16，
   剩下能挤的只有摘要复用（B6）和链接（C6），量级 0.2–0.4 s。

## 5. 建议顺序

**第 0 步（决定项）**：确认主平台。若日常在 Windows 原生开发，
先做 **B8（桥专项定位）**——它决定了其他所有优化在 Windows 上是否被桥吃掉；
若以 Linux/容器为主，直接进第 1 步。

1. **B4 SP12 默认增量**（1 行 + AGENTS.md 一句话，需拍板）：日常回路 11 s → 1–4 s。
2. **B5 `-j`**：只加参数、缺省 `min(核数, 模块数)`，不做默认放开（PF3 已证 8 worker 无益）。
3. **B1+B2+B3 合并一次验证**（bridge 两处 + `.fchk` 冷编门）：当天可测冷编变化；
   门禁 `just test` + `just selfhost-native`，产物 `.o` 逐字节比对。
4. **B6 源/接口摘要复用**：热编/单函数各再省 0.2–0.4 s。
5. **B8 → B7**（仅 Windows）：先定位桥的 82 s，再上并行进程池。
6. **C1 PC7 函数级 `.o`（⏸ 暂缓）**：2026-11-06 决定对象粒度停在模块级（ADR-0020），
   单函数 ≤3 s 不再承诺；先做函数缓存/键收口，不推进更细对象。
7. **C3 PC2d → C2 SP7**：全量重编 17.5 → ~9–11 s。
8. **C5 SP8/SP9 → C4 SP5 → C6**：冷编本体收尾（合计目标 5–6 s）。
9. **D1 LA5**（顺带解决 Windows 无 fork）、**D2 SP21**、**D3 SP17 仅在 Tier 2 达标后决策**。

每阶段验收门（缺一不可）：`just test`、`just selfhost-native`（两代固定点逐字节）、
`python3 tools/arch-check.py`、`python3 tools/perf-baseline.py`（20 轮、记 load1、A/B 交错）、
最后才 `just seed`。性能门不设绝对值，只做**同机 A/B 变化率**（>+5% 必须归因）。

## 6. 本机实测（Windows x86_64，16 逻辑核，2026-11-03）

### 6.1 方法

- 编译器：根 `./yh`（PE32+，0.0.11 时代，2026-11-03 15:40 构建）。
- 语料：仓库 `compiler/`（134 文件 / 57,247 行）。
- 冷编：`YH_BUILD_CACHE=tmp/perf/cache-*` 独立缓存目录 + `yh build --stats -o …`，
  **不删除** `compiler/.build`；热编复用同一缓存；单模块重编 = 删该模块
  `obj/<tag>.o` + `manifest/<tag>.manifest` 后重建。
- 限制：Windows 无 `getloadavg`（load 不可测）；`just` 在本机沙箱内因反引号
  `拒绝访问 (os error 5)` 不可用；`perf-baseline.py` 需 `os.symlink`（无特权）。
  因此数字是**单机、少量轮次**，只用于「段落结构」判断，不与 Linux 基线相减。

### 6.2 四场景

| 场景 | 墙钟 | schedule | object | link | 阶段归因 |
|---|---:|---:|---:|---:|---|
| 冷编 | **248 s / 324 s** | 242 / 317 | 2.5 / 3.0 | 2.5 | front 2.8–3.4、lower 19–20、irbuild 1.3、**bridge 195–237（73–90%）** |
| 热编 | **3.5 s** | 0.17 | 2.47–3.0 | 0.26 | 全部命中，object 主导 |
| 单函数改动（measure） | 13.6 / 17.2 s | 8.8 / 11.7 | 2.3 / 2.8 | 1.9 / 2.2 | 模块重编 + 串行 |
| 单模块重编（backend，空闲机） | **91.4 s** | 86.9 | 3.5 | 0.33 | **bridge 82.4 s = 90%** |

有效并发 = worker 累计 / schedule = **0.83–0.90×**（Windows 无 fork → 串行）。
进程启动固定开销 0.19–0.34 s（`version`/`--help`）；80 KB 语法检查 0.18–0.24 s，
其中解析增量 <60 ms。

### 6.3 关键异常：桥在少数模块上是「病态」的

合成语料的桥成本是正常的：

| 输入 | 桥耗时 | 单位成本 |
|---|---:|---|
| 1 个函数 | 14 ms | 固定开销 |
| 150 个小函数 | 83 ms | 0.55 ms/函数 |
| 120 函数 × 80 语句（9,600 语句） | 407 ms | 0.04 ms/语句 |
| 200 个 if 分支（单函数） | 51 ms | — |
| **`backend` 模块（136 函数 / 20,511 AST 节点）** | **82–103 s** | **605–757 ms/函数** |

同一台机器、同一二进制、同一 LLVM 闭包（`D:\tmp\llvm-win\build\Release`，
`LLVM_ENABLE_ASSERTIONS=OFF`、`LLVM_ENABLE_EXPENSIVE_CHECKS=OFF`、`/O2`），
recompile 两次均复现（91.4 s / 111.8 s）。**结论：不是平台固定开销，是
「该模块的 IR 文本/函数形态 × 桥内某段」被放大**。待验证的候选（按可疑度）：
① 桥内逐 pass verify（`VerifyEach=1`，bridge.c:240）；② 巨函数的 verifier/惰性分析；
③ 文本 IR 解析（`ParseIRInContext`）在超大模块上的表现；④ 每模块新建
