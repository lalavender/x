## 1. 问题：流程不清晰的数据结构根源

「编译流程不清晰」不是文件组织问题（文件合并见
[build_pipeline 分析](yh-build流程集中到build_pipeline分析-2026-11-10.md)，正交待决），
而是三个结构性事实：

### 1.1 阶段身份靠开关组合编码

`support.SessionCtx`（`support/api.yh:93`）有 9 个阶段行为开关：
`compile/pass/check_only/test_mode/ast_capture/syntax_ast/front_checked/iface_load/ct_iface_mode`。
再叠加 `mb_pass2_file(path, fi, mode)`（`build/module_emit.yh:495`）的魔数 mode：

| mode | 实际阶段 | 调用点（module_worker.yh） |
| ---:| --- | --- |
| 0 | 函数体检查 | :389 |
| 1 | 全局初始化 | :342 |
| 2 | CT 函数捕获 | :294 |
| 3 | CT 布局登记 | :302 |
| 4 | CT 布局求值（循环） | :314 |
| 5 | 测试体检查 | :409 |

读 `mb_emit_indexed_module`（`build/module_worker.yh:138`）必须在脑内维护
「开关 × mode」矩阵才能定位当前阶段。**同一文件被重复 parse 6+ 次**，每次靠
`mb_restore_front_file` 恢复 token 快照重来——因为没有任何结构把上一阶段的成果
显式传给下一阶段。

### 1.2 阶段产物靠全局 arena，没有输入→输出契约

parse 写 `ast` 模块私有数组、check 写 `support.ms()`（`ModelStore` 单例）、
CT 写 comptime 全局；203 个模块级可变 `let`（架构 §4.5 实测）。
全管线唯一显式的阶段产物结构是 `CheckedModule` 快照。
`AstExpr`（`ast/api.yh:75`）25 个字段里 **15 个是语义注解**
（`type_id/sym_id/sym_name_*/binding_row/sym_type_id/sym_kind/sym_flags/sym_offset/
is_const/const_bits/is_lit/lit_big/fval_bits/layout_type_id`），
语法节点与语义结果同体——S4-2 影子门的双跑成本正来自这个双重身份。
对照组：`AstType`（`ast/api.yh:120`）已在 S4 纯化，只存语法，是正确样板。

### 1.3 编排层的隐式输入

worker 入口的真实输入分散在四处：函数参数（`m/main_off/main_len/out_dir/ir_cache_salt`）、
`BuildCtx.dep/dep_base`（每模块态却放构建会话）、`proj.cfg().module_mode/is_entry_mod`
（worker 改写只读模型的配置）、`support.fs().sym_sfx_*` 与 session 开关。
调度器运行期态是栈上三条平行数组（`states/pids/keys`，魔数状态 0–4）。
链接层已有 `LinkPlan`（`link/link_cache.yh:676`），但它是过程私有的大杂烩
（入参/驱动选择/暂存路径/argv 缓冲/阶段游标混在一个 struct），不是阶段契约。

## 2. 设计原则

1. **阶段显式化，存储不搬家。** fork/COW 模型下单例存储合法且高效；重设计的是
   **阶段间契约**（显式结构传递），不是把 203 个 `let` 全部线程化。
   状态归属判据沿用 §4.5：fork 后子进程允许各自不同的，归任务私有。
2. **语法与语义分离。** 语法节点只留 kind/op/span/children；语义结果放 check 拥有的
   注解侧表，按节点 id 平行索引。`AstType` 已是样板，`AstExpr/AstStmt/AstDecl` 照做。
3. **已好的不动。** `proj.ProjectCtx`（只读模型）、`ir.IRModule/IRFunction`
   （目标隔离、可序列化）、comptime `Ct*` 族（自包含执行器）、`CheckedModule`
   容器概念全部保留，只演进其内容物。
4. **每片可验、可回退。** 纯移动片要求产物逐字节一致；语义片走影子门差分。

## 3. 目标管线总览

```text
CliRequest（已有，cmd/yh）
  → BuildSession                     一次构建：项目模型(只读) + 目标(只读) + 缓存 + 计划
      ProjectModel = proj.ProjectCtx 现状保留
  → BuildPlan { order[], slots[] }   调度输入：拓扑序 + WorkerSlot 表
  → ModuleJob                        每模块显式任务（worker 唯一输入）
      │  worker 进程内（fork COW 或 --emit-module）：
      ├─ SyntaxModule                lex+parse：token + 纯语法 arena + 声明索引
      ├─ SemEnv                      check.resolve：类型/符号/签名/常量环境
      ├─ ExpandedSyntax              check.expand：CT 展开（新声明回 resolve 迭代）
      ├─ → 发布 .s.i/.s.ct/ready     接口就绪（full 之前，现状时点不变）
      ├─ HIRModule                   check.full：纯语法节点 + 注解侧表 + 语义表 + 静态数据
      │                              （= CheckedModule/CheckedStorage 的内容演进）
      ├─ IRModule                    lower（现状不变）
      └─ ModuleArtifacts             obj/iface/manifest 路径 + 摘要
  → LinkJob                          对象清单 + 链接组 + 输出 + 目标（LinkPlan 拆输入/私态）
  → Executable
```

阶段契约表：

| 阶段 | 输入 → 输出 | 所有者 | 停止条件 |
| --- | --- | --- | --- |
| 项目装载 | CliRequest → ProjectModel + BuildPlan | build/proj | 清单/依赖/拓扑错误 |
| 语法 | 源字节+token → SyntaxModule | parse/ast | 词法/语法错误 |
| resolve | SyntaxModule + 依赖接口 → SemEnv | check | 声明/类型/签名错误 |
| expand | SemEnv + SyntaxModule → ExpandedSyntax | check+comptime | CT 迭代收敛或 stuck 诊断 |
| full | ExpandedSyntax + SemEnv → HIRModule | check | 类型/控制流/可见性错误 |
| lower | HIRModule → IRModule | lower/ir | 不受检输入拒绝（verifier） |
| 后端 | IRModule → LLVM 文本 → .o | backend/llvm 桥 | 桥/架构校验失败 |
| 链接 | LinkJob → Executable | link | 链接器/产物校验失败 |

与架构 §6.10 已决定的两遍化完全同向；本方案是把该决定**落成字段级结构**，
并补上编排层（ModuleJob/WorkerSlot/LinkJob）——§6.10 只覆盖前端。

## 4. 核心结构定义（目标态草案）

### 4.1 纯语法 AST：AstExpr 拆分

`AstExpr` 25 字段拆为 **10 语法 + 15 语义**：

```yh
// 语法侧（ast 模块）：只描述「源码写了什么」，不回答「它是什么类型」。
pub struct AstExpr {
    kind int        // AST_EXPR_*
    op int
    first int       // token 半开区间
    after int
    token_count int
    file_id int
    owner_decl int  // 所属文件级声明（语法作用域事实）
    child0 int
    child1 int
    child2 int
}
```

语义 15 字段原样搬入 check 拥有的侧表（§4.2），**字段不增不减、语义不变**——
这是 S4-2e/f 的终态结构，不是新语义。`AstStmt` 已接近纯语法（结构字段为主），
`AstDecl.sym_id/type_id`（pass1 后绑定的语义事实）与 `AstBinding.sym_*` 快照同样外移；
`AstBinding.id/stmt_id/name_token/is_param` 是声明的语法身份，留语法侧。

**序列化兼容技巧**：内存中分离，落盘时按旧行布局合并写回——`.fchk`/快照字节不变，
缓存键与固定点不受拆分影响。读取侧拆开到两张表。

### 4.2 语义注解侧表（check 拥有）

```yh
// ExprSem：按 expr_id 平行索引的语义注解。check.full 写入，lower 只读。
// 字段与旧 AstExpr 语义 15 字段一一对应，迁移期由影子门保证逐字段相等。
pub struct ExprSem {
    type_id int
    sym_id int
    sym_name_off int   // 以下为绑定快照：作用域弹出后符号槽可复用，
    sym_name_len int   // 快照保证 lower 读到的是解析时刻的事实
    binding_row int
    sym_type_id int
    sym_kind int
    sym_flags int
    sym_offset int
    is_const int
    const_bits i64
    is_lit int
    lit_big int
    fval_bits i64
    layout_type_id int
}
```

生命周期：resolve 建声明级注解 → full 补函数体注解 → capture 时与语法 arena
一起深拷贝进 `CheckedStorage`。侧表行与节点同 id，verifier 增加「侧表行数 ≥
节点数且引用 id 越界拒绝」断言。`StmtSem`/`BindingSem`/`DeclSem` 同理，按需最小化。

### 4.3 SemEnv：ModelStore 演进

`support.ModelStore`（`support/api.yh:278`）的类型/字段/签名/名字/符号表整体保留，
但拆出两类不属于「模块语义环境」的字段：

- `scope_start/scope_n`（作用域栈）→ **函数任务私有**（full 阶段上下文）；
- `cur_enum/cur_struct/name_form`（「正在解析」游标）→ **resolve 阶段私态**。

归属从 support 单例演进为 check 拥有的模块任务结构；fork/COW 下存储形态不变，
变的是**写者与生命周期在类型上可见**。`FileScope/ModInfo/ImportEnt` 整簇按既有
结论归 proj（扫描期登记、绑定期解析，本就是项目数据）。

### 4.4 FrontendStage：SessionCtx 收编

```yh
pub const STAGE_SYNTAX int = 0      // 纯语法（--syntax-check / S4 终态的 parse）
pub const STAGE_RESOLVE int = 1     // 声明/类型/签名/全局初始化登记
pub const STAGE_CT_CAPTURE int = 2  // @[comptime] 正文捕获
pub const STAGE_EXPAND int = 3      // CT 布局登记+求值迭代
pub const STAGE_FULL int = 4        // 函数体/测试体完整检查
pub const STAGE_IFACE_LOAD int = 5  // 读 .s.i/.s.ct（登记不发射）
```

SessionCtx 字段映射（逐个消灭或归位）：

| 现字段 | 去向 |
| --- | --- |
| `compile` `pass` `ast_capture` `syntax_ast` `front_checked` | 由 `FrontendStage` 取代；`ast_capture/syntax_ast` 是 S4 过渡门，收口后删除 |
| `iface_load` `ct_iface_mode` | `STAGE_IFACE_LOAD` + 该阶段私态 |
| `ct_origin_active/line` | iface-load 阶段私态游标 |
| `active_file` `data_label` | 阶段私态游标（文件编号/标签计数） |
| `check_only` `test_mode` | **行为配置不是阶段**：上移 `ModuleJob.mode`（Build/Check/Test） |
| `legacy_system` | 上移 `BuildSession.config` |

`mb_pass2_file` 的魔数 mode 改命名入口（薄转发，逐字搬移）：

```text
mode 2 → check_capture_ct()      mode 3 → check_register_layout()
mode 4 → check_eval_layout()     mode 1 → check_globals()
mode 0 → check_full_bodies()     mode 5 → check_test_bodies()
```

worker 主流程随之顺读：`resolve → capture_ct → expand → globals → emit_iface →
full_bodies → (test_bodies) → capture → lower`，每步是命名函数+显式阶段枚举，
不再需要 flag 矩阵。**重复 parse 本方案不消除**（它是 S4 纯语法化的结果而非原因：
语法/语义分离后，各阶段读同一 SyntaxModule，重解析自然消失）；B 片只把阶段身份显式化。

### 4.5 ModuleJob：worker 的唯一输入

```yh
// ModuleJob：一个模块编译任务的全部显式输入。build 组装，worker 只读。
pub struct ModuleJob {
    mod int            // proj 模块下标
    mode int           // JOB_BUILD / JOB_CHECK / JOB_TEST
    dep list.List      // 依赖接口记录（BDep，从 BuildCtx 迁入——本就是每模块态）
    dep_base int       // 接口加载前符号基线
    sym_sfx_off int    // 模块符号后缀（从 support.fs() 迁入）
    sym_sfx_len int
    out_dir *char      // 产物目录（现 worker 参数）
    ir_cache_salt u64  // 编译器指纹（现 worker 参数）
}
```

取代现状四处分散：worker 五参数、`BuildCtx.dep/dep_base`、
`proj.cfg().module_mode/is_entry_mod`（worker 不再写项目模型）、`support.fs().sym_sfx_*`。
`mb_emit_indexed_module(m, main_off, main_len, out_dir, salt)` →
`mb_emit_module(*ModuleJob)`。`--emit-module` 子进程协议 argv 不变（job 在子进程
重建），fork 路径父进程组装后 COW 继承。`BuildCtx` 只剩构建会话真正的自属态：
编译器身份、缓存 store、调度上限、接口后缀。

### 4.6 WorkerSlot：调度状态结构

```yh
pub const SLOT_PENDING int = 0
pub const SLOT_RUNNING int = 1
pub const SLOT_IFACE_READY int = 2
pub const SLOT_DONE int = 3
pub const SLOT_FAILED int = 4

pub struct WorkerSlot {
    state int
    pid int
    action_id [32]u8   // cache.CACHE_ID_SIZE； keys 数组的一行
}
```

取代 `mb_schedule_modules_locked` 的 `states/pids/keys` 三平行数组与魔数注释。
调度循环读 `slot.state`，语义不变。

### 4.7 LinkJob 与 ModuleArtifacts

`LinkPlan` 拆两层：**输入契约**（build 组装、link 只读）与**阶段私态**（link 私有）：

```yh
// LinkJob：链接任务的显式输入。
pub struct LinkJob {
    out_path *char
    build_off int      // 产物根路径（池偏移）
    build_len int
    root_proj int
    object_n int       // 对象清单（模块产物 tag 表）
    // 链接组/C 输入/自举 flags 由 prepare 从 ProjectModel 读入私态，
    // 与现状一致；后续若要完全显式化再单列切片。
}
```

`LinkPlan` 后半（cc 缓冲、暂存路径、argv 行缓冲、macho/coff 游标）留作 link 私有
阶段态，改名 `LinkScratch`。`mb_link(*LinkJob)` 六段流程不变。
`ModuleArtifacts`（obj/iface/ct/manifest 路径+摘要）把 `module_cache.yh` 的
四产物检查与 manifest 提交收成一个结构，路径仍经 proj 产物路径窄口，不另拼路径。

## 5. D1：UIR 层不引入（评审 §6.11，推荐）

§6.11 草案拟在 parse 与 check 之间加 AstGen→UIR（Zig ZIR 对等）。**推荐不引入**，
CT 展开位置从草案的「UIR」改为「纯语法 AST」。理由：

1. **Zig AstGen 的存在理由在 yh 不存在。** Zig AST 是指针树，AstGen 把它转成扁平
   指令流（ZIR）以获得可序列化紧凑表示。yh 的 `AstExpr/AstStmt` **已是扁平
   arena + id 引用**（child0/1/2、first/last_child），且已随 `CheckedStorage`
   深拷贝、随 `.fchk` 序列化。再加 UIR 近乎同构复制，多一份 arena 与 verifier。
2. **文件级缓存收益无测量支撑。** PF2 实测冷编 worker CPU：lowering 66% /
   IR 构造 20% / 桥 8% / **前端 6%**。UIR 文件缓存优化的是 6% 里的一段；
   函数级增量已由 `.fchk`/`.fir` 覆盖。新增一层缓存键/失效矩阵的成本大于收益。
3. **§6.11 的核心收益本方案全部获得**：语法/语义分离（§4.1/4.2）、CT 在显式节点上
   展开（S4-3，纯语法 AST 与 UIR 在此等价）、HIR 契约（§4.2 + CheckedStorage 演进）、
   eager full（不变）。

草案已确认两点中的「暂不接受惰性 Sema」保留；「CT 展开放 UIR」修订为
「CT 展开放纯语法 AST」。若将来实测前端成为瓶颈、或要按文件并行 parse/AstGen，
再立 ADR 引入 UIR（届时本方案的语法/语义分离已是其必要前提，不返工）。

## 8. 不做的事

- 不消除单例存储形态（fork/COW 合法），不线程化 203 个 `let`；
- 不动 `ir.IRModule`/后端/链接六段流程/缓存键 schema（`.fchk` 字节不变是硬门）；
- 不动 `proj`/`cache`/`hash` 模块边界与平台变体选片机制；
- 不引入惰性 Sema、不引入第二后端（沿用 §6.11 已确认点与 ADR-0014）；
- 不顺手的死代码清理：B4 之外的既有死字段只记录不删除；
- 不与 build_pipeline 文件合并方案耦合（该方案待决，两者正交）。
