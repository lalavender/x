## 0. 结论速览

| # | 结论 | 位置 |
|---|---|---|
| C1 | 依赖层**没有依赖管理，只有路径引用**：`[dependencies]` 只有 `path` 一种合法形态，全仓无锁文件、无版本、无校验和 → 构建**不可复现** | §2 D1 |
| C2 | 有 **3 处静默失败**（依赖超 64 条截断、未知清单节不报错、拼错节名变成「模块不存在」），属最高优先级 | §2 D2 / D3 |
| C3 | 命名空间**平坦且单标识符**，三层搜索的硬优先级使**标准库不可替换**、第三方同名只能报歧义 | §2 M1 |
| C4 | 可见性**只有两档**，项目内跨模块协作即等于对下游完全公开；`pub(proj)` 是唯一实解 | §2 M3 / §3 MD10 |
| C5 | 类型**必须先定义**（`parse/parse_type.yh:392`），于是 `00_/10_/20_` 文件名编号在承担头文件职责；这是**文件级对象增量（R4）的前置障碍** | §2 M4 / §3 MD12 |
| C6 | 项目身份（符号后缀）只含 `project.name`，**不含 version 与路径** → 多版本共存在符号层就已不可能，不只是"没设计" | §2 D5 / §3 MD16 |

## 2. 缺陷清单

符号级耦合实测（2026-10-26，按 `模块.符号` 去重）：`parse→gen` 272、`lex→gen` 107、
`comptime→gen` 106、`lower→ir` 97、`lower→gen` 95、`backend→ir` 79、`parse→ast` 69、
`parse→comptime` 67、`build→gen` 56、`testkit→build` 28。模块间 import 共 37 条边、无环。

### 2.1 依赖与清单层

#### D1 没有版本、没有锁文件、没有校验和 → 构建不可复现

`build/project_index.yh:334`：

```
if (snap_path_off[di] < 0) {
    return pj_proj_diag(root_off, dep_line, "依赖必须是 { path = \"...\" } 表")
}
```

`build/` 全目录搜 `lock` / `semver` / `registry` 零命中。三条后果：

1. 同一份 `project.toml`，不同时间构建可能用不同依赖内容，**没有任何记录**说明上次用的是哪份；
2. `IFACE_VERSION_MIN/MAX` 只解决「接口格式能不能读」，**不解决「语义变了没有」**；
3. 与自举体系不对称：种子有 SHA-256（`bin/*.sha256` + `just seed` 拒绝带构建机路径的种子），
   依赖什么哈希都没有。

旁证：`snap_path_off[di] < 0` 同时意味着「一条依赖只能是一个带 `path` 的内联表」，
**将来加 `version = "1.2"` 会被当前解析器先判为非法**，改法必须是新增节或新形态，不能只是加键。

#### D2 `[dependencies]` 超过 64 条被静默截断

`build/project_index.yh:320-326`：

```
let snap_key_off [64]int
let snap_key_len [64]int
let snap_path_off [64]int
let snap_line [64]int
...
for snap_n < toml_secs[dsec].val_n && snap_n < 64 {   // ← 无 else 诊断
```

第 65 条依赖不报错、不警告，直接消失，最终表现为「模块不存在」，排查方向被引向源码。
相同的定长处理还出现在别处（`module_build.yh` 的 `[192]u8`/`[512]u8` 缓冲），但那些是
有界诊断文本，不改变语义；此处改变的是**装载结果**。

#### D3 未知**字段**有诊断，未知**节**没有

`toml_find_sec` 只在 3 处被调用（`project` / `c` / `dependencies`）；`[project]` 与 `[c]`
有「未知字段」检查（`project_index.yh:131`、`:273-311`），**没有任何「未知节」检查**。

实证——仓库自己的 `libs/project.toml`：

```toml
[bin]                       # 空节，无人读
[lib]                       # 12 条路径依赖，无人读
os   = {path  = "./os"}
io   = {path  = "./io"}
... （共 12 条）
```

`libs/` 的模块是靠 `source = "."` 目录扫描发现的，这 12 行**完全是死配置**。三个后果：

1. 把 `libs/project.toml` 当模板抄的人会以为依赖在那儿声明；
2. 拼错 `[dependecies]` → 静默零依赖 → 报「模块不存在」，错误位置指向源码而**不是清单**；
3. `[lib]`/`[bin]`/`target = lib|bin|all`（清单注释里提到的目标类型）都只是规划字样，
   既不生效也不拒绝 —— **规划与拒绝之间的第三种状态是最坏的**。

#### D4 不能借用传递依赖，摩擦靠人记

设计文档 §6 明文：app→A→B 时，app 想 `import` B 的模块必须**自己在 `[dependencies]`
再写一遍 B**；§13 验收矩阵也钉了「仅传递依赖提供所导入模块 → 拒绝」。

这本身是**合理的取舍**（清单即事实、没有隐式依赖面），但当前错误文本是「模块不存在」，
用户拿不到「B 是 A 带来的，请自己声明」这个关键信息，摩擦全部转成人工排查。

#### D5 多版本共存：符号层就已不可能

设计文档 §7 说「多版本共存和远程项目身份验证另行设计」。实测比这句更严重——
符号后缀是 `__<project.name>__<module.name>_`（`build/project_resolve.yh:354-386`），
**身份里既没有 version 也没有路径**：

- 两个 `name = "json"` 的不同版本 → 生成完全相同的符号 → 链接期直接撞；
- `pj_load_project` 又用「相同 project.name 从不同真实目录装载即冲突」把这种情况提前拦死。

所以 D5 不是「没设计」，而是**身份模型不足以支撑**。同时没有 workspace 概念，
`libs/` 这种「15 个模块共享一个清单」的布局无法拆成独立可发布的单元。

### 2.2 命名与解析层

#### M1 平坦名字空间 + 不可协商的三层优先级

- 模块名是**单个合法标识符**、无嵌套（设计文档 §1）；
- `import json;` 按「本项目 → 标准库 → 直接依赖」搜索，命中即停（§5）；
- 标准库**无法被第三方同名模块替换**——想做 `json` 的高性能替代只能改名字；
- 第三方层出现两个 `json` → **报歧义**，唯一解法是 `import a.json as x;`（`as` 可用）
  或改模块名，且没有任何清单级声明能表达「我要 fast 版」。

#### M2 没有 re-export，库无法收口 API

无 `pub import` / `pub use`。模块 A 用了 B，A 的用户必须自己也依赖 B。配合 D4，
结果是**每个库的依赖面永久暴露给下游**，库作者无法把实现库藏起来。

#### M3 可见性只有两档，项目内共享 = 对世界公开

设计文档 §8 自述取舍：*「两档权限意味着项目内部跨模块协作需要 pub」*。无
`pub(proj)` / `internal`（「internal 目录与名为 internal 的模块均按普通名字处理」）。

代价可量化：`libs/cli` 11,120 行（占 libs 24k 行的 46%）的内部协作面全是公开面；
`compiler/build` 的 54 个 `pub fn` 里绝大多数只该在项目内可见。另外 struct 字段一律
公开（§8），无字段级封装。

#### M4 类型必须先定义 → 文件名编号在承担头文件职责

函数跨文件前向引用是允许的：pass1 先对整个模块登记签名（`mb_pass1_file`），再
`mb_check_binding_clash` 复查导入名冲突，然后 pass2 走函数体。**类型不行**：

```
compiler/parse/parse_type.yh:392
    return gen.sem_err("未知类型（类型必须先定义）")
```

于是 `base.yh` / `read.yh` / `write.yh` / `ir/ssa_module_00..50` /
`comptime/ct_00_model.yh` 这些编号不是风格，而是**编译顺序依赖的补偿**。后果：

- 重命名文件可能直接引入编译错误；
- 模块是「有序翻译单元」而不是「声明序无关的集合」，**这正是按文件对象增量（R4）落不了地的根因**（今天仍每模块发一个 `.o`）。

#### M5 目录树与模块图永久脱钩

`project_index.yh:738` 强制「每目录一个模块」（报错文本：「同目录存在另一个模块（每目录一个模块）」），
同时模块名来自文件头 `module X;`、与目录名无关（§1 明文）。两条规则合起来：
**目录名与模块名是两套命名**，IDE 跳转、`import` 补全、代码审查都读不出对应关系，
只能打开文件看第一行。

#### M6 入口模块名 `main` 硬编码，清单无 `entry`

`build/project_index.yh:390` 逐字节比较 `'m','a','i','n'` 判定入口；`yh build` 只能接受
一个模块（`module_build.yh:1908`：「yh build 只能指定一个模块」）。后果：一个项目
**只有一个可执行目标**，`cmd/foo`、`cmd/bar` 类多二进制布局无法表达（`libs/project.toml`
那个空 `[bin]` 正是这个缺口）。

#### M7 平台适配靠文件名后缀，没有模块级条件编译

`.linux.yh` / `.darwin.yh` / `.arm64.yh` 后缀按 `TargetInfo` 选文件（机制正确，优于
`#ifdef`），但只能表达「某平台换实现」，不能表达「某模块在某平台禁用/降级」，
也没有 feature / 条件依赖。新增平台要写第三份同类文件：`clock.*` 与 `project_dir.*`
现在各 3 份（`build/clock.darwin.yh` / `.linux.arm64.yh` / `.linux.x64.yh`，同构）。

#### M8 契约版本分散 5 处，接口是自制文本

| 契约 | 常量 | 值 | 位置 |
|---|---|---:|---|
| 模块接口 | `IFACE_VERSION_MIN/MAX` | 1–3 | `parse/iface.yh:436` |
| 编译期接口 | `CTIFACE_VERSION` | 1 | `parse/iface.yh:438` |
| SSA 函数编码 | `IR_SERIAL_VERSION` | 9 | `ir/ssa_serialize.yh:4` |
| 模块 IR 编码 | `IR_MODULE_SERIAL_VERSION` | 3 | `ir/ssa_module_30_serialize.yh:62` |
| 函数缓存 | `IR_FUNCTION_CACHE_VERSION` | 1 | `ir/ssa_module_40_function_cache.yh:21` |

读取端各自「相等即通过」（接口侧有区间），升级一处不影响其余四处的提示路径。
manifest 写入点（`module_build.yh:2151-2163`）逐个引用这 5 个常量，是唯一「看得见
全部 5 个」的地方 —— 恰好也是最不该硬编码的地方。

#### M9 项目模型类型放错了模块

`PFile` / `PMod` / `PDep` / `PProject` 定义在 `gen`（共享内核），字段挂在 `GenState`
（65 字段，`gen/state.yh:273` 一带是 `p_stdlib` 等），唯一使用者与唯一写者是 `build`。
成因是依赖方向：`gen` 不能 import `build`，所以类型被迫放进 `gen`。结果是 `build → gen`
的 56 个符号里混着「项目表类型」，而 `gen` 本不该知道「项目」这个概念。

#### M10 没有 `[dev-dependencies]`，测试依赖伪装成正式依赖

测试专用导入仍要写进 `[dependencies]`，靠 `pj_classify_test_imports`
（`project_index.yh:900` 一带的「测试专用导入分类」）在非测试构建里跳过 ——
**语义上分离、清单上没分离**。实现这件事的 `testkit` 又直接使用 28 个 `build` 内部
符号（`mb_link`、`mb_build_dir`、`mb_fnv`、`mb_module_obj_row` 等，见
`testkit/test_cmd.yh:950/1357/1467/1492`）：**测试发现属于模块系统，却没有独立边界**。

#### M11 工具面薄

有 `yh list` 与 `yh list --resolve <名>`（`module_build.yh:2193`，能解释三层绑定，这点做得好），
但没有：依赖树（`tree`/`why`）、`add`/`update`、锁文件 diff、循环依赖可视化。
出了依赖问题只能读诊断文本。

## 3. 修复方案（4 批 / 18 项）

约定：每项都给「改哪里 / 怎么改 / 验收 / 代价」。所有方案受两条硬约束：①必须落在
自举子集内（整数/指针/结构体/`for`，无泛型无闭包）；②每批结束
`just test` + `just selfhost-native` 全绿才滚种子；新增行为一律先加
`tests/yh-run/` 或 `tests/modules/` 用例（AGENTS.md 规则）。

### 批 0：先消灭所有「静默」（当天，零语义变化）

#### MD1 未知清单节报错 + 清掉 `libs` 死配置（解 D3）

- **改哪里**：`build/project_index.yh`（新增 `pj_check_known_sections`）、`libs/project.toml`。
- **怎么改**：`TomlSec` 已带节名与节头行号（`build/toml.yh:34`）。在 `pj_load_project`
  解析完 TOML、校验 `[project]` **之前**前检：遍历 `toml_sec_n`，节名必须匹配白名单
  （§1 那 7 个形态，`[link-options-*]` 的名字判定复用 `project_link.yh:231-237`），
  否则 `pj_proj_diag` 报 `<line>: 未知清单节 [xxx]（支持：project / dependencies / c /
  link / link-<os>-<arch> / link-options-<os>-<arch>）`。随后删掉 `libs/project.toml`
  的 `[bin]` 与 `[lib]` 两节。
- **验收**：新增 `tests/modules/projects/badsection/`（`[dependecies]` → 期望清单诊断）；
  正例 `[link-options-darwin-arm64]` 仍通过；`just libs-test` 不受影响。
- **代价**：~80 行。**全清单性价比最高**：把「模块不存在」变成一句准确的清单诊断。

#### MD2 依赖表去定长上限（解 D2）

- **改哪里**：`build/project_index.yh:320-326`。
- **怎么改**：节内条目数在解析后已知（`toml_secs[dsec].val_n`），改为
  `malloc(val_n * sizeof(int))` 的四个快照数组，递归装载完统一 `free`（保持现有
  「快照而非引用」语义，因为递归装载会重置 `toml_secs`）。同时加显式上限检查
  `val_n > 1024 → 报错`（有界报错优于静默截断，但上限要远大于实际）。
- **验收**：新增 `tests/modules/projects/manydeps/`，70 个本地依赖 → `yh list` 输出 70
  个模块。此用例在改前失败，正好当回归钉。
- **代价**：~60 行。

#### MD3 `yh list` 打模块 ← 目录 + arch-check 目录名断言（解 M5 一半）

- **改哪里**：`build/module_build.yh:2193`（`mb_cmd_list`）、`tools/arch-check.py`。
- **怎么改**：`yh list` 每行输出 `模块名  <- <相对源码根的目录>`（`p_mods[m].files[0]`
  的路径截到目录即可）。`arch-check` 新增**约定检查**（不是语言规则）：
  `compiler/` 下每个目录名必须等于其中的 `module` 声明名；今天 13/13 相符，改成守护断言。
- **验收**：`yh list` 输出快照比对；`arch-check` 在故意改错一个目录名时失败。
- **代价**：~40 行。真正消除「目录树与模块图脱钩」需要嵌套模块（§5 决定不做），
  本条只让现状可读。

#### MD4 契约版本登记表（解 M8）

- **改哪里**：新建 `compiler/gen/contract.yh`；改 `parse/iface.yh`、`parse/iface_ct.yh`、
  `ir/ssa_serialize.yh`、`ir/ssa_module_30_serialize.yh`、`ir/ssa_module_40_function_cache.yh`、
  `build/module_build.yh:2151-2163`。
- **怎么改**：唯一一份常量放 `gen/contract.yh`（保持 `pub const`，因为 `.s.i` 与 manifest

### 批 1：可复现与可诊断

- **验收**：`tests/modules/projects/locked/`：构建 → 篡改依赖 → 构建失败且含

### 批 3：架构级（需 ADR，每条单独一代种子）

#### MD13 项目模型迁出 `gen`（解 M9）

- **现状成因**：`GenState` 是进程级单例，`gen` 不能 import `build`，类型被迫放 `gen`。
- **真正的解**：项目状态从 `GenState` 搬出，成为 `build` 拥有的 `ProjState`，由 `mb_*`
  显式传递。这与[系统架构与长期演进设计](../03-design/yh-系统架构与长期演进设计-2026-10-24.md)
  的 `Session` 议题是同一件事，**不是新任务，是那件事的必要前提**；与 todo 的 B1
  （`BuildCtx` 对象化）同源，应在 B1 之前或同时立项。
- **过渡（一天，可先做）**：四个结构体移到新 `gen/proj_model.yh`，文件头写明
  「临时：项目模型暂存 `gen` 以避免 `GenState` 反向依赖 `build`；随 `Session` 化迁出」。
  收益是诚实，不解决耦合。
- **验收**：`arch-check` 加断言（`gen/proj_model.yh` 字段数只减不增）。

#### MD14 `pub import`（re-export）（解 M2）

- **改法**：`.s.i` 升 **v6** 加 `pub import json;` 行；`iface_load` 时把被 re-export 的
  模块登记进本模块命名空间；下游经本模块跳转。
- **硬约束（写进 ADR）**：re-export 只重发**接口**，不重发依赖的 `[link]`/`[c]`；
  它是 D4「禁止传递依赖」的受控例外，边界必须逐条列出。
- **风险**：本清单最容易做出「隐式依赖面」的一条。**建议在 MD13 完成后才做。**

#### MD15 命名空间：决定不做嵌套模块，改做「依赖键.模块名」诊断

- 方案 A（嵌套模块 `a.b.c`）成本远超收益，且与「每目录一模块」冲突（需重写扫描器）。
- 方案 B（推荐）：把已有先例 `import libs.os;` 的「依赖键」这一级推广为**歧义时的
  建议解**——歧义诊断直接给出 `可以写 json-fast.json 或 import json-fast.json as json`。
  配合 MD9，真实冲突场景已够用。**零成本，只改诊断文本。**

#### MD16 workspace 与多版本共存（解 D5）

- **根因**：符号后缀 `__<name>__<mod>_`（`project_resolve.yh:354-386`）不含 version 与路径。
- **两步**：
  1. 后缀加身份：`__<name>_<ver-hash>__<mod>_`（同版本多副本共用符号，语义正确）。
     `project.version` 参与身份后必须由可选改为**必填**——可选字段同时当身份的一部分是陷阱。
  2. 放宽装载检查：`pj_load_project` 的「同 name 不同目录即冲突」改为
     「name+version 相同而路径不同 → 冲突；name 相同 version 不同 → 允许两个实例」。
- **代价**：一次全量缓存失效 + 符号变，**必须单独一代种子**。
- **耦合**：与 MD10 的 provider 项目 id 有耦合（provider id 要能区分同名不同版本），
  故 MD16 在 MD10 之后或同时。

#### MD17 平台条件编译（解 M7）

- **近期（便宜）**：每组平台文件抽**共享声明文件**。以 clock 为例：新建 `build/clock.yh`
  声明 `pub fn cmd_clock_ns() u64` 与 `CmdTimespec`，三个 `clock.<os>.<arch>.yh` 只留实现；
  `arch-check` 加断言「同组平台文件签名集合一致」。第三份复制从 ~20 行降到 ~10 行，
  且签名只写一遍。
- **中期（真解）**：`@[platform(linux, arm64)]` 属性，parser + `.s.i` + 非匹配目标跳过登记。
  **必须在 MD12 之后**（两者都改 pass1 登记时机，分开做要碰两次同一段代码）。

#### MD18 `testkit` 收口（解 M10 后半）

- **改法**：`testkit` 实际只用三类东西：产物路径（`mb_build_dir`）、链接（`mb_link`）、
  哈希（`mb_fnv`）。在 `build` 上开 3 个窄口 `art_build_dir` / `art_module_obj` /
  `art_link`，`testkit → build` 的 28 个符号降到 3 个。
- **不做**「抽模块」这类投机抽象，只开窄口（符合本项目取向）。
- **验收**：`arch-check` 把 `testkit → build` 从「符号级不限」改成「只允许 `art_*` 前缀」
  （参照 `check` 的白名单做法）。

## 4. 执行顺序与门禁

```
批 0（1 天）  MD1 MD2 MD4 MD3 MD5      → just test + just selfhost-native，无语义变化，可直接滚种子
批 1（1–2 天）MD6 MD7                  → 加 tests/modules/projects/locked，滚种子
```

| 种子 | `just seed` | 仅在前四项全绿后 |

## 5. 决定不做（连同理由，防止反复讨论）

- **远程仓库 / 版本求解 / registry**。与「种子即二进制 + 本地 path 依赖」的自举体系
  不兼容：一旦引入，`just fetch-seed` 的可复现性担保会被依赖下载破坏。MD6 的内容哈希锁
  是这一步的替代品。
- **嵌套模块树**（原 M1 的大解）。MD9 + MD15 已覆盖真实冲突场景，方案 A 成本远超收益（见 MD15）。
- **`[[bin]]` 多二进制数组**。在「一个项目一个产物」的缓存/链接布局改变之前不做（见 MD8）。
- **放开传递依赖**。与 D4 保留一致：会重建隐式依赖面。

## 7. 验收矩阵（按批补充到语料）

| 场景 | 期望 | 归属 |
|---|---|---|
| 清单写 `[dependecies]` | 未知清单节诊断（带行号） | MD1 |
| 70 个依赖 | 全部装载，`yh list` 显示 70 个模块 | MD2 |
| 依赖源码被篡改后构建 | 失败并提示 `--update-lock` | MD6 |
| 仅传递依赖提供模块 | 报「B 由 A 提供，请自行声明」+ `yh tree` 输出 | MD7 |
| 入口模块不叫 `main` | `[project] entry` 生效，其余项目行为不变 | MD8 |
| 两个依赖都提供 `json` | 无 `[resolve]` → 歧义；有 → 指定方生效 | MD9 |
| 同项目用 `pub(proj)` | 通过 | MD10 |
| 下游项目用上游 `pub(proj)` | 报「只在项目内可见」 | MD10 |
