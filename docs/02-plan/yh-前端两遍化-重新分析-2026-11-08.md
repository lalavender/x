# 前端两遍化：重新分析（2026-11-08）

对 2026-11-06 的「parse 纯语法 + check 语义分析」（原 F0–F7）做**重新评估**。
触发原因：自那之后 GEN0–GEN4 与 F2/F4 全部落地（`gen` 删除、`TaskCtx` 归零、
状态归 `support`），前端耦合结构已经变化，原计划的行数与风险假设需要更新。

结论先说：**不建议按原 F0–F7 全量重写**；建议改为 S1–S4 四个可独立验收的切片，
其中 S1 现在就能做且零成环风险。

## 2. 三条硬约束（决定可行顺序，比 2026-11-06 更明确）

### C1 依赖方向：`parse → check`，所以「check 调 parse」= 环

今天 `parse` import `check`。任何「搬进 `check` 但仍要重新解析源码」的逻辑都会
形成 `check → parse → check`。受此约束：

- `parse_ct_layout.yh`（501 行，26 次 `comptime` 调用）**不能**迁 `check`：它要靠
  `p_cur`/`p_adv`/`parse_expr`/`parse_top_decl` 重放长度表达式。
- `iface_load` / `iface_ct_load`（392 行）**不能**迁 `check`：它们要 `parse_source`。
- 反过来，**发射侧没有这个约束**（纯序列化）。

### C2 CT 展开晚于 resolve（原结论仍成立）

`$for values/fields`、`$field`、`@[comptime]`、插值 spec 都要声明/类型环境；
`check` 内部必须是 `resolve → 检查 CT 函数 → expand → full`，且 expand 可能迭代
（新生成的声明要重新 resolve），必须有展开预算。

### C3 自举与固定点

跨模块搬家**不要求**编译器自身 `.s.i` 字节一致（模块身份/后缀会变），但要求：
`just` 冷编 + `just test` 全绿 + `just selfhost-native` 两代固定点一致 + 全量语料
等价。现在本地与 CI 都具备这些门禁（2026-11-08 恢复）。

## 4.1 S2 实施结果与结论修正（2026-11-08）

原 S2 写的是「把 `parse_ct_layout` 迁 `check`」，实施时发现**方向不可行**：

- 该文件的核心（`parse_source_ct_layout_exprs` / `ct_enum_pending_run`）要
  **重入解析器**（`parse_expr`）。若主体搬到 `check`，`check` 就必须 import `parse`，
  而 `parse` 已经 import `check` → 直接成环。`parse.eval_token_range` 只是把「重入」
  收成一个函数，**不能消除方向约束**。
- 因此实际执行的是**可行的那一半（S2a）**：
  1. 新增窄口 `parse.eval_token_range(first, after, out *Res)`：自管 pos/ast_capture/
     c_fold，替换 parse 内两处重复的求值样板（数组长度表达式、延迟枚举判别值）。
  2. 把**不需要重入解析器**的策略函数下沉 `comptime/ct_layout_sched.yh`：
     `ct_layout_expr_runnable`（const/CT 函数/sizeof 依赖判定）、
     `ct_layout_expr_register`（依赖边登记）。它们只读 token 表与 `ms()`、只写
     comptime 自己的依赖图，因此与「布局请求数据」同处一模块最自然。
- **S2b（调度整体下沉 `check`）** 不是独立切片：它要求 `parse` 不再 import `check`
  ——那正是 S3 的产物。结论：S2b 并入 S3 的前置条件，不再单列。

指标：`parse` 7,640 → **7,580 行**（`-60`），`comptime` 5,956 → 6,076 行（+120，含
新文件头注释）；产物与 S1 后**逐字节一致**。
