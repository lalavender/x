# yh 编译期符号依赖解析实施方案

- 日期：2026-11-11
- 状态：规划
- 目标：模块级顶层声明的**类型与值依赖**在编译期按依赖求值，不再依赖源码书写顺序；
  循环依赖给确定诊断。`pub` API 仍强制显式类型。
- 关联：[类型推导方案](yh-类型推导实施方案-2026-11-11.md)；
  S4-2/S4-3（parse 纯化、CT 下沉）。

---

## 1. 目标与非目标

### 1.1 目标

1. 模块级 `const` / `let` 初始化允许前向引用：
   `const B = A + 1; const A = 1` 可以编译，B 为 `int`。
2. 模块级类型声明允许前向引用：
   `struct A { b B }` 在 `struct B` 之前声明也能解析（S2）。
3. 跨文件（同一模块）的声明依赖同样按依赖解析，不按文件/声明顺序。
4. CT 调用与 CT 函数体读到的全局值也纳入依赖图（S3）。
5. 循环依赖报完整路径：
   `循环依赖: A -> B -> A`，带各自声明位置。
6. 解析过程不改变运行期语义、不改变公开 API 的显式类型要求。

### 1.2 非目标

- 不做跨模块循环依赖（项目调度已有依赖图；`.s.i` 仍是模块边界）。
- 不做运行期初始化顺序重排；只处理编译期可求值的模块级初始化。
- 不做函数返回类型推导、HM、`$any` 实例化（各自方案）。
- 不改变 `pub` 声明必须显式类型的规则。
- 不把模块级 `let` 初始化放宽到运行时调用；仍要求编译期常量。

## 2. 现状与证据

| 场景 | 当前行为 |
| --- | --- |
| 函数前向调用 `main` 调后定义的 `f` | 合法（pass1 登记全部函数） |
| 函数体引用后定义的全局 | 合法（pass1 登记全部全局符号） |
| `struct A { b B }` 在 `struct B` 之前 | `未知类型（类型必须先定义）` |
| `const B int = A + 1; const A int = 1` | `编译期常量尚未就绪`（显式类型也一样） |
| `const A int = 1; const B int = A + 1` | 合法 |

结论：

- 函数符号已经由 pass1 前向登记，不需要额外处理。
- **类型名**在 parse/type_syntax 阶段即时解析，尚未声明就报错。
- **值**在 `MB_PASS2_GLOBALS` 按文件/声明顺序初始化；后声明的常量未就绪。

现有流程（`compiler/build/module_worker.yh`）：

```text
pass1（源顺序登记符号）
→ main/绑定冲突检查
→ pass2 CT 函数正文
→ 布局注册/求值（数组长度等）
→ 全局初始化（源顺序）
→ 接口发射
→ 普通函数体
```

## 3. 依赖模型

### 3.1 节点

| 节点 | 说明 | 阶段 |
| --- | --- | --- |
| `T` 类型声明 | struct/union/enum/type 别名 | S2 |
| `C` 常量/全局变量 | 模块级 `let`/`const` 初值 | S1 |
| `F` 普通函数 | 签名/正文 | 无需排序（pass1/2） |
| `Q` CT 函数 | `@[comptime]` 正文与 `$` 调用 | S3 |
| `L` 布局请求 | 数组长度、`sizeof` 依赖 | 现有 layout 调度 |

### 3.2 边

- 类型 → 类型：字段、指针、数组元素、函数类型参数、别名目标。
- 值 → 值：初始化式引用的模块级 `const`/`let`。
- 值 → 类型：初始化式使用结构体/数组字面量、`sizeof`、`to_type`。
- 类型 → 值：数组长度表达式引用常量。
- CT 调用 → CT 函数 → CT 函数体读到的值/类型（S3）。

### 3.3 求解顺序

```text
S2 类型声明依赖排序/解析（类型名全部可见）
  ↓
pass1 值/函数符号登记（类型已可用）
  ↓
类型推导（无类型私有 let/const，按依赖多轮）
  ↓
pass2 CT 函数正文捕获（S3 再把 CT 函数体依赖纳入图）
  ↓
layout 调度（数组长度等；按需提前求值相关常量）
  ↓
S1 全局值初始化调度（probe → commit，多轮；跳过 layout 已就绪的常量）
  ↓
接口发射 → 普通函数体
```

具体落地顺序可按现有管线微调；原则是**同层内按依赖求值，循环即报错**。

## 4. S1：模块级值依赖调度（直接解决 `const B = A + 1`）

### 4.1 方案：probe → commit 固定点

不先建显式图，而是对每个模块级 `let`/`const` 做两段：

```text
probe（无副作用）：
  解析初值，判断它依赖的常量是否已 READY
  - 全部就绪 → ready
  - 有未就绪 → defer（不报错）
  - 真错误（类型/语法/非法引用）→ 报错

commit（正常解析）：
  对 ready 的声明走现有 parse_global_init，真正求值/发射
```

每轮扫描模块全部文件的全部全局声明：

```text
while 有 pending:
    progress = false
    for 每个 pending 的模块级 let/const:
        probe
        if ready: commit; pending -= 1; progress = true
    if !progress: 报循环依赖并停止
```

- 独立声明保持源码顺序（稳定输出）。
- 先 commit 的常量把 `const_ready` 置位，下一轮 probe 即可通过。
- 跨文件：外层按模块文件表迭代，不按单文件顺序。
- 不要求显式类型：类型推导（I3）先给出 `tid`，S1 负责值顺序。

### 4.2 probe 的副作用抑制

复用类型推导计划的 `c_type_probe`，并扩展为 `c_defer`/`c_global_probe`：

- 字符串：不分配标签。
- `sem_ident_val` 常量：
  - 已 ready → 正常类型/值；
  - 未 ready 且是模块级常量 → 置 defer，不报错；
  - 未 ready 且不是可调度常量（如 CT 中间态）→ 保持原诊断。
- 结构体/数组字面量：只算类型/依赖，不写数据。
- `sizeof`/`len`：只算类型，不要求布局值。
- 普通函数调用：取返回类型；不执行。
- `$` 初始化：
  - 已有显式类型的 `$` 初始化沿用现有 CT/全局路径，不由 S1 直接 probe；
  - 推断类型的 `$` 初始化首版要求显式类型；
  - S3 再把 `$` 调用与 CT 函数体依赖统一纳入调度。

probe 失败/延迟必须可回滚：只解析、不写 AST、不写数据表、不写符号值。

### 4.3 commit 顺序与布局

- `MB_PASS2_GLOBALS` 改为模块级调度器，而不是每文件 `parse_source_globals`。
- 对每个 ready 声明：恢复文件快照、设置 token 游标到 PDecl、正常 `parse_top_decl`。
- 布局（数组长度）仍在全局初始化之前；布局调度已经能按需求值常量。
  若某常量只被值初始化使用，S1 调度器负责；若被类型布局使用，layout 负责。
- 常量同时被布局和值使用：两边都走 `const_ready`，先到先得，后到复用。

### 4.4 诊断

- 循环：
  `循环依赖: B -> A -> B`，每个节点带 `file:line:col` 与声明种类。
- 未就绪但无法调度（例如引用了 CT 内部值）：
  `常量初始化依赖无法在编译期求值: ...`
- 真错误保持原诊断位置。

## 5. S2：类型声明前向引用

### 5.1 现状

`parse_type_ref` 立即 `check.type_resolve`；未知类型直接报错。要允许前向类型，
必须让“类型名可见”早于“类型布局完成”。

### 5.2 推荐路径：依赖排序后解析

在 S4 纯语法解析（`AstType` 已外置）基础上：

1. 预扫描模块全部顶层类型声明（PDecl 索引已有）。
2. 提取每个类型声明的类型名依赖（只看类型位置的标识符；跳过字段名/成员名）。
3. 对类型声明做稳定拓扑排序（同层保持源码顺序）。
4. 按排序解析类型声明：先解析被依赖的 `B`，再解析 `A`，现有
   `parse_type_ref` 不需要支持占位类型。
5. 解析完全部类型后，再按源顺序登记全局/函数符号。

这样不需要在类型表里引入 pending 类型，也不需要改布局/ABI 快照格式。

依赖提取的保守策略：

- 无法确定是否为类型引用时，宁可加边；若因此形成假循环，退化为“请调整声明顺序”。
- 字段名、结构体字面量字段、成员访问名不算依赖。
- 数组长度里的常量是“类型 → 值”边；S1/S2 交界处按需先求值常量，
  或继续交给 layout 调度（数组长度延迟）。

边界（S2a/S2b 拆分）：

- **S2a**：只支持结构/别名/枚举字段里的**类型名前向引用**，不改变数组长度
  的常量求值路径。类型里的 `[N]T` 仍要求 N 的符号已可延迟求值。
- **S2b**：预登记顶层 const/let 名称（占位类型）后再解析类型，让类型里的
  `[N]T` 可以引用后声明的常量；值与布局仍由 S1/layout 调度。
- 若 S2a 阶段某类型声明同时依赖后声明的 const，先给出
  “请显式调整顺序”诊断，不强行半解析。

### 5.3 备选：占位类型

在 `TName` 中登记 pending 类型并在解析后回填。更通用，但要动类型表、
布局、接口、缓存与 ABI，风险明显高于排序解析；除非排序方案无法覆盖
（例如类型别名互相引用成环但有合法指针语义），否则不采用。

### 5.4 顺序与诊断

- 类型定义成环：
  - 值语义（struct 按值包含自身）→ 报循环/无限大小；
  - 指针/切片间接环 → 允许（`struct A { b *B }`、`struct B { a *A }`）。
- 重复类型名、重复声明仍按原规则报错，位置用源码位置，不受解析顺序影响。
- 接口发射按排序后的稳定顺序，避免同一源码两次构建出现不同 `.s.i` 顺序。

## 6. S3：CT 函数与 `$` 调用依赖

S1/S2 只解决直接的类型/值引用；CT 调用会读取 CT 函数体内部的全局：

```yh
const A = 1
const B = $f()       // f 体内可能读 A
@[comptime] fn f() int { return A }
```

要“所有符号依赖”，S3 需要：

1. 把 CT 函数作为图节点；`$f()` 初值依赖 `f` 的函数体。
2. 提取 CT 函数体读到的模块级符号（复用 probe/依赖收集），形成传递边。
3. 与现有 `ct_value_requests`/layout 调度合并，避免重复执行和重复诊断。
4. CT 函数与全局互相依赖（`const A = $f(); fn f() { return A }`）→ 循环诊断。
5. S3 完成后再放开“模块级推断初值含 `$`”；首版在 S1 直接要求显式类型。

## 7. S4：接口、缓存与自举

- `.s.i`：类型/常量按依赖顺序或稳定排序输出；消费者按名字查找，不依赖顺序。
- `.s.ct`：CT 闭包也要稳定顺序；私有推断常量不得以未解析占位进入闭包。
- 缓存：输出内容变化只来自源码/依赖顺序，不来自调度随机性；同源码两次构建
  逐字节稳定。
- 自举：`compiler/` 源码在种子支持前不使用新语法；调度器本身用显式类型。
- 文档：编码规范增加“模块级声明顺序不参与语义”的规则与例外（pub 显式类型）。

## 9. 测试计划

### 9.1 S1

- `const B = A + 1; const A = 1` → 编译并运行，B == 2。
- 跨文件：`b.yh` 的常量依赖 `a.yh` 的后声明常量。
- `let g = A + 1`（全局变量）依赖后声明 const。
- 显式类型与推断类型各一份。
- 循环：`const A = B + 1; const B = A + 1` → 循环路径。
- 真错误（类型不匹配、非法运行期调用）仍报原诊断。
- 独立声明输出顺序稳定（连续两次构建产物一致）。

### 9.2 S2

- `struct A { b B }` 在 `struct B` 前 → 通过。
- 别名/指针/切片/数组元素/函数类型参数前向引用。
- 值语义自包含 → 报无限大小/循环。
- 指针间接环 → 通过。
- 数组长度引用后声明 const（与 S1 交界）。
- 接口 `.s.i` 顺序稳定。

### 9.3 S3

- `const B = $f(); @[comptime] fn f() int { return A }; const A = 1` 通过。
- CT 函数与常量互相依赖 → 循环诊断。
- CT 闭包/接口消费者零回归。

## 10. 风险与回退

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 调度顺序改变符号/数据标签/接口顺序 | 产物 diff | 稳定排序（同层源码序）；两次构建逐字节对比 |
| probe 有副作用 | 重复数据/错值 | 只读/无 AST/无数据表；probe 后断言状态未变 |
| 假循环（保守依赖边） | 合法代码被拒 | 依赖提取精确化；无法判定时给“请显式调整顺序”可操作诊断 |
| 类型排序解析改 pass1 结构 | 回归面大 | S2 单独阶段；先 S1；S2 以现有 S4 AstType 为基础 |
| CT 调度与现有 value request 冲突 | 重复执行/死锁 | S3 独立；复用现有 request 队列；预算与超时 |
| 公共 API 依赖推断 | 契约不稳定 | `pub` 仍强制显式；接口发射前断言无待解析类型 |
| 旧种子不认识新语法 | 自举死锁 | 调度器/编译器源码保持显式；新语法先只进测试 |

回退：

- S1 调度器可切回 `parse_source_globals` 源顺序（保留旧诊断）。
- S2 排序解析可按模块开关关闭，回退“类型必须先定义”。
- S3 CT 依赖独立开关，不影响 S1/S2。

## 11. 与类型推导方案的关系

- S1 是类型推导 I3 的**值依赖前置**：类型解析多轮解决 `B` 的类型，S1 解决
  `B` 的初值在 `A` 之后就绪。
- S2 让“类型声明顺序”不再影响类型推导/字段布局。
- S3 完成后，模块级推断初值可以重新允许 `$` 调用；首版仍按类型推导方案的
  决定要求显式类型。
- `pub` API 显式、`$any` 泛型、函数返回类型推导均不在本方案范围。
