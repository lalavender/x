# yh 编译器性能测试方案

日期：2026-10-23。状态：**方案提案，尚未执行性能测量或实施工具改造**。

目标：持续回答一次修改是否让 yh 编译更快、减少了哪些工作、是否增加内存，
以及生成程序的速度和体积是否退化。默认优先解决日常编译体验，其次评估代码质量。
性能测量独立于正确性门；本平台 `make test` 与 `make selfhost-native` 仍是前提。

## 1. 现状与建议

复用 [现有脚本](../../tools/compiler-performance.py)，扩展为版本对照工具，
首期采用 Python 标准库，不引入性能平台或数据库。

- 已有三种负载：`no-change`、`function-change`、`cold-build`，默认各 20 轮；
  有原始 JSON、median/p95、模块重编次数、部分阶段时间和单次子进程 RSS。
- [R0 冻结语料](../../tests/perf/corpus-r0/README.md)来自旧编译流程，适合保留历史
  对照；其中包含旧后端源码，不能作为当前 LLVM 编译器源码规模和结构的代表。
- 现有脚本的函数改动锚定 `cmd/project_state.yh`，行为断言写死 `yh 0.0.5`，
  `--corpus` 还不是通用项目入口。新增快照前先解除这些假设，不改写 R0。
- `--stats` 已输出 IR/check 缓存等字段，但脚本尚未将命中/未命中/跳过数纳入报告；
  仅记录“产生多少 IR 函数”不足以说明节省多少工作。
- PATH 包装器只看得到外部 gcc/clang 调用，看不到内嵌 LLVM/lld；包装器调用为零
  不表示没有对象生成或链接。当前调度上限是四个 worker，未发现通用 `-j` 参数。
- 工作区存在未提交实现，文档和源码中的缓存状态可能不同；测量时冻结实际二进制、
  输入与配置，以行为和计数为准，不能只记录 Git HEAD 或根据设计文档推断缓存已启用。

只用 `time make` 可做粗测，但混入种子选择、构建包装器和冷热状态，难以归因。
完整 LNT 服务留待样本、平台和趋势管理确有需要时再考虑。

## 2. 测试分成四组

| 组别 | 要回答的问题 | 主指标 |
| --- | --- | --- |
| 编译体验（首期） | 从命令启动到可用产物要多久？ | wall time、用户/内核 CPU 时间、median、p95 |
| 增量效率（首期） | 修改真正触发了多少工作？ | 重编模块、checked/lowered/emitted 函数数、缓存命中、对象生成/链接次数 |
| 资源与规模（第二期） | 并行或输入扩大后是否失控？ | 单进程峰值、进程树采样峰值、缓存大小、规模增长比 |
| 产物质量（第二期） | 生成的程序是否快且紧凑？ | 程序运行时间、校验结果、`.text`/只读数据大小、文件大小 |

编译体验的正式时间由外部单调时钟测量，包含进程启动、编译、对象生成和链接；
复制语料、恢复缓存、修改文件、结果校验均放在计时之外。生成程序的运行单独计时。

## 3. 基准语料

### 3.1 真实项目

1. 保留 `corpus-r0` 及其哈希，历史成绩标注旧负载、旧机器和旧工具链。
2. 在正确性门通过的明确源码状态上新增版本化 `corpus-llvm-v1`：冻结当前
   `compiler/` 的完整构建输入、依赖和清单，作为主要自编负载。
3. 增加一个小型多模块项目：入口、独立叶模块、依赖链、多个消费者，专门观察
   私有函数、公有接口、编译期依赖的失效范围；每种改动预先列出期望结果。

每套输入提交 SHA-256 清单，记录文件数、字节数、行数、模块/函数数。
语言升级导致输入不兼容时新增版本，禁止静默修订历史语料后续用旧成绩。
链接清单中的机器路径通过明确的环境绑定步骤在 `tmp/` 副本中解析，记录最终
清单哈希、归档身份和绑定规则；A/B 使用相同规则与依赖，不计入编译时间。

### 3.2 合成与运行语料

- 合成编译负载按 1×/2×/4×/8×增加函数数，另设模块数与依赖深度两条序列；
  每次只变一个维度，固定生成器版本和随机种子，记录实际输入规模。
- 分别覆盖大量小函数、大函数控制流、类型/名称查找、字符串、编译期计算。
  不把这些微基准的行/秒直接解释为所有项目的吞吐量。
- 运行基准首批选择整数循环、数组扫描、排序、字符串/哈希、结构体与切片传递、
  函数调用；只采用当前支持且语义明确的能力，不为基准扩展语言。
- 输入运行时传入，输出 checksum 并与参考答案比对，防止常量折叠或死代码删除
  让负载消失。调整输入使单样本约 0.5–2 秒，初始化是否计入由用例明确规定。
- 用例源文件统一 `.yh`，放 `tests/perf/`；涉及行为的新实现同时按仓库规则补
  `tests/yh-run/` 或 `tests/modules/` 验收。

## 4. 编译场景矩阵

| 场景 | 每轮准备 | 必须核验 |
| --- | --- | --- |
| 清构建缓存 | 删除该场景副本的 `.build` | 编译/对象缓存确实未命中，产物可运行 |
| 无改动 | 先完整构建，保留源码、缓存和产物 | 重编、对象生成和链接次数；预期可避免的工作单列 |
| 仅注释/空白 | 每轮在两份等价文本间切换 | 行为不变，哪些键被判定变化 |
| 私有函数体 | 同规模 A/B 函数体交替，接口不变 | 行为确实变化，依赖消费者是否重做，check/IR 复用范围 |
| 公有接口 | 修改签名/布局并同步必要调用点 | 所需消费者均失效，不误用旧接口 |
| 编译期依赖 | 改变被导入的编译期值或函数结果 | 传递依赖重新求值，结果与清缓存构建一致 |
| 缓存/产物缺失 | 分别移除函数缓存、对象或最终程序 | 按层恢复，不能把缺产物的成功退出当作命中 |

清构建缓存默认保留 OS 页缓存，准确命名为“清 yh 缓存构建”，不称首次磁盘冷读。
首次安装/LLVM 闭包准备是另一项工具链体验指标，单独记录，不混入编译基准。
损坏缓存、失败后重建等以恢复正确性为主，不参与速度综合评分。

首期每项跑 `-O0` 和 `-O2`，结果分别展示；预算有限时完整对照先跑 O0 的前三个
核心场景，再扩展 O2 和失效矩阵。运行语料也分别以 O0/O2 编译。
O0/O2 是被测负载的优化级别，被测编译器二进制自身的优化级别必须另记。

## 5. A/B 测量协议

1. A 是明确的基线二进制，B 是候选。两者由相同固定种子、LLVM 闭包、SDK、
   编译选项构建；记录种子和 A/B SHA-256。闭包准备、候选构建与正确性门均在计时外。
2. A/B 编译**同一冻结输入**，各用独立且固定的工作目录、缓存和输出。
   不让两个版本交替覆盖同一缓存；移除/归一化路径差异的规则也要固定。
   某版本不支持该输入时标记不兼容，不换另一份源码后继续计算速度比。
3. 每种热场景先做 2–3 次不计分预热。清缓存场景先预热文件读取，随后每个
   正式样本仍删除自己的构建缓存。先校验预热状态，再采样。
4. 快测各 5 轮用于检查工具和方向；正式对照各至少 20 轮。A/B 成对交错，
   每对的先后顺序用固定随机种子平衡，禁止只跑完 A 再跑完 B 作为最终证据。
5. 函数修改不能用“同一内容重复写入”代替真实改动。每对 A/B 接收相同方向
   的修改，恢复/修改两个方向分别保留标签，避免负载大小差异掩盖结果。
6. 每轮检查退出码、期望统计与产物行为；增量产物还需与同源码清缓存构建的
   结果对照。失败、超时、缺失统计均显式报告，该场景不得给出性能通过结论。
7. 保存全部原始值，计算 median、p95、MAD 和相对基线变化。
   `变化率 = (候选 median / 基线 median - 1) × 100%`，耗时为负表示改善。
8. 20 轮的 p95 只作描述，不用于稳定的尾延迟承诺；尾部问题另采至少 100 轮。
   不自动删去慢样本；负载干扰导致整批无效时保留原报告、标注原因并重跑。

外部正式计时默认关闭诊断输出；另跑相同状态的 `--stats` 样本供归因。
先对比开关统计的开销，确认足够小时才允许合并采集。深度采样 profiler 单独跑。

## 6. 阶段归因与内存口径

先利用现有 project/schedule/objects/link 时间，补采 cache hits/misses、
`checked_functions`、`ir_lowered`、`backend_emitted_functions`、worker 峰值。
先核对计数语义，区分受检覆盖总数、实际执行 check 的函数数和复用数；
覆盖数不能直接当作本轮重新检查的工作量。
再按实际函数边界增加以下区间，必要时第一步将前端合并计时，避免为拆词法/语法
而重构生产流程：

`装载与索引 → 前端检查 → check/IR 缓存读取与恢复 → lowering → LLVM IR 构造
→ LLVM 优化 → 对象生成 → 链接`

- 每条记录标明进程、模块、区间和时钟，缺失字段写“不支持”，不能默认为零。
  统计解析采用可扩展 key=value 字段，而非依赖整行固定顺序的大正则。
- 父进程 schedule 可能包含等待 worker；它与 worker 时间有重叠。
  分开报告父进程时间线、worker 累计工作量及最长模块，不能全部相加当总耗时。
- 阶段计时先定义 inclusive/exclusive 关系。只有同一条时间线的互斥区间
  可以相加；保留启动、等待、I/O 等未归因时间，不强行凑齐百分比。
- 现有 RSS 明确标为“最大单个子进程 RSS”，不视为并行构建总内存。
  Linux 可用独立 cgroup 的峰值指标；不可用时采样进程树 RSS 并注明采样间隔、
  可能漏峰值、共享页重复计入等局限。cgroup 内存还可能包含页缓存，二者不混比。
- 首期按现有四 worker 调度测量并记录实际并发；1/2/4 worker 的扩展性实验
  留到有明确并发控制入口后实施，不编造当前不存在的 CLI 选项。

## 7. 环境、平台与报告

固定 CPU/内存、OS、工具链、SDK、target triple、电源模式、worker 数和存储布局。
运行时避免其他构建和 CI 并发；资源繁忙则排队。Linux 与 Darwin 各自维护基线，
跨机器、跨架构结果分开展示，不计算统一“更快百分比”。

遵守本地/CI 分工：本机 Darwin 原生先建立本平台基线；Linux 原生趋势交给其
固定 runner/CI。使用 Apple Container 的结果标注镜像 digest、资源限制和挂载方式，
不能当作独立 Linux 裸机结论；模拟 x86_64 只作兼容性证据，不参与原生性能排名。
闭包复用 `tmp/llvm-migration` 或 `$YH_LLVM_CACHE`，不得作为冷编准备步骤删除。

原始产物统一放 `tmp/perf/<run-id>/`，CI 上传为报告资产。每次包含：

- 元数据：源码提交、dirty 状态及源码清单哈希、种子/A/B 哈希、编译器构建选项、
  负载哈希、目标选项、工具链/闭包/SDK 身份、机器与容器信息、测量顺序和随机种子。
- 原始样本 JSON、独立日志、失败/超时与有效性状态，记录格式版本与时间/内存单位。
- 汇总 Markdown：每场景 A/B median、p95、MAD、变化率、内存、重编范围、缓存统计。
- 产物报告：checksum、运行时间、`.text`/只读数据和文件体积；统一符号/调试信息
  选项。编译器静态链接 LLVM 带来的体积单列，避免用整个文件大小代表代码质量。

所有场景逐项展示；运行基准可补充耗时比的几何平均，但不得用综合分掩盖单例回退。
可选 C/Clang 参考仅比较同算法、输入、校验与目标设置的运行程序，不能据此概括
两种语言的编译速度；首期优先完成 yh 自身版本间对照。

## 8. 回归策略与目标

先连续建立稳定基线，只出报告，再决定性能硬门。以下是**建议初值**，需要实测
噪声校准，不表示已经达到或已经接入 CI：

- 编译/运行 median 慢于基线 5% 标记待复测；内存或代码段增加 10% 单列提醒。
- 对疑似回退增加采样，计算成对耗时比的 bootstrap 95% 置信区间；只有区间下界
  超过 1.05，且独立第二批重现，才确认“耗时回退超过 5%”。否则标记证据不足。
- 正确性失败立即判该测试无效，不因速度改善而通过；预期缓存计数不符也要归因。
- 稳定后可将高信噪比核心场景接为独立性能检查。普通 CI 的噪声提醒不阻塞本地迭代；
  回退按仓库约定进入 todo。

历史无改动 50 ms、单函数修改 200 ms、冷编 1 s 作为待复核目标保留。
这些数值必须绑定语料版本、平台、优化级别与缓存定义；不能直接套用到源码规模
已经变化的 LLVM 自编负载，也不能把 IR 缓存命中等同于已达到 200 ms。

## 9. 分阶段实施与验收

| 阶段 | 工作 | 可核验的完成条件 |
| --- | --- | --- |
| PF0 固定口径 | 确定 A/B、当前 LLVM 冻结输入、小项目与修改补丁；记录环境/依赖 | 哈希可核验；A/B 在相同输入上可构建；每种修改有可观察结果 |
| PF1 最小对照 | 扩展现有 Python 工具，去掉版本/项目硬编码，保留原始值，补缓存统计与 A/B 交错 | O0 三个核心场景各 20 轮；失败不出通过结论；JSON/Markdown 可追溯 |
| PF2 定位瓶颈 | 增加 LLVM 边界计时、内存口径、接口/编译期失效矩阵和 O2 | 时间重叠解释清楚；增量结果与清缓存一致；产物/内部对象计数不依赖 PATH 包装器 |
| PF3 规模与产物 | 合成规模序列、运行内核、代码段/缓存大小；有并发入口后再扫 worker 数 | 输出参考校验通过；各规模有输入清单；O0/O2 编译时间与运行收益可同时比较 |
| PF4 持续回归 | Gitea 独立性能任务、资产归档、基线选择和复测策略 | 同机两批可重现；阈值由噪声校准；平台分开；回退有样本和归因 |

建议先只落 PF0/PF1，拿到当前三场景的真实对照，再按耗时决定 PF2 优先埋点位置。
不预设前端、LLVM 或链接一定是主要瓶颈，也不把 RS2/RS3/线程池作为性能测试的前提。
涉及工具或编译器行为的实施轮次需补相应验收与 `.yh` 语料，并执行本平台构建/全门。

## 10. 方法参考

- [LLVM Benchmarking tips](https://llvm.org/docs/Benchmarking.html)：重复测量、控制环境噪声，
  且低噪声本身不排除偏差；本文据此采用固定环境和成对交错方案。
- [LLVM test-suite Guide](https://llvm.org/docs/TestSuiteGuide.html)：同时关注编译时间、
  程序运行时间、代码体积，并用参考输出检查结果。
- [Hyperfine 官方说明](https://github.com/sharkdp/hyperfine)：预热、每轮准备及原始数据导出
  可作独立复核手段；首期沿用现有 Python 工具，无需额外安装。
