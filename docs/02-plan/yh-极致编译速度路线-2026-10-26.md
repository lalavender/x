## 2. 时间去向

### 2.1 已测部分

```
冷编 10.3 s
├── schedule 8.2 s   ← 父进程调度墙钟；worker 内的 lex/parse/sem/check/lower/SSA/LLVM 全在这里
├── object  0.5 s    ← 父进程对象收尾
└── link    1.1 s    ← 内嵌 lld 全量重链（10.7%）
```

`schedule` 是**墙钟**，包含 4 个并发 worker 的全部工作。也就是说冷编的 CPU 时间远大于
10.3 s，而其中**前端与 LLVM 各占多少，至今没有测量**。

### 2.2 未测部分（盲区）

`docs/todo.md` 的 PF2「LLVM 阶段归因」一直未做。缺的是 worker 内这一串的分段计时：

```
worker 启动 → sem_init_tables/front_prepare → 依赖 .s.i/.s.ct 文本解析
  → 每文件 decl_index_file + ast_decl_add_file → pass1 → ast_decl_bind_file
  → pass2a/2b → check 切片读写 → lowering → IR 序列化 → LLVM 文本生成
  → 桥调用（parse + verify + passes + codegen）→ 对象原子写
```

**在 SP1 完成之前，本文所有排序都是结构推断。** 这一点必须写在最前面，避免后续
用"预估收益"代替实测。

### 2.3 从代码结构可确定的成本项（按可疑度）

| 项 | 证据 | 为什么可疑 |
|---|---|---|
| LLVM 文本 IR 往返 | `bridge.c:149–151` 用 `LLVMCreateMemoryBufferWithMemoryRangeCopy` + `LLVMParseIRInContext` | 后端先拼出 LLVM 文本（MB 级），再由 LLVM 重新词法+语法解析，纯重复劳动 |
| 每 pass 后验证 | `bridge.c:186` `LLVMPassBuilderOptionsSetVerifyEach(options, 1)` | 官方默认 0；开 1 等于把 verifier 插进管线每一步 |
| 双次 VerifyModule | `bridge.c:152`、`bridge.c:192` | 加上 VerifyEach，实际上同一模块被验很多遍 |
| 每模块新建上下文与目标机器 | `bridge.c:141` `LLVMContextCreate()`、`bridge.c:163` `LLVMCreateTargetMachine(...)` | 13 个模块 = 13 次 target machine 初始化；CPU 固定 `"generic"` |
| 函数缓存每函数一文件 | `ssa_module_40_function_cache.yh:11` `<key>.fir` | ~1,400 函数 → 每次全量重编写 ~2,800 个小文件（`.fchk`+`.fir`）+ 2 份 index |
| worker 重复初始化 | `module_worker.yh:153 sem_init_tables`、`:154 front_prepare`、`:179/:190` 加载全部依赖接口 | 13 个 worker 各做一遍；fork/COW 本可共享 |
| 每文件 4 趟前端 | `module_worker.yh:199` `decl_index_file` + `ast_decl_add_file`、`:213` `pass1_file`、`:220` `ast_decl_bind_file`，再 pass2a/2b | 同一 token 流被走 4 遍，V 是单趟 |
| 调度上限 4、调度单位模块 | `build_scheduler.yh:403` `active < 4` | 最大模块 `parse`（9.7k 行）决定墙钟下限 |
| 全量哈希源文件 | `mb_hash_file` 遍历模块全部源 + 依赖接口 | 编译器指纹已改成 size+mtime，源目录没有 |
| 冷编删 `.build` | `justfile:178` | 日常改一行 = 丢掉全部缓存 |

## 3. 天花板模型（为什么"LLVM 不是借口"）

三个事实放在一起：

1. **`clang -O0` 单核吞吐约 300k 行/秒**（250k 行的 SQLite 合并文件约 0.6–1 s 完成
   预处理 + 解析 + IR + O0 codegen）。yh 是 4.9k 行/秒 —— 差 **60 倍**，LLVM 本身
   显然不是主因。
2. yh 的 LLVM 用法比 clang 多做了：**文本 IR 生成 + 再解析、每 pass 验证、每模块一套
   Context/TargetMachine、13 次进程初始化**。这些都是 clang 一次都不做的事。
3. 前端方面 yh 对每个文件走 4 趟，但前端是纯 yh 代码、无 malloc 密集型 IR 构造，
   在 53k 行规模上不可能是秒级主力。

由此得到三档天花板：

| 档 | 关键动作 | 估算墙钟 | 差距来源 |
|---|---|---:|---|
| **Tier 1** 工程优化（SP3–SP11） | 去 VerifyEach、复用 TargetMachine、批量桥、冷编不写缓存、一次性 worker 初始化 | **冷编 5–6 s** | 重复劳动 |
| **Tier 2** 粒度与并发（SP12–SP16） | `-j`、文件级调度、`--fast-link`、默认增量 | **冷编 2–3 s；单函数 0.8–1.2 s** | 调度与缓存粒度 |
| **Tier 3** 直出后端（SP17） | AST → 机器码，无 LLVM/IR/verifier | **冷编 0.2–0.5 s** | 架构（等同 V 的做法） |

结论：**J5（1 s）落在 Tier 2 的下沿，很紧但可达；V 的绝对值需要 Tier 3。**
Tier 3 正是 LL12（2026-10-21）退役的那条路（`compiler/` 净减 6,516 行，
见[完成报告](../01-finished/yh-LL12退役旧机器发射-2026-10-21.md)），所以本文
**不建议**在 Tier 2 达标前重启直出后端 —— 先拿到 4–5 倍再决定是否要再拿 5 倍。

## 4. 优化项（SP1–SP17）

约定：每项给「改哪里 / 怎么改 / 预估 / 验收 / 风险」。**预估一律是上界**，
SP1/SP2 完成后统一按实测重排。

### 阶段 A：先量（阻塞其他一切）

#### SP1 worker 内分段计时（PF2）

- **改哪里**：`build/module_worker.yh`、`build/module_build.yh` 的 `mb_stats`、`gen/state.yh` 加计时字段。
- **怎么改**：在 worker 里用 `cmd_clock_ns()`（`build/clock.*`，已有）打点，分成 9 段：
  `init / iface_load / decl_index / pass1 / pass2 / check_slice / lower / ir_ser / llvm_text / bridge / obj_write`。
  输出到 `--stats` 行（现有 `c_stats_*` 已是计数字段，加用户时间与墙钟两组），
  worker 与父进程都打，`tools/perf-baseline.py` 已按「取每列最大值」聚合，直接可用。
- **验收**：`just build --stats` 输出 11 段耗时；四场景各 3 轮，报告落 `tmp/perf/`。
- **风险**：无（只加计时）。

#### SP2 口径固定

- **改哪里**：`tools/perf-baseline.py`。
- **怎么改**：把 SP1 的新列纳入报告；每轮记录 load1；冷编 / 全量重编 / 热编 / 单函数
  四场景**禁止互相混测**（PERF 方案已要求）；A/B 用 `--ab` 成对交错。
- **验收**：同一二进制连测 3 轮，各列 median 波动 <10%。
- **风险**：无。

### 阶段 B：不改语义的工程优化（一次固定点验证可合并提交）

#### SP3 关掉 verify-each

- **改哪里**：`compiler/llvm/bridge.c:186`。
- **怎么改**：`LLVMPassBuilderOptionsSetVerifyEach(options, 0)`；保留
  `getenv("YH_LLVM_VERIFY_EACH")` 作 debug 开关。前置的 `LLVMVerifyModule`
  （`:152`）与后置验证（`:192`）**保留** —— 那是每次构建一道的便宜保险。
- **预估**：冷编 −5~10%。
- **验收**：`just test` + `just selfhost-native` 全绿；`YH_LLVM_VERIFY_EACH=1` 时行为与今天一致。
- **风险**：低。verifier 覆盖面下降，由前后两次 VerifyModule 兜住。

#### SP4 复用 TargetMachine / TargetData / Context

- **改哪里**：`compiler/llvm/bridge.c:141/163`。
- **怎么改**：进程内静态缓存，键 = `(triple, opt_level, reloc)`。
  `LLVMContextCreate` 保留每模块（context 间的 module 不能共享，改动风险高），
  但 Target/TargetMachine/TargetData 全局建一次。注意 **lld 与 LLVM 共用进程**时
  线程安全性：自举是 fork 出来的单线程 worker，安全。
- **预估**：冷编 −5~15%（13 次初始化 → 1 次）。
- **验收**：同一模块编译产物逐字节一致（`.o` 比对）；固定点不变。
- **风险**：低。

#### SP5 单次桥调用处理整个项目（可选，收益最大也最贵）

- **改哪里**：`llvm/bridge.h` 新增批量入口；`build/llvm_pipeline.yh`。
- **怎么改**：一次 `LLVMParseIRInContext`（把全项目 IR 拼成一个 module 或按 module
  数组）+ 一次 pass 管线 + 逐 module `LLVMTargetMachineEmitToFile`。
  省掉 N−1 次 context/target 初始化与 N−1 次 parse 固定开销。
- **预估**：冷编 −10~20%。
- **风险**：中 —— 与「一模块一对象」的产物契约冲突，必须保留按模块输出的能力
  （批量入口作为可选路径，默认仍按模块调用）。
- **建议**：**放在 SP3/SP4 之后**，因为它与 SP15（`--fast-link` 单对象）有重叠，
  先看前两项实测再决定做不做。

#### SP6 冷编不写函数缓存

- **改哪里**：`build/module_build.yh` 冷编路径、`build/function_ir_cache.yh`。
- **怎么改**：PC3 已让冷编写入 `.fir = 0`，但 `.fchk`（check 切片）与 capture 仍在。
  冷编（`.build` 不存在）时把 `c_ast_capture` 与 `.fchk` 提交一并关闭，只在**增量**
  构建时写。判据用现有「`.build` 是否已存在」即可，不引入新状态。
- **预估**：冷编 −0.5~1 s（`finish.md:422` 的差异证明 capture 成本在 10 s 量级）。
- **验收**：冷编后热编仍命中（不能把热编变成全量）；`--stats` 显示冷编 `.fchk` 写入 0。
- **风险**：低。

#### SP7 函数缓存格式：每函数一文件 → 每模块一文件 + 内存索引

- **改哪里**：`ir/ssa_module_40_function_cache.yh`（格式）、`build/function_ir_cache.yh`（I/O）、
  `IR_FUNCTION_CACHE_VERSION` 递增。
- **怎么改**：一个模块一个追加容器：32 字节头 + `[count][key,offset,length]*` + payload 区。
  写：一次 `write_all`；读：一次 `read` + 内存扫描。文件数从 ~2,800 降到 13（每模块
  一个 `.firc`，替代 `.fir`+`index` 两份）。
- **预估**：全量重编 **16.1 → 11 s 左右**（−30%）；冷编 −0.5 s（少 2,800 次 create/rename）。
- **验收**：`tests/selfhost/llvm-function-cache.py` 全绿；缓存命中数与改前一致；
  `IR_FUNCTION_CACHE_VERSION` 升版后旧缓存能识别并重建。
- **风险**：中（缓存是固定点敏感区），必须单独提交、单独滚种子。

#### SP8 依赖接口由父进程解析一次

- **改哪里**：`build/module_worker.yh:179/190`、`build/build_scheduler.yh`。
- **怎么改**：fork 之前父进程把全部依赖 `.s.i` / `.s.ct` 解析进只读表，worker 通过
  COW 直接可见，删掉每个 worker 的 N 次 `iface_load`。
  这正是 fork/COW 的既有优势（[架构设计 §1.4](../03-design/yh-架构设计.md)
  的另一半价值），且不依赖 LA5 线程池。
- **预估**：冷编 −5~10%。
- **验收**：13 模块构建，`--stats` 里每 worker 的接口加载次数 = 0；产物逐字节一致。
- **风险**：中（接口表要真正只读；`iface_load` 现在会写 `c_syms` 等可变区，需先把
  加载与绑定分离）。

#### SP9 `sem_init_tables` + `front_prepare` 提到 fork 之前

- **改哪里**：`build/module_worker.yh:153/154`、`build/build_scheduler.yh`。
- **怎么改**：同 SP8 的手法，把与模块无关的初始化前移一次。
- **预估**：冷编 −3~5%（13 次 → 1 次）。
- **风险**：低。
- **依赖**：SP8 同源，建议合并成一个「worker 冷启动收敛」提交。

#### SP10 源文件哈希用 size+mtime 短路

- **改哪里**：`build/module_build.yh` 的 `mb_hash_file` 调用点、`mb_mix_file_identity`（已对编译器二进制做了）。
- **怎么改**：模块源文件哈希键改成 `(size, mtime_ns)`，内容哈希只在 identity 变化时重算；
  目录级 mtime 未变可整棵子树跳过。
- **预估**：冷编 −0.2~0.5 s。
- **验收**：改一个文件后必须判脏（mtime 精度陷阱：NTFS/ext4 都是 ns，但要处理
  同一 tick 内两次写入的测试用例）。
- **风险**：中（假阴性会让增量构建产物错误），必须有专门回归用例：
  「同 size、改内容、不换 mtime」必须判脏。

#### SP11 `yh check` 快路径

- **改哪里**：`build/module_build.yh` 的 `mb_cmd_check`、`build/llvm_pipeline.yh`。
- **怎么改**：`check` 只跑到 `CheckedModule + check.verify`，**不碰 lowering / IR /
  LLVM / 缓存写**（现在虽然用独立目录但仍走完整前端与切片）。
- **预估**：语法/语义反馈 <0.3 s（编辑-检查回路）。
- **风险**：低。注意 `check` 的既有语义（"检查当前项目全部模块的语义"）保持不变。

#### SP12 默认增量（需用户拍板）

- **改哪里**：`justfile:466` `_ensure_built`、`AGENTS.md`。
- **怎么改**：`_ensure_built` 走 `dev`（不删 `.build`），`just build` 保留冷编。
- **预估**：日常回路 **11 s → 1–4 s**（体感收益最大、成本最低的一改）。
- **验收**：连续两次 `just` 第二次 <2 s；固定点门仍用显式 `just build`。
- **风险**：低，但**与 `AGENTS.md` 现约定冲突**（现写「`just` = 冷编」），需用户决定后修文档。

### 阶段 C：粒度与并发

#### SP13 `-j` 参数 + 提高并发上限

- **改哪里**：`build/build_scheduler.yh:403`、`cmd/driver.yh`。
- **怎么改**：`active < 4` → `active < gs.c_jobs`，`-j` 缺省 `min(核数, 模块数)`。
- **预估**：8 核冷编 −20%（−5~8 s）；代价峰值内存 490 → ~800 MB（已有实测）。
- **验收**：`-j1` 与 `-j8` 产物逐字节一致。
- **风险**：低。

#### SP14 调度单位从模块降到文件（需 LA4）

- **改哪里**：`build/build_scheduler.yh`、`build/module_worker.yh`、LA4 的文件对象键/提交协议。
- **怎么改**：现在对象**已经**是按文件发射（`module_build.yh:439` `mb_module_obj_row`：
  「每模块 N 个文件 + 1 个运行时桩」），但**缓存与提交仍以模块为单位**，所以改一个
  函数仍要整模块 lowering + 整模块 LLVM 发射。
  前置是 `docs/todo.md` 的 **LA4.1–LA4.4**（分区模型 → hidden 私有身份 → 文件对象键/
  manifest/原子提交 → 删除/重命名/并发回归）。
- **预估**：**单函数改动 3.59 → 0.8–1.2 s**（T-1 达标的关键）。
- **验收**：`tests/selfhost/llvm-function-cache.py` 矩阵 + 新增「改 1 函数只重编 1 文件对象」计数断言。
- **风险**：高（跨对象私有符号、删除/重命名、并发提交都是硬骨头）。
- **依赖**：Module 拆分（MD12 类型 placeholder 前置登记）会大幅降低这里的难度。

#### SP15 `--fast-link`：自举场景单对象直链

- **改哪里**：`build/link_cache.yh`、`build/llvm_pipeline.yh`。
- **怎么改**：整项目合并成**一个** LLVM module 一次发射，链接输入从「119 个按文件对象
  + 桩」降到 1–2 个。
- **预估**：link **1.1 → 0.3 s**；LLVM 侧省掉 12 次 context/target 初始化。
- **风险**：中。与 SP14 直接冲突（一个要粗粒度为了链接快，一个要细粒度为了增量快），
  所以**按场景二选一**：`--fast-link` 用于 `just`/测试/CI，文件对象用于 `-j` 增量。
- **建议**：与 SP5 合并设计（同一个"批量桥"入口）。

#### SP16 LA5 线程池替代 fork/COW

- **改哪里**：按[架构设计 §1.4/§4.5](../03-design/yh-架构设计.md)收口 `FrontendTask`/`AstStore`/`CtContext`/`CacheContext`/`Diagnostics`。
- **预估**：每模块省 fork+COW+初始化的固定开销，冷编 −0.3~0.5 s；主要价值是让 SP8/SP9
  的"共享只读快照"变成默认形态而不是特例。
- **风险**：高（线程安全），最后做。

### 阶段 D：决策点

#### SP17 是否重建直出后端

- **触发条件**：Tier 2 达标（冷编 ≤2.5 s、单函数 ≤1.2 s）**之后**仍要求 <0.5 s。
- **内容**：评估 `-backend fast`（AST → 机器码，无 IR/verifier/LLVM），
  对照 LL12 的退役教训（净减 6,516 行、`--backend legacy` 一刀拒绝）。
- **明确不默认启用**：直出后端只用于日常迭代与自举引导，发布产物仍走 LLVM O0/O2，
  否则等于把 LL12 撤销。
- **本文不承诺工期**，只登记为决策点。

## 9. 追加分析：`ir/` 的 SSA 层还有没有必要（2026-10-26）

起因：用户问「当前的 SSA 还有没有必要实现？生产 LLVM IR 他本身是不是有优化」。
结论：**SSA 形式必须保留；`ir/` 的落盘序列化与函数级缓存需要重新评估。**

### 9.1 两个「S」必须拆开看

| | 内容 | 位置 | 判决 |
|---|---|---|---|
| ① **SSA 形式**（基本块 + phi + 支配） | phi 建点、break/continue 合流 | `lower/module_snapshot_lower_flow.yh:154` | **不可省** |
| ② **yh 自有 IR 层**（数据模型 + 验证 + 序列化 + 缓存） | 10 文件 5,005 行 | `compiler/ir/` | **部分该砍** |

①为什么不可省：LLVM IR **要求输入为 SSA**。替代方案是「全 `alloca` + `load/store`，
交给 `mem2reg` 提升」，但 mem2reg 属于 **-O1 以上**管线；yh 默认 `-O0`
（`gen/state.yh:279`），O0 不跑 mem2reg → 产出全栈访问的劣质 IR。**自建 SSA 是正确选择。**

### 9.2 「LLVM 有优化」与 yh 的 IR 层不重叠

1. yh 默认 O0，`bridge.c:184` 的 `default<O0>` **没有任何真正的优化 pass**；
2. 更糟：clang 在 -O0 给函数打 `optnone` 让管线跳过，**yh 的用户函数没有**
   （只有运行时包装函数有，`backend/llvm_runtime.yh:90`），所以 O0 管线真的在跑（SP18）；
3. yh 自己的 IR 层**优化代码为 0 行**——`ir_simplify` 已随 A0e 删除、
   `ir/ssa_inline.yh`（283 行）已随 A0b 删除。

因此「LLVM 会优化」既不能成为**保留** IR 层的理由，也不能成为**删除**它的理由：
两者优化的是不同层面的东西（LLVM 优化 IR 上的代码质量；yh 的 IR 层提供可验证、
可序列化、目标无关的中间契约）。

### 9.3 `ir/` 5,005 行的实际构成

| 文件 | 行数 | 性质 |
|---|---:|---|
| `ssa_module_30_serialize.yh` | 998 | 序列化 |
| `ssa_module_40_function_cache.yh` | 618 | 函数缓存 |
| `ssa_module_50_function_rebind.yh` | 383 | 缓存重绑定 |
| `ssa_serialize.yh` | 372 | 序列化 |
| `ssa_module_20_verify.yh` | 511 | 验证 |
| `ssa.yh` | 859 | 数据模型 + verifier 基础 |
| `verify.test.yh` | 733 | 测试 |
| model / build / call | 531 | 构造辅助 |

**序列化 + 缓存 + 重绑定 = 2,371 行（47%）只为「把 IR 落到磁盘再读回来」存在。**

### 9.4 关键事实：函数缓存的有效窗口 = 单个种子二进制

`firc_env_key`（`build/function_ir_cache.yh:263`）混入 `c_ir_cache_salt`，
而 `gen/state.yh:237` 注释写明它是「父构建器传入的**编译器二进制指纹**」，
指纹来自 `mb_mix_file_identity`（`build/link_inputs.yh`）= `(size, mtime_sec, mtime_nsec)`。

| 场景 | 缓存是否有效 |
|---|---|
| 同一种子 + `just dev` 日常回路 | **有效**（单函数改动 3.59 s 里「IR 204 命中」的来源） |
| `just seed` 滚种子后 | **全部失效** |
| `just selfhost-native`（cc2→cc3→cc4，三个二进制） | **每代全部失效**，三代各写一遍 ~2,800 个文件 |
| 换机器 / CI | 全部失效 |

即「每代编译器只写一次、几乎读不到」。而自举门与 CI 恰是多代构建 ——
那 5.8 s 在那里是**纯成本**（并且跨代复用缓存本就不该允许，否则会掩盖 lowering 改动）。

### 9.5 处置建议（代价递增）

| 步 | 动作 | 收益 | 风险 |
|---|---|---|---|
| **1（先做，SP20）** | **A/B 判定**：加开关关掉函数缓存落盘，20 轮测「单函数改动」与「全量重编」 | 用实测终结「`.fir` 命中值不值」的猜测 | 零（开关） |
| **2（SP21）** | 若不值：**IR 只做进程内中间表示**，增量完全依赖模块级对象缓存（manifest 短路，热编 0.98 s 即来自它） | 吃掉 5.8 s 写成本；`ir/` 从 5,005 → ≈2,600 行，`compiler/` 减 ≈2,400 行 | 低（删代码） |
| **3（SP7）** | 若值（用户项目场景确实命中）：改成每模块一个追加文件 + 内存索引，文件数 2,800 → 13 | 保收益、砍 I/O | 中（固定点敏感区） |

**保留项（三条理由都要写进 ADR）**：① 验证边界——`ir_module_verify` 是自举时唯一
可读的错误边界（LLVM verifier 报错无源位置）；② 后端隔离——`backend/` 只吃
`IRModule`，`gen.G()` 读点为 0，也是 SP17 直出后端的唯一复用点；
③ 1,390 行的数据模型本身不贵。

## 10. 对标：Zig 的编译速度是怎么做到的（2026-10-26 追加）

起因：用户问「zig 的编译速度是如何优化的」。这里只记**与 yh 可对照的部分**，
不评价 Zig 语言本身。

### 10.1 先分层，否则会误判

| 层 | 内容 | 量级 | 关键 |
|---|---|---|---|
| ① **无操作构建**（`zig build` 无改动） | 内容哈希 manifest 短路 | **0.05–0.2 s** | 什么都没发生 |
| ② **调试构建**（`-fno-llvm`，自研后端 + 自写对象/链接） | 不碰 LLVM、不经汇编文本 | 数千–数万文件/秒 | 代码质量低 |
| ③ **LLVM 构建**（ReleaseSafe/Fast） | 内存内构造 LLVM IR → LLVM 优化 → 出对象 | **与同规模 clang 同量级，不快** | 公平对照 |

**"Zig 很快"的印象主要来自 ① ②，不是 ③。** 对标时必须说清是哪一层，否则会得出
"只要照 Zig 做就能 1M 行/秒"的错误结论。

### 10.2 六个手法与 yh 现状

| # | Zig 做法 | yh 现状 | 判定 |
|---|---|---|---|
| 1 | IR 全在内存，从不落文本（C API 构造，同一 module 句柄给优化与后端） | 后端拼 LLVM **文本** → `bridge.c:149` 再解析 | 可抄（代价 = 重写后端构造，同 SP5 的彻底形态） |
| 2 | **ZIR 二进制缓存，每文件一份**（粒度对齐"输入单元"） | 函数级 `.fir`，**每函数一文件**（~2,800/次全量） | 可抄，粒度改为**文件**，与"每文件对象"天然对齐 |
| 3 | 内容寻址 build manifest，未变即跳过整条链 | 已有（热编 0.98 s 即来自它） | **已是 yh 最成熟的一块** |
| 4 | Sema **惰性**：只分析被引用的 decl | `pass2b` 走全部函数（有 check 缓存，语义仍全量） | 可抄；对库/大项目收益大，对自举程序收益有限 |
| 5 | 自写后端 + 自写对象/链接（不经汇编文本、不调外部 ld） | LLVM 出 `.o` → 内嵌 lld 链接 | 可抄但成本高（= SP17） |
| 6 | 单进程 + 线程池 + 全局 **InternPool**（hash map，一处分配一次释放） | `fork`+COW 进程池（上限 4）；类型表线性数组；符号查找**全表线性扫描** | 部分可抄（= LA5 + SP19） |

### 10.3 与 yh 病灶正对上的两处

1. **序列化往返的粒度**：Zig 也落盘（ZIR），但目的是"下次跳过 parse"且粒度=文件；
   yh 是每函数一份小文件，且环境键混入编译器二进制指纹（`size+mtime`）→ 有效窗口
   只有单个种子（§9.4）。**成本恒定、收益窗口窄**（SP20/SP21/SP7）。
2. **固定开销 × 单元数**：Zig 一个进程一个类型池，yh 是 13 个 worker 各重做
   `sem_init_tables` + `front_prepare` + 重解析全部依赖接口（SP8/SP9）。

### 10.4 抄不了的两条

1. **语言复杂度**：Zig 无运算符重载、无 trait 求解、无模板，部分快来自"语言要求
   编译器做的事少"；yh 语言已定，这部分差距不可消除。
2. **无历史包袱的自建后端**：Zig 从第一天就有；yh 在 LL12（2026-10-21）删除了直出后端
   （净减 6,516 行）。重做要重新解决已由 LLVM 解决过的 ABI/HFA/变参问题 ——
   只在 Tier 2 达标后仍嫌慢时才值得（SP17）。

### 10.5 由此校准 yh 的目标

| 目标 | 数值 | 靠什么 | 可达性 |
|---|---|---|---|
| 无操作 / 小改回路（对齐 Zig ①） | ≤0.3 s / ≤1 s | manifest + 文件级粒度 + 默认增量（SP12/SP14/SP21） | **可达** |
| 冷编全量（对齐 clang -O0） | 1–3 s | SP3/SP4/SP5/SP8/SP9 | **可达** |
| 冷编 <0.5 s（对齐 Zig ②） | — | 仅自建后端（SP17） | **不推荐现在做** |
