## 1. 取证摘要（2026-11-05 实测）

### 1.1 `--emit-asm` 失败面收窄

- 失败诊断「内嵌 LLVM：目标文件原子写入失败」是 `publish_buffer` 的**统一**
  失败文案（bridge.c:255）。
- `--emit-asm` 走 `out="-"`：`publish_buffer` 在入口就分流到 **stdout 写循环**
  （bridge.c:102-112，`write(STDOUT_FILENO,…)`，`write=_write`）——**完全不经过**
  `_mktemp_s/_open/MoveFileExA`（那四处服务对象文件发布，日常增量构建全在跑
  且全部成功）。
- 结论：失败点 = `_write(1,…)` 返回 ≤0，且仅在新闭包（`/MT` 静态 CRT）下
  复现。首要嫌疑：/MT 让进程内出现第二份 CRT（yh.exe 主体另一份），fd 1 的
  stdio 初始化/文本模式翻译差异；次要嫌疑：老 `rebuild-bridge.bat` 与
  `llvm-windows-closure.py build_bridge` 的其他编译开关差异。

### 1.2 桥的两代自举机制（ci-bootstrap.py）

gen-1 把源码临时改成「0.0.11 认识的等价形态」（移出 15 个 `*.windows.*.yh`
变体、`$if (windows)` 换对侧 OS 标记、清单去 windows 链接节）→ Release 种子
冷编出 yh1 → gen-2 恢复原样、yh1 冷编全量 HEAD。所有临时改动有 finally 恢复
+ 崩溃恢复备份。

### 1.3 `.test.yh` 改名的冲突机理

0.0.11 种子按文件名字典序扫描模块；无前缀的 `actions.test.yh` 等会排到
`cli.yh` 之前 → gen-1/gen-2 解析 `libs/cli` 直接报「未知类型」。而
`*.test.yh` 后缀本身 0.0.11 可接受（`pj_source_target_match` 未识别段放行），
0.0.11 时代的 `zz_`/`99_` 前缀排序语义仍然有效。

**解法**：gen-1 staging 增加第 4 类临时改写——把 16 个测试文件临时加回
`zz_`/`99_` 排序前缀（机制与 windows 变体移出完全一致，走同一套
finally 恢复 + 备份）。main 树保持无前缀最终形态不动。

### 1.4 自 2026-11-03 桥建立以来的其他源码变化（gen-1 兼容性盘点）

| 变化 | 0.0.11 兼容性 | 结论 |
|------|--------------|------|
| 版本功能（cmdline `--version`、libs/cli `version_text` 透传） | 纯既有语法（字段/枚举/字面量） | ✅ |
| `pj_name_is_test`/`pj_dir_less`（指针下标 + `to_type`） | 既有语法 | ✅ |
| `gen/console.*.yh` + driver 调用 | 平台文件机制既有；linux/darwin 空实现保符号 | ✅（windows 变体在 gen-1 被移出，非 Windows 宿主用 linux/darwin 文件） |
| SDK 迁移 vendor（纯路径字符串/文件移动） | 无语言面 | ✅ |
| `.test.yh` 改名 | **字典序破坏** | ❌ → §3 B1 处理 |
| 空函数体 `fn f() void {}`（console 空实现） | 需 gen-1 实跑确认；若 0.0.11 拒绝，staging 填入 `return` | ⚠️ B2 首跑验证点 |

## 2. Lane A：`--emit-asm` 修复（Windows 本机，可与 B 并行）

- **A1 复现矩阵**：新闭包 `yh.exe` 下，`--emit-asm` 分别向 终端 / 管道 /
  文件重定向 各跑一次，记录失败面；用旧旗标（对照 `tmp/rebuild-bridge.bat`
  与 `llvm-windows-closure.py build_bridge` 的完整命令行 diff）重编一座桥
  验证「旗标 → 失败」的单向归因。
- **A2 errno 诊断**：`publish_buffer` 失败分支把 `errno`（以及 out=="-" 分支
  的 `write` 返回值）拼进 diagnostic 文本（如「…原子写入失败（write=-1
  errno=EBADF）」）。一次重编即可定位到具体系统原因。
- **A3 根因修复**（按 A2 结果三选一）：
  - fd 1 在 /MT CRT 未初始化 → 启动期显式 `_setmode`/`__acrt` 触发 stdio 初始化；
  - /MT 与主体 CRT 双实例冲突 → 闭包桥改 `/MD` 或与主体同款运行库旗标；
  - 文本模式翻译问题 → fd 1 强制 `_O_BINARY`。
- **A4 验收**：`tests/selfhost/llvm-architecture.py` 绿；`just test` 全量绿
  （含 emit-asm 相关语料）；失败路径不破坏既有产物的语义保持。

## 3. Lane B：发布顺序线（串行主线）

- **B1 ci-bootstrap.py staging 扩展**：新增「测试文件临时改名映射」
  （16 个 `*.test.yh` → `zz_*/99_` 中间名），并入既有 VARIANTS 处理与
  恢复/备份机制；staged 清单同步。
- **B2 桥全流程本机验证**：`python3 tools/ci-bootstrap.py run` 本机实跑
  （Linux/WSL 或 CI 首跑均可），确认 gen-1 在「改名后源码」上通过；同时
  验证 §1.4 的空函数体兼容性（若失败，staging 补写法）。
- **B3 CI 解禁**：触发 `ci.yml`，四端 job 全绿（此时桥仍在，A3 的 bridge.c
  修复必须已合入）。
- **B4 rc tag → Release**：`release.yml` 产出四平台种子（内嵌按 HEAD 编译的
  桥 = 含 A3 修复 + test-last 排序规则）；发布说明标注 Windows 种子自此
  转正（todo 第 3 条随之关闭）。
- **B5 删桥**：ci.yml/release.yml 切回 `just bootstrap`、自举门改回默认
  种子，删除 `tools/ci-bootstrap.py`、`just bootstrap-bridge` 与 todo 条目
  （todo P0-2 关闭）。
- **B6 清账**：todo 「合流后首建」（P0-4）以本机 llvm-host 实跑证据勾选
  （`YH_LLVM_WINDOWS_WORK` 复用 CMake 树验证幂等）； Lane A 的 todo 条目
  勾选。
