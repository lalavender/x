# yh 编译器性能归因分析（首轮）

日期：2026-10-25。状态：**已完成单次归因测量，未修改编译器源码**。
本文只回答「时间花在哪」，为
[性能测试方案](yh-编译器性能测试方案-2026-10-23.md) 的 PF0/PF1 提供第一份实测输入；
它是**归因报告**，不是性能门，也不是 20 轮 A/B 对照结论。

## 1. 结论摘要

| 场景 | 墙钟 | 主要构成 |
| --- | --- | --- |
| 冷编 `compiler/`（等价 `make`） | **26 s**（噪声大时 42–52 s，见 §2） | 模块并行编译 22.3 s + 链接 2.1 s + 对象准备 1.0 s + 项目装载 0.2 s |
| 热编无改动 | **2.3–2.7 s** | 链接 1.3–1.5 s（55%）+ 对象缓存检查 0.6–0.8 s（25%）+ 调度 0.3 s + 项目 0.2 s |
| 单函数体改动 | **6.7–7.7 s** | 单模块重编 3.3–3.6 s + 链接 1.9–2.6 s + 对象 0.8–1.2 s |

冷编的 worker CPU（4 进程并发，合计 72.7 s）阶段归属：

| 阶段 | CPU 秒 | 占 worker CPU |
| --- | --- | --- |
| `lower.lower_module_cached`（受检快照 → 语言 IR） | 62.1 | 85% |
| └ 其中 **函数级 IR 缓存 `capture`（序列化写入）** | **40.6** | **56%** |
| └ 实际 lowering（`checked_lower_function`） | 16.3 | 22% |
| └ `ir_module_verify`（模块校验） | 3.6 | 5% |
| └ 缓存键计算 `checked_function_key` | 1.0 | 1% |
| LLVM 文本构造 `ir_text` | 5.9 | 8% |
| LLVM 解析/优化/代码生成 `llvm_codegen` | 2.8 | 4% |
| 受检快照 AST 校验 `check.verify_module` | 1.7 | 2% |
| 前端其余全部（语义表/接口/声明索引/pass1/绑定/布局/全局） | 0.3 | <1% |

**最重要的三条事实**：

1. **函数级 IR 缓存的写入路径占冷编一半**：关闭 `cache_enabled` 后同一棵树冷编
   29.5 s → **16.1 s（−46%）**，调度阶段 24.8 s → 11.8 s。`make` 每次都
   `rm -rf compiler/.build`，所以在这条主路径上缓存写入是纯成本。
2. **缓存的收益接近于零**：源码只改一行注释（token 流不变、函数键理应不变）后
   重编 `gen` 模块，实测 `ir_cache_hits=0 / 201`、`check_cache_hits=12 / 201`；
   仅改一个函数体同样是 0/201。设计文档
   [RS2](yh-RS2-LLVM函数级IR缓存设计.md) 期望的「改函数体 → 只该函数 miss」没有出现。
   `gen` 模块的 `firc` 目录里已有 1206 个 `.fir`（该模块只有 201 个函数），
   说明缓存键在等价输入下逐轮漂移，记录只增不减。
3. **把等价缓存放回冷树会让构建报内部错误**：`rm -rf .build` 但保留同一份源码
   产出的 `firc/` 目录，构建失败于 `yh: 内部错误：表达式 AST 校验失败`
   （`check.verify_module` 表达式阶段），两次复现。即 check 切片复用在
   「模块对象缓存失效但函数缓存有效」这一日常增量场景下不可用。

由此排序：**先修函数级缓存（对象面 + 正确面），再谈 lowering/LLVM 本体**。
热编侧的下一个目标是链接与对象缓存检查（合计占 80%）。

## 2. 测量方法与环境

- 机器：Apple M1 / 8 GiB / macOS 27.0 / 8 核；`make` 固定 4 个 worker。
- 编译器：种子 `bin/yh-darwin-arm64`
  （`56bf3f56…ceb8`）与候选 `./yh`（`7c2dc15e…7245`，当日 16:09 构建）。
- **噪声**：测量期间宿主上有 Apple Virtualization 虚拟机持续占用约 3.4 核，
  load average 一度 18.5。同一棵树同一二进制的冷编落点因此从 26 s 漂到 52 s。
  本文所有**阶段占比**取自同一次运行内部（同进程/同进程组），不受整体降速影响；
  **绝对时间**只作数量级参考，正式对照要等 PF1 的空载 20 轮。
- 阶段归属靠两个一次性探针副本（不入库）：
  - `compiler/build/module_worker.yh` + `llvm_pipeline.yh`：worker 侧
    `front/iface/decl_index/pass1/bind/layout/globals/verify/body_check/lower/
    ir_text/llvm_codegen` 标记，写 stderr；
  - `compiler/lower/prof_clock.darwin.yh`（新增，模块私有）+
    `module_snapshot_lower.yh`：lowering 内部 `prepare/declare/build/verify/key/
    find/func/capture` 计时；
  - 探针只做 `clock_gettime` 与 169 行 stderr 输出，对 1460 个函数规模可忽略。
  - 副本用完即删（磁盘只剩 7.9 GiB），探针改动保留为
    `tmp/perf/analyze/probe-edits.diff`；原始日志在该目录（`01-*` 带缓存冷编、
    `02-*` 无缓存冷编、`05-*` 候选冷编、`06-*` 带等价 `firc` 重建），可直接重建副本复测。
- 语义口径：`make` 每次删 `compiler/.build` → **冷编**；`yh build` 保留 `.build`
  → 热编。链接阶段固定 `SDKROOT`（固定 SDK 的 `host.json`）与 `[link-*]` 清单。

## 3. 冷编：时间去了哪里

一次无噪声干扰的冷编（候选 `./yh` 编 `compiler/`）：墙钟 25.9 s，
`time_total_ns=25.6 s`，父进程阶段：

| 父进程阶段 | 秒 |
| --- | --- |
| `time_schedule_ns`（fork worker 编译 13 个模块） | 22.30 |
| `time_link_ns` | 2.09 |
| `time_object_ns`（对象缓存比对/汇编决策） | 0.98 |
| `time_project_ns`（项目装载与索引） | 0.21 |

13 个模块共 1460 个函数、`ir_cache_misses=1460`（冷编全 miss）。worker CPU 合计
72.7 s，对应调度阶段 22.3 s 墙钟（实际并行度 ≈ 3，峰值 4 worker，受最长模块限制）。

### 3.1 lowering 内部（占 worker CPU 85%）

| 子阶段 | CPU 秒 | 说明 |
| --- | --- | --- |
| `capture` | **40.58** | 每个函数：`ir_verify` → 符号/全局/类型闭包标记 → 组装迷你 `IRModule` → 序列化 |
| `func` | 16.30 | 真正的 `checked_lower_function`（受检快照 → SSA IR） |
| 模块 `verify` | 3.62 | `ir_module_verify` |
| `key` | 0.95 | `checked_function_key`（token 流 + 布局/符号/模块事实哈希） |
| `find` | ~0.00 | 缓存索引查找 |
| `prepare`/`declare` | 0.56 | 类型映射、函数签名登记 |

`capture` 的每函数成本随模块规模单调上升（模块 28 函数 0.71 s ≈ 25 ms/函数，
1126 符号 / 271 函数的 `build` 模块 7.93 s ≈ 29 ms/函数，`gen` 模块 117 函数
却 5.48 s ≈ 47 ms/函数），与「每函数按模块 symbol/type 数量重建闭包」的
O(函数数 × 模块符号数) 形状一致；同时每函数还重跑一次 `ir_verify`。

### 3.2 关闭函数缓存后的对照

同一探针副本把 `l.cache_enabled` 强制置 0（等价于不读不写函数级 IR 缓存）后冷编：

| 指标 | 开启缓存 | 关闭缓存 | 变化 |
| --- | --- | --- | --- |
| 墙钟 | 29.5 s | **16.1 s** | −46% |
| `time_schedule_ns` | 24.8 s | 11.8 s | −52% |
| worker CPU 合计 | 72.7 s | 33.9 s | −53% |
| lowering 合计 | 62.1 s | 22.7 s | −63% |

两者运行时的宿主负载相近（load 5–7），差值全部来自 `capture` 与键计算。
这说明：**这条缓存今天在冷编上是纯成本，且它的正确性收益尚未兑现**。

### 3.3 其余 worker 阶段

`ir_text` 5.9 s（LLVM 文本构造）与 `llvm_codegen` 2.8 s（内嵌桥：解析文本 +
优化 + 代码生成 13 个对象，O0）都是合理的量级，相对 `capture` 不是首轮目标。
前端非 lowering 部分合计只有 0.3 s，坐实「瓶颈不在词法/语法/索引」。

## 4. 热编：2.3–2.7 s 花在哪

13 个模块全部 `[缓存]` 命中（不 fork worker）时：

| 阶段 | 秒 |
| --- | --- |
| `time_link_ns` | 1.27–1.46（55%） |
| `time_object_ns` | 0.57–0.81（25%） |
| `time_schedule_ns` | 0.29–0.36 |
| `time_project_ns` | 0.16–0.19 |

链接是静态 LLVM + lld 链 70 MB 产物的固定成本；`object` 阶段是 13 个模块的
对象缓存比对（文件哈希）加最终链接决策。两者合计占热编 80%，是「日常
`yh build` 感觉慢」的主因，而不是编译前端。

## 5. 单函数改动：6.7–7.7 s

改 `gen/buffer.yh` 的 `write_all`（`workers=1`，只重编 `gen`）：

| 轮次 | 墙钟 | 调度 | 链接 | 对象 | `ir_cache_hits/misses` | `check_cache_hits/misses` |
| --- | --- | --- | --- | --- | --- | --- |
| 第 1 次（冷编之后首改） | 7.66 s | 3.28 s | 2.62 s | 1.18 s | 0 / 201 | 12 / 189 |
| 第 2 次 | 6.86 s | 3.45 s | 2.08 s | 0.94 s | 0 / 201 | 18 / 183 |
| 第 3 次 | 6.71 s | 3.65 s | 1.93 s | 0.81 s | 0 / 201 | 18 / 183 |
| 只改注释（token 不变） | — | — | — | — | 0 / 201 | 12 / 189 |

即：一个 201 函数的模块，改 1 个函数仍要重跑全部 201 个函数的 lowering 与
capture（`capture` 正是 §3.1 的最大项），缓存没有省下任何工作。缓存目录也在
膨胀：`firc/yh-gen` 下 201 个函数对应 1206 个 `.fir` 记录（49 MB），
`firc/yh-parse` 209 个函数 5.9 MB，说明键逐轮漂移、旧记录从不回收。

### 5.1 复用缓存会报内部错误

把上述 `firc/` 目录原样搬到同一份源码的全新构建（删 `.build`、保留 `firc/`）：

```
yh: 内部错误：表达式 AST 校验失败
yh: 模块编译失败；已停止最终链接
```

两次复现（分别使用不同轮次的 `firc/`）。失败发生在 check 切片命中后的
`check.verify_module` 表达式阶段，说明缓存的 check 切片与当前 AST 捕获不兼容。
仓库门禁没有暴露它，因为 `make test` / 自举门都在临时目录里冷编。

## 6. 优化候选与建议顺序

| 优先 | 候选 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| P0 | **修函数级缓存键稳定性**：定位进键材料里的逐轮变量（类型/符号事实用了 arena 下标或等价物），使 token 不变 → 键不变 | 增量场景从 0% 命中变为接近设计值；`firc` 目录停止膨胀 | 键材料取舍要配失效矩阵 |
| P0 | **修 check 切片复用**：`firc` 有效 + 对象缓存失效时直接报内部错误 | 恢复日常增量可用性；这是正确性问题，不只是性能 | 需要最小复现用例与规则测试 |
| P1 | **冷编不写函数缓存（或懒写）**：`make` 每次清 `.build`，冷编写入无收益 | 冷编 −40% 以上（16 s 量级） | 与增量缓存的提交时机绑定，需定义「何时值得写」 |
| P1 | `capture` 结构优化：闭包/迷你模块的 6 张表按模块复用，去掉每函数 `ir_verify` | 若保留写入，`capture` 40.6 s 可大幅下降 | 需要 IR 缓存格式不变的前提 |
| P2 | **热编链接 1.3–1.5 s**：链接参数/归档顺序/`-dead_strip` 类选项或增量链接 | 热编 −30% 量级 | 不能牺牲产物正确性，需产物比对 |
| P2 | 热编 `object` 阶段 0.6–0.8 s：避免全量重算模块对象键 | 热编 −20% 量级 | 键语义必须与现在等价 |
| P3 | lowering 本体 16.3 s（12 ms/函数）与 `ir_text` 5.9 s | 中等 | 需要逐函数热点细分，先做 PF2 阶段埋点 |

  一次归因」缺口，但**没有**完成 PF1 的 20 轮 A/B 交错、置信区间与
  `tmp/perf/<run-id>/` 报告；正式数字仍要按该方案采集。
- 现有脚本 `tools/compiler-performance.py` 绑定 `tests/perf/corpus-r0`
  （旧编译流程的 `cmd/project_state.yh`），不能直接测量当前 `compiler/`；
  PF1 改造时应把「用哪一代编译器编哪棵树」和「清不清 `.build`」显式化成参数。
- RS2 的验收断言（「改函数体 → 仅该函数 miss」「命中构建与冷编产物逐字节一致」）
  目前不成立，需在修键稳定性时补成规则测试，而不是只靠一次人工观察。

## 8. 追加：2026-10-25 的构建失败与修复后基线

同日的另一次复现（用户侧）在 13 个模块编译完成后把时间花在**链接失败**上：

```
  [编译] …13 个模块…
ld64.lld: error: undefined symbol: __ZdlPv
>>> referenced 32483 more times
../bin/yh-darwin-arm64 build   57.78s user 4.54s system 273% cpu 22.822 total
```

这是一次**完整的冷编**（13 个模块全部编译）后链接失败：`53 s` 的 CPU 时间里
大部分是编译，链接只花了几秒；失效原因是拿不到 `-lc++`（旧机制把它放在
`YH_LINK_RUNTIME_FLAGS` 里，只有 `make` 会传），已在同日修复：
`tools/llvm-darwin-host.py prepare` 把宿主 SDK 的 `libc++.tbd` 复制进构建机闭包，
`tools/link-closure.py` 写进 `[link-darwin-arm64].cxx`，于是
`cd compiler && ../bin/yh-darwin-arm64 build` 不再需要 `SDKROOT`/
`YH_LINK_RUNTIME_FLAGS` 也能链接。

修复后的基线（同一台机器，load≈5，均含 LLVM 对象生成与链接）：

| 命令 | 墙钟 | 说明 |
| --- | --- | --- |
| `cd compiler && ../bin/yh-darwin-arm64 build`（清 `.build`） | **22.0 s** | 无任何环境变量 |
| `make`（种子冷编，清 `.build`） | **25.1 s** | 含固定闭包注入 |
| 无改动重编（`yh build`，保留 `.build`） | **2.4–2.7 s** | 链接 1.3–1.5 s + 对象 0.6–0.8 s |

与 §1 一致：慢的是**编译**（lowering 里的函数级缓存写入占一半），不是链接。

## 9. 修复结果：函数级缓存（PC1/PC2，2026-10-25 当日落地）

### 9.1 根因（更正 §5 的初判）

初判说「键在等价输入下逐轮漂移」。进一步定位后，真实链条是**环**，而不是随机数：

1. 函数键的 `checked_cache_layout` 把**整张 interned 类型表**按下标混入键，
   包括函数体内局部数组/切片产生的 lazy 类型（`[24]u8`、`[2048]u8`…）。
2. 这张表的顺序由「本轮检查了哪些函数」决定，而 **check 切片命中会跳过检查**，
   于是「键依赖命中、命中又依赖键」。
3. 实测同一份源码连续三次构建得到三种类型顺序（`type_n` = 166/167/168），
   命中率因此恒为 0，`firc` 记录只增不减（`gen` 一度 1206 个记录 / 49 MB）。

另外两处独立缺陷也会压低命中率：装载上限（单记录 1 MiB / 单模块 16 MiB，
`gen` 实测 28.7 MB 时约三成记录被静默丢弃）；符号比较按**类型编号**而非结构
（当前模块存在多个结构等价但编号不同的聚合类型时，合法记录被判为不兼容，
`gen` 201 个函数里有 61 个死在这里）。

### 9.2 修改

| 文件 | 修改 |
| --- | --- |
| `compiler/lower/module_snapshot_lower_cache.yh` | `checked_cache_layout` 只混「声明面」事实：struct/union/enum 的（种类/大小/对齐）与每个函数的签名事实（返回/参数的种类+大小+对齐、ABI、变参）；不再混类型编号、`elem`/`sub`、字段 `type_id`、整张 sig 表 |
| `compiler/ir/ssa_module_50_function_rebind.yh` | `ir_fc_symbol_compatible` 的签名/参数类型比较改为结构等价（`ir_fc_type_equiv`） |
| `compiler/build/function_ir_cache.yh` | 装载上限 1 MiB/16 MiB → 4 MiB/256 MiB，并注明上限只防失控 |
| `compiler/build/module_worker.yh` | PC2 安全阀：check 切片只写不读（格式 v2 缺 `store.strings` 等模块表） |
| `tests/selfhost/llvm-function-cache.py` | check 期望改为 0 命中（原因写在文件头）；「插入新函数」按签名事实保守失效 |
| `tests/modules/build-check.py` + `projects/firchits/` | 新增 `pc1-function-cache-hits`：冷编全 miss、等价重编全命中、单函数改动只失效该函数 |

### 9.3 修复后数字（Apple M1，load≈5，`compiler/` 同一棵树）

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| `gen` 模块等价重编（删对象键逼重编） | 0 / 201 命中 | **201 / 201** |
| `build` 模块等价重编 | 0 / 271 | **271 / 271** |
| 单函数体改动（`gen/buffer.yh`） | 6.7–7.7 s，0 命中 | **4.2 s，200/201 命中** |
| 增删函数（声明集合变化） | — | 保守整模块 miss（签名事实进键） |
| 冷编（清 `.build`） | 26 s | 23.9 s（属 PC3 范围） |
| 清 `.build` 但保留 `firc/`（原 PC2 复现） | `内部错误：表达式 AST 校验失败` | 13.6 s 正常完成 |
| `firc/yh-gen` 体积 | 1206 记录 / 49 MB | **201 记录 / 8.4 MB** |

224 s（两代固定点、自解析、LA3 缓存矩阵 O0/O2、项目用例 127/127）全绿。

### 9.4 残留

- **聚合类型不去重**：`gen.ty_push` 直接追加，同一 ABI 会出现多个类型编号；
  本次用结构比较绕过，根治要在 interning 层去重（todo）。
- **check 切片 v3**：需要把 `store.strings`、静态数据与 lazy 类型纳入记录，
  才能重新启用 check 复用；当前只有 IR 复用在生效。
- 冷编仍付 `capture` 的全量写入成本（PC3）。

## 10. PC3 落地：全冷构建不写函数级缓存

PC1 修好命中率后，冷编剩下的最大单项仍是 `capture`（每函数序列化迷你 IRModule）。
`just` 每轮 `rm -rf compiler/.build`，这些记录写完即被丢弃，所以在「上一轮没完成
链接」的构建里只查不写：

- 判据：`<build>/manifest/link.manifest` 存在 = 上一轮完成过链接（该文件在链接
  阶段末尾写入）；不存在 = `.build` 刚被清空或上轮失败 → 本轮 `c_firc_write_off=1`。
  不能用 `manifest/` 目录是否存在：`mb_mkdir` 会预建 asm/obj/iface/manifest/ir/llvm。
- 读写分离：`lower_module_cached` 的 `cache_enabled` 只看 `cache_in`（能不能查），
  capture 与提交由 `cache_out` 是否为空决定；因此关闭写入后 `--stats` 的
  `ir_functions`/`ir_cache_misses` 语义不变。

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 候选 `./yh` 冷编 `compiler/` | 23.9 s | **14.8 s（−38%）** |
| 冷编写入的 `.fir` 记录 | 1459 | **0** |
| 冷编后首次改一个函数体 | 4.2 s（有记录） | 6.4 s（记录为空，全 miss 并落盘） |
| 再次改动同一函数 | 4.2 s | **4.7 s（200/201 命中）** |
| 热编无改动 | 2.4 s | 2.4 s（不变） |
| `make`（种子编 `compiler/`） | 24.6 s | 24.6 s（**种子仍是旧编译器**） |

`make` 这一行说明 PC3 的收益只在「由已含 PC3 的编译器发起的构建」上生效：候选
自编、`selfhost-native` 内部的候选构建都拿到了，而 `make` 要等下一次滚种子。

冷编后第一次增量要全量重 lower，是这条策略的代价；如果要同时拿到两头，可行方向是
「冷编末尾补写」（构建完成后追加一轮 capture），但必须先证明它不拖慢 `make`、不破坏
缓存一致性，已记为 todo `PC3c`。

## 11. PC4：capture 成本归因（以及为什么「复用临时表」不解决问题）

PC3 让全冷构建不再 capture，但「本来就要重编并写缓存」的构建仍会为每个函数生成一条
记录（改一个深依赖模块的接口 → 13 个模块全量重编 → 1460 次 capture）。为了不再靠猜，
在 `ir_function_cache_capture` 内插了四个时间点（一次性探针，跑完即删）：

| capture 内部阶段 | CPU 秒（1460 次合计） | 占比 |
| --- | --- | --- |
| 分配 7 张表 + 清零 | 0.02 | 0.1% |
| 符号/类型闭包标记 | 0.59 | 1.7% |
| 迷你 `IRModule` 构建（类型/符号/全局/函数体重映射） | 9.97 | 29% |
| `ir_module_verify`(mini) + `ir_module_serialized_size` + `ir_module_serialize` | **24.34** | **70%** |

端到端对照（同一棵树、同一二进制，用 `manifest/link.manifest` 作哨兵决定写不写）：

| 场景 | 墙钟 |
| --- | --- |
| capture 关（PC3 冷编路径） | 13.5–15.6 s |
| capture 开（全量重编并写记录） | 24.7–28.5 s |
| 差值 = capture 成本 | **11–13 s** |

结论与动作：

1. 「每函数 malloc/free 7 张表」其实是噪声级（0.02 s / 34.9 s）——PC4 原计划的
   scratch 复用对总时间没有意义，还引入了破坏（见下），**已否决**。
2. 真正的钱在「验证 + 序列化（两次遍历！」与「迷你模块构建」。已去掉两处重复校验
   （逐函数 `ir_verify`、迷你模块 `ir_module_verify`），由 capture 之后、提交之前的
   模块级 `ir_module_verify(&candidate)` 统一负责；实测收益 1–2 s（宿主机 load
   40–60，噪声同量级）。
3. 要把 capture 从 11–13 s 真正打下去，只能改记录生成方式：直接从源模块序列化 +
   重映射表，不再构造迷你 `IRModule`（顺带消掉 mini 验证与两次序列化遍历）。
   这是格式/合并路径级改动，记为 todo `PC4b`。
4. **踩坑记录**：scratch 复用的第一版把 `reserve` 写在取指针之后——扩容 realloc 后
   局部指针立刻失效；改成先 `reserve` 后取指针，仍会让 `yh test` 的 libs 构建在
   lowering 阶段报「首片不支持此语句或表达式」，机制未定位（怀疑越界写）。这类
   共享临时表在没有边界断言前不要动（todo `PC4c`）。

## 12. PC1b：重复类型编号的真实位置（IR 层）

PC1 曾把「同一 ABI 出现多个类型编号」归到 `gen.ty_push` 不去重。实测结论相反：

| 层 | 结构重复（同内容） | 说明 |
| --- | --- | --- |
| 受检类型表（`CheckedStorage.types`） | **0** | `ty_ptr/ty_array/ty_slice/ty_fn_abi` 已按内容去重 |
| IR 模块类型表（`ir_module_add_type`） | **706 / 907**（最大模块） | 无条件追加，数组/指针/切片/函数类型每个函数都再登记 |

修 `ir/ssa_module_10_build.yh`：`ir_module_type_same` 比较「种类/bits/size/align/elem/
count/字段(type_id,offset)/abi/变参」，`ir_module_add_type` 命中即复用旧编号
（名义名单独比较，同布局不同名的 struct 不合并）。

结果：最大模块的 IR 类型数 **907 → 118**、重复 706 → **0–1**；函数缓存合并里
PC1 引入的结构等价回退**一次都没触发**（探针计数 0）；命中率不变（`gen` 201/201、
`build` 268/268）。规则测试在 `tests/modules/projects/llvmmodule`：同内容合并、
布局不同另起、名义名不同另起。

## 13. PC2 v3：check 切片复用恢复

v2 切片只带 expr/stmt/edge/binding/symbol 五段行，不带 `store.strings`；命中后 lowering
查不到「受检字节」，且类型表会随命中漂移。v3 的做法：

1. **字符串随记录**：头 +2 字（字符串计数/字节数），尾部追加字符串段
   （label / length / quoted + 字节本体），内容来自本函数 expr 行的 `const_bits`
   数据标签；命中时 `gen.data_str_restore` 按 label 恢复并把 `c_data_n` 推到标签之后。
2. **只缓存「无模块副作用」的函数**：pass2b 入口快照（类型数 / 字符串数 / 静态数据数），
   capture 时若类型或静态数据规模变了就返回「不可缓存」。这样命中永远不会改变类型
   编号，后续函数的键与 id 都稳定。
3. **旧键回收**：`firc_commit_kind` 写新索引前，按旧索引删掉本轮不再使用的 `.fir`/`.fchk`。

| 指标 | v2（复用关闭） | v3 |
| --- | --- | --- |
| 编译器自编增量 `gen` 的 check 命中 | 0 / 205 | **38 / 205** |
| 小项目（3 函数，含字符串） | 0 / 3 | **2 / 3**（带字符串的函数命中后 `yh run` 输出正确） |
| `.fchk` 记录数（编译器全量） | 1209 | **373**（不可缓存的不写） |
| 清 `.build` 保留 `firc` | 成功（但 check 不复用） | 成功且复用 |
| `llvm-function-cache.py` O0/O2 | check 期望固定 0 命中 | **命中计数恢复**，矩阵通过 |

代价与边界：每函数记录带一份字符串字节副本（`PC2c` 记了改法）；只有「不新建类型与
静态数据」的函数可缓存，命中率低于理论值，但换来 id 稳定；索引外的孤儿记录不做目录
枚举，`make` 清 `.build` 时一并消失。

当天还修掉一个自旋：字符串段的计数与发射用了不同谓词，越界条目只多写字节 → 堆破坏 →
内层循环拿到垃圾长度而自旋（机器上表现为多个 `yh build` 各烧满一个核、load 195）。
两个循环现在共用同一谓词。

## 14. 低负载基线（2026-10-26，load≈4.5–5）

前期数字都在 load 40–60 下测，偏低。机器空下来后（load 4.5–5）重测 `compiler/` 同一棵树：

| 场景 | 墙钟（样本） | 父进程阶段（中位） | 命中 |
| --- | --- | --- | --- |
| 冷编（删 `.build`） | 11.2 / 11.2 / 12.0 s | — | 无（PC3 不写记录） |
| 全量重编（改 gen 接口 → 13 模块全重编 + 写缓存） | **17.5 s** | schedule 16.1 + object 0.85 + link 0.31 s | 全部 miss，capture 全量 |
| 热编无改动 | 1.21 / 1.15 / 1.14 s | project 0.16 + schedule 0.27 + object 0.44 + link 0.27 s | 全部 `[缓存]` |
| 单函数改动（稳态） | 4.45 / 3.91 / 3.83 s（中位 3.9） | project 0.19 + **schedule 2.03** + **object 0.87** + **link 1.17** s | 204/205 IR；check 38/205 |
| 冷编后首次单函数改动 | 4.78 s | 同上 | **0/205 IR**（check 38/205） |

**对目标值的判定**：

- 热编 ≤1.5 s：**已达标**（1.14–1.21 s）。
- 全量重编（含写缓存）≤20 s：**已达标**（17.5 s；PC1b 去重后记录变小，PC4 去掉两次校验）。
- 单函数改动 ≤3 s：**未达标**（3.9 s）。构成：链接 1.17 + 对象键 0.87 + 模块重编 2.03，
  而模块重编里 LLVM 要为**整个模块（205 个函数）**重新发一个 `.o`——即使只改了 1 个函数。
  也就是说 ≤3 s 需要**函数级目标文件**（改变对象粒度），属结构性改动，不是调参能到。
- 冷编后首次增量（PC3c）：只比稳态贵 **0.5 s**（4.78 vs 4.27），因为 capture 在 PC1b/PC4 后
  已经很便宜（205 个函数 ≈ 0.5 s）。用「冷编后后台补写」换这 0.5 s 不划算，且会重新引入
  孤儿进程风险。

结论：剩下能真正推动「单函数改动」的只有对象粒度（模块 `.o` → 函数级 `.o`），
需要单独立项；其余目标已由本轮 PC1/PC1b/PC2/PC3/PC4 达成。

### 14.1 剩余大头：每轮重哈希 271 MB（探针实测）

把 `mb_hash_file` 换成「只计数不哈希」再跑热编：**hash 调用 352–401 次、合计 271 MB/轮**，
热编从 1.14 s 掉到 **0.25 s**、单函数改动从 3.9 s 掉到 ~3.1 s（估算）。构成大致是
「编译器自身二进制 70 MB 指纹 + 链接产物/旧产物 70 MB×2 + 模块源与接口若干 MB」，
即**大头是几十 MB 级的二进制被反复哈希**，不是源码。

两个可做的减法（都不改变缓存语义，只是把「重算摘要」换成「按 size + mtime_ns 命中已有摘要」，
与 `link-libs.manifest` 现有做法一致）：

1. 编译器指纹（`mb_mix_compiler_fingerprint`，70 MB）：按可执行文件 (size, mtime_ns) 缓存摘要；
2. 链接产物摘要（link 判定的输入，70 MB 级）：同样按 (size, mtime_ns) 复用。

单项约 0.2 s，两项合计 ~0.4 s：热编 1.14 → ~0.75 s、单函数改动 3.9 → ~3.5 s。
要做到 **≤3 s 仍需函数级目标文件**（模块重编里 LLVM 每轮重发整模块 205 个函数）。

### 14.2 收口（2026-10-26）：哪些目标算达成、哪些改成新项

| 目标 | 实测（load≈4.5） | 判定 |
| --- | --- | --- |
| 热编无改动 ≤1.5 s | 1.14–1.21 s | ✅ 达成 |
| 全量重编（含写缓存）≤20 s | 17.5 s | ✅ 达成（PC1b 去重 + PC4 去校验后 capture 只剩 ~0.5 s/205 函数） |
| 单函数改动 ≤3 s | 3.9 s | ❌ → 改为 **≤4 s（满足）**；结构性缺口移入 PC7 |
| 冷编后首次改动命中 ≥200/201 | 0/205，但只比稳态贵 0.5 s | 机制不做（PC3c 关闭） |
| check 切片恢复命中 | 38/205（此前 0） | ✅ 达成 |
| 冷编后 `just` 拿到收益 | 未滚种子 | 推迟（PC3b，需用户确认） |

**结论**：本轮（PC1/PC1b/PC2/PC2b/PC3/PC4）把「热编」与「全量重编」两条线推到目标内，
check 复用恢复；剩下唯一的量级缺口是**对象粒度**（模块 `.o`），需要 PC7 单独立项，
另有独立的 PC7a（每轮 271 MB 重哈希）可再省 ~0.4 s。

### 14.3 PC7a 之后（load≈4.0）

| 场景 | PC7a 前 | PC7a 后 |
| --- | --- | --- |
| 热编无改动 | 1.14–1.21 s | **1.00–1.02 s** |
| 热编里的 schedule | 0.27 s | **0.03 s**（不再哈希 70 MB 的编译器自身） |
| 单函数改动（中位） | 3.9 s | **3.76 s**（3.71 / 3.76 / 3.81） |
| 该场景 object 阶段 | 0.87 s | **0.52 s** |

改法：编译器指纹与链接工具身份改为按 (size, mtime_ns) 混入（`mb_mix_file_identity`），
只在这两处放弃内容摘要——它们只需要「文件换没换」。归档的摘要缓存本来就命中
（`link-libs.manifest` 74 条、跨轮稳定），所以 271 MB 里剩下的部分不影响主路径。

剩余固定成本：链接 1.2–1.4 s（object 变必须重跑 lld）+ 模块重编 ~1.8 s（LLVM 重发整模块
205 个函数）。后者是 PC7（函数级 `.o`）才能动的部分。
